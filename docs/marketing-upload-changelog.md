# 마케팅 리포트 업로드 — 변경 이력

`marketing_service.py`(CSV 업로드 → KPI 계산 파이프라인) 변경 사항을 시간순으로 누적한다.
새 변경이 생기면 파일 맨 위(최신순)에 새 항목을 추가한다.

## 2026-07-21 (3) — 구글 파일 동시 업로드 정밀 검증 + 기간(period) 오인식 수정

**배경**: "구글 캠페인데이터+전환데이터 파일이 동시에 업로드돼도 정상 작동하는지 정밀 확인해달라"는 요청. 실제 `/upload`(`_run_analysis` → `_classify` → `process_and_analyze`) 경로를 인메모리 SQLite로 재현해 검증.

**검증해서 확인된 정상 동작**:
- `_classify`가 파일 순서(캠페인 먼저/전환 먼저)에 상관없이 정확히 conv/media로 분류됨.
- 두 파일을 한 번에 업로드하면 `구글SA` 12개 행이 노출/클릭/비용 + 전환 지표가 한 행에 모두 채워진 채로 정확히 저장됨(수기 검산 완료).
- 동일한 두 파일을 재업로드해도 중복 생성 없이 "updated"로 정상 갱신되고 값이 일관됨(더블카운트·초기화 없음).

**정밀 검증 중 새로 발견한 이상 1건**: `_extract_period()`가 파일명에서 기간을 못 찾으면 CSV 내용에서 폴백으로 찾도록 지난 변경에서 고쳤었는데, 그 정규식(`\(2026\.06\.01\.~...\)` 형태)이 네이버 dot 표기만 지원했다. 구글 Ads 내보내기의 기간 행은 `"2026년 6월 1일 - 2026년 6월 12일"` 형식이라 매칭되지 않고, 게다가 구글 파일은 UTF-16이라 ASCII 바이트 사이에 널바이트가 끼어 raw 바이트 정규식 자체가 원천적으로 못 찾는 구조였다. 결과적으로 구글 파일 업로드 시 기간이 항상 기본값 "26년 5월"로 잘못 표시됨을 재현 확인 — 실제 데이터는 6월인데 `/export` 다운로드 파일명이 `마케팅분석_26년5월.xlsx`로 나가는 등 표시상 혼선이 있었음(단, DB에 저장되는 `report_date`는 각 행의 실제 날짜라 데이터 자체는 정확했음).

**변경 내용**:
- `_period_from_content()` 추가: raw 바이트 정규식 대신 파일의 실제 인코딩(BOM으로 UTF-16 여부 판별)으로 먼저 디코딩한 뒤, 네이버 dot 표기와 구글 `YYYY년 M월` 표기 둘 다 인식하도록 정규식 확장.
- 캠페인 파일 단독/전환 파일 단독/두 파일 동시 업로드 모두 기간이 "26년 6월"로 정확히 추출되는지 확인, 기존 네이버 dot 표기·파워컨텐츠 단독 파일 회귀 없음 확인.

**파일**: `back/app/services/marketing_service.py`

## 2026-07-21 (2) — 구글 Ads 네이티브 내보내기 지원 + "파일 하나씩 업로드" 데이터 유실 버그 수정

**배경**: `(HM)SA daily_캠페인데이터 (3).csv` + `(HM) SA daily_전환데이터 (3).csv`(구글 검색 캠페인)를 업로드해도 구글SA 탭에 반영되지 않는다는 문의. 추가로 "파일을 1개씩 업로드하면 잘 안 된다"는 별도 증상 보고.

**파일 정밀 분석 결과 (이상 3건, 순차적으로 겹쳐 있었음)**:
1. 두 파일 모두 **UTF-16(BOM `\xff\xfe`) 인코딩 + 탭(`\t`) 구분자**로 저장되어 있었음. 기존 `_read_csv`는 utf-8-sig/utf-8/cp949/euc-kr만 시도하고 구분자는 항상 콤마로 가정 — 두 파일 다 인코딩 단계에서부터 `CSV 파싱 실패` 예외로 죽는 것을 재현 확인. **이게 "파일을 1개씩 올려도 안 된다"의 1차 원인** — 같이 올리든 따로 올리든 이 형식 자체를 아예 못 읽었음.
2. 컬럼명이 기존 네이버 표준과 다름: `일`(not 일별), `캠페인 유형`(공백 있음, not 캠페인유형), `비용(VAT포함)`(not 총비용), `전환 액션`(not 전환 유형). 메타 행도 3줄(제목/기간/헤더)로 네이버 표준(2줄)과 다름.
3. **더 심각한 기존 버그 발견**: `MarketingRepository._upsert()`가 (날짜, 매체) 키로 기존 행을 **통째로 DELETE 후 새로 INSERT**하는 방식이었음. 캠페인 파일만 올리면 노출/클릭/비용은 채워지고 전환 관련 필드는 0으로 계산되는데, 이 상태로 저장한 뒤 나중에 전환 파일만 따로 올리면 이번엔 반대로 전환 필드만 채워지고 노출/클릭/비용이 0으로 계산된 행이 **기존 행을 통째로 덮어써서 방금 전에 저장했던 노출/클릭/비용 값이 사라짐**. 인메모리 SQLite로 재현 확인 — **이게 "파일을 1개씩 올리면 잘 안 된다"의 진짜 핵심 원인**. 네이버 쪽도 파일을 나눠 올리면 동일하게 발생할 수 있는 잠재 버그였음(이번에 같이 수정).

**변경 내용**:
- `_read_csv()`: BOM으로 UTF-16 여부를 감지해 `encoding="utf-16", sep="\t", skiprows=2`로 분기 파싱하는 전용 경로 추가 (다른 형식은 이 BOM을 쓰지 않아 오탐 없음).
- `_is_google_campaign()` / `_is_google_conversion()` / `_google_conv_subset()` 추가로 구글 포맷 판별. `_is_conversion()`(파일 분류기)도 "전환 액션" 컬럼을 인식하도록 확장 — 전환 파일만 단독 업로드해도 media가 아닌 conv로 정확히 분류됨.
- `GOOGLE_CONV_ACTION_MAP`으로 의뢰자 요청 통합 규칙을 그대로 반영:
  `설명회신청 = 설명회신청 + 설명회신청완료_MO`, `구매완료 = 인강구매완료 + 인강구매완료_의약`, `회원가입 = 회원가입`.
  `_calc_google_kpis()`(캠페인+전환 함께) / `_calc_google_conv_only_kpis()`(전환만 단독)에서 이 매핑으로 집계 후 `구글SA` 라벨로 반환 — 실제 파일로 계산해 수기 검산 완료(예: 06-01 구매완료=97.22+1.90=99.12, 매출=12,119,178.20+1,067,800.00=13,186,978.20).
- `_finalize_daily_kpis`의 CTR/CPC/전환율 등 파생지표 계산부를 `_compute_kpi_ratios()`로 추출해 네이버/구글 계산 공용화.
- **`_upsert` 필드그룹 병합 수정**: `save_from_kpis()`가 라벨별로 이번 업로드가 media(노출/클릭/비용) 그룹과 conv(전환 관련) 그룹 각각을 실제로 갖고 있었는지(`media_authority`/`conv_authority`) 계산해 전달. `_upsert()`는 기존 행이 있고 이번 업로드가 특정 그룹을 갖고 있지 않으면 그 그룹만 기존 DB 값을 유지한 채 나머지만 갱신 — 파일을 어떤 순서로 나눠 올려도 데이터가 사라지지 않음. authority 컬럼이 없는 기존 호출(`save_dataframe`/`save_mapped_dataframe`)은 그대로 완전 덮어쓰기 동작 유지(회귀 없음).

**검증**: 실제 두 구글 파일로 조합 업로드(회원가입/구매완료/설명회신청 수치 수기 검산) + 캠페인 단독/전환 단독 각각 업로드 + 인메모리 SQLite로 "캠페인→전환", "전환→캠페인" 양쪽 순서 모두 값이 올바르게 병합되는지 확인 + authority 컬럼 없는 레거시 경로 회귀 없음 확인.

**참고**: 프론트엔드(`ReportView.tsx`/`ExcelReportView.tsx`)는 이미 `구글SA` 라벨을 `MEDIA_ORDER`에 갖고 있어 프론트 변경 없이 바로 탭에 표시됨.

**파일**: `back/app/services/marketing_service.py`, `back/app/repositories/marketing_repo.py`

## 2026-07-21 — 파워컨텐츠 단독 다운로드 CSV(캠페인유형 컬럼 없음) 지원 추가

**배경**: 의뢰자가 업로드한 `work/(HM) daily,1921185 (4).csv`가 적용되지 않는다는 문의.

**파일 자체 정밀 분석 결과**: 데이터 품질 이상은 없음 (2026.06.01~06.12 12일 연속, 중복/결측/음수 없음). 문제는 구조:
- 컬럼이 `일별, 노출수, 클릭수, 총비용` 4개뿐이고 `캠페인유형` 컬럼이 없음 — 이미 한 매체(파워컨텐츠)만 필터링되어 내려받은 "일별" 리포트.
- 기존 파이프라인은 미디어 CSV에 `캠페인유형` 컬럼이 항상 있다고 가정하고 `df_media["캠페인유형"]`으로 필터링했는데, 이 컬럼이 없어 **`KeyError: '캠페인유형'`로 즉시 크래시**하는 것을 재현 확인. 이게 "적용이 안 된다"의 원인.
- 부수적으로, 파일명(`(HM) daily,1921185 (4).csv`)에는 기간을 알 수 있는 패턴(YYYYMMDD, YY.MM)이 없어 기간 자동 인식이 기본값("26년 5월")으로 잘못 잡히는 것도 확인.

**변경 내용**:
- `_is_single_media_daily()` 추가: `일별/노출수/클릭수/총비용` 4개 컬럼만 있고 `캠페인유형`이 없는 파일을 "단독 매체 일별 리포트"로 판별.
- `_calc_single_media_kpis()` 추가: 이 형식은 **파워컨텐츠(네이버PSA)로 확정 처리**. 파일 내용만으로는 어떤 매체인지 판별할 근거가 없어 사용자 확인(이 파일=파워컨텐츠)을 그대로 반영한 것 — **다른 매체도 동일한 4컬럼 포맷으로 내려받게 되면 이 가정이 깨짐**. 그런 사례가 실제로 생기면 업로드 시 매체를 직접 지정하는 UI가 필요.
- `_calc_kpis()`의 전환 데이터 조인 + 비율 지표(CTR/CPC/전환율 등) 계산 로직을 `_finalize_daily_kpis()`로 추출해 `_calc_kpis`/`_calc_single_media_kpis` 둘 다 공용으로 사용하도록 리팩터링 (동일 로직 중복 방지).
- `_extract_period()`가 파일명에서 기간을 못 찾으면 CSV 제목 행(`(2026.06.01.~2026.06.12.)`)에서 폴백으로 기간을 읽도록 개선 — 인코딩이 깨져도 날짜 자체는 ASCII라 바이트 매칭으로 안전하게 추출.
- `process_and_analyze` / `process_for_export` 양쪽에 `_is_single_media_daily` 분기 추가, `_extract_period` 호출 시 파일 content도 함께 전달하도록 변경.

**검증**: 실제 클라이언트 파일로 전체 파이프라인(`process_for_export`) 통과 확인(기존엔 크래시) + 기존 결합형(캠페인유형 컬럼 포함) CSV 회귀 테스트 통과.

**파일**: `back/app/services/marketing_service.py`
