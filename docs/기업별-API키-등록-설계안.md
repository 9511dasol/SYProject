# 기업별 네이버 광고 API 키 등록 — 설계안

> **작성일**: 2026-11-26
> **배경**: 현재 네이버 검색광고 API 키가 서버 환경변수 1벌이라, 모든 기업이 같은 광고 계정(김영, 고객ID 41612)을 바라봅니다. 멀티테넌시(0012~0016)로 데이터는 기업별로 격리됐지만 **외부 계정 연결은 아직 전역**입니다.
> **목표**: 기업 admin이 자기 광고 계정 키를 직접 등록하고, 순위 수집·입찰가·경쟁지표가 그 기업의 키로 동작하게 합니다.

---

## 0. 결론 먼저

**키를 DB에 암호화해 기업별로 저장하고, 기존 코드의 "키 주입 지점"에 그 값을 흘려보냅니다.** 클라이언트(`NaverSearchAdClient`)가 이미 생성자로 키를 받도록 열려 있어, 서비스 로직은 거의 손대지 않습니다.

| 구분 | 지금 | 바뀐 뒤 |
|---|---|---|
| 키 보관 | 서버 `.env` 1벌 (VM `app.env` 수동 복사) | DB `company_credential` 테이블에 **기업별·암호화** 저장 |
| 키 입력 | 개발자가 서버에 SSH 접속 | 기업 admin이 **관리자 화면에서 입력** |
| 수집 대상 | 전역 1개 계정 | 키를 등록한 **모든 기업을 순회** |
| 키 없는 기업 | 전역 키로 남의 계정 데이터를 봄 (격리 위반) | 수집 비활성 + "키를 등록하세요" 안내 |

마지막 줄이 이 작업의 진짜 이유입니다. 지금은 **B기업이 가입하면 김영 광고 계정의 순위를 보게 됩니다.**

## 1. 데이터 모델

### 1-1. 새 테이블 `company_credential`

기업당 공급자별 1행. 지금은 네이버 검색광고뿐이지만, 나중에 카카오·메타가 붙을 자리를 같은 모양으로 비워 둡니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | int PK | |
| `company_id` | int FK → companies, **NOT NULL** | 테넌트 소속. `ON DELETE CASCADE` |
| `provider` | str(30) | `"naver_searchad"` — 공급자 식별자 |
| `customer_id` | str(50) | 고객 ID. **비밀값이 아니므로 평문** (화면에 그대로 보여줘야 함) |
| `api_key_enc` | Text | 액세스 라이선스 — **암호화 저장** |
| `secret_key_enc` | Text | 비밀키 — **암호화 저장** |
| `is_active` | bool | 일시 중지용. 키를 지우지 않고 수집만 멈춤 |
| `last_verified_at` | datetime? | 마지막으로 연결 확인에 성공한 시각 |
| `last_error_code` | str(30)? | 마지막 검증 실패 원인 (`AUTH_ERROR` 등) |
| `created_at` / `updated_at` | datetime | |
| `updated_by` | int? FK → users | 누가 바꿨는지 (감사 추적) |

**제약**: `UNIQUE (company_id, provider)` — 기업당 공급자 1벌.

**설계 판단**
- `customer_id`를 평문으로 두는 이유: 비밀이 아니고, 화면에서 "어느 계정에 연결됐는지" 확인하려면 복호화 없이 읽혀야 합니다.
- 키를 `companies` 테이블 컬럼이 아니라 별도 테이블로 빼는 이유: 공급자가 늘어날 때 컬럼이 증식하지 않고, 기업 조회 쿼리가 비밀값을 끌고 다니지 않습니다.

### 1-2. 암호화 방식 — Fernet (대칭키)

`cryptography` 48.0.1이 이미 설치돼 있어 의존성 추가가 없습니다.

```python
# 서버 환경변수 1개만 추가
CREDENTIAL_ENCRYPTION_KEY=<Fernet.generate_key() 결과>
```

| 질문 | 답 |
|---|---|
| 왜 해시가 아닌 암호화인가 | API 호출에 **원본 값이 필요**합니다. 비밀번호처럼 "맞는지만 확인"하는 값이 아닙니다. |
| 키가 유출되면? | DB만 유출돼도 복호화 불가(암호화 키는 환경변수). 둘 다 털리면 뚫리므로, **DB 덤프와 서버 환경변수의 보관처를 분리**하는 것이 이 설계의 전제입니다. |
| 암호화 키를 잃어버리면? | 저장된 키를 복호화할 수 없습니다 → 기업이 다시 입력해야 합니다. 운영 시 키를 안전한 곳에 **반드시 별도 백업**. |
| 키 교체(rotation) | 1차 범위 밖. 필요해지면 `key_version` 컬럼을 추가해 다중 키를 지원합니다 — 지금 넣으면 쓰지도 않는 복잡도만 늘어납니다. |

**기동 검증**: 운영(`ENVIRONMENT=production`)에서 `CREDENTIAL_ENCRYPTION_KEY`가 없으면 **기동 실패**시킵니다. `settings.py`가 이미 운영 필수값을 강제하는 패턴(`SECRET_KEY`)이 있어 그대로 따릅니다. 개발 환경에서는 없으면 "자격증명 기능 비활성"으로 조용히 넘어갑니다(기존 기능은 그대로 동작해야 하므로).

## 2. 키가 흘러가는 경로

### 2-1. 핵심 — 주입 지점은 이미 열려 있습니다

```python
# app/services/rank/naver_client.py (현재 코드)
class NaverSearchAdClient:
    def __init__(self, api_key=None, secret_key=None, customer_id=None, ...):
        self._api_key = api_key if api_key is not None else settings.NAVER_SEARCHAD_API_KEY
```

생성자가 이미 키를 받습니다. **바꿀 것은 "누가 그 값을 넣어주느냐" 하나**입니다.

### 2-2. 팩토리 함수 신설

```
app/services/rank/credential_factory.py

  build_naver_client(db, company_id) -> NaverSearchAdClient | None
     1. company_credential 조회 (provider="naver_searchad", is_active=True)
     2. 있으면 → 복호화해서 키를 넣은 클라이언트 반환
     3. 없으면 → None
```

**`None`을 반환하는 것이 핵심 설계입니다.** 전역 환경변수로 **폴백하지 않습니다** — 폴백하면 키를 등록하지 않은 기업이 조용히 김영 계정 데이터를 보게 되고, 이는 0015 마이그레이션이 경계한 "격리 위반이 가장 들키기 어려운 형태로 숨는" 바로 그 상황입니다.

| 호출부 | 변경 |
|---|---|
| `collector.collect_ranks` | `provider` 인자에 기업 키로 만든 provider 주입. 키 없으면 `skipped_reason="API 키 미등록"` |
| `BidEstimateService` / `KeywordInsightService` | 생성자에 client 주입 (이미 지원) |
| `report_section.build_rank_section` | estimator를 기업 키로 생성 |
| 라우터 3곳 | `BidEstimateService()` → `BidEstimateService(client=build_naver_client(db, ctx.company_id))` |

### 2-3. 과도기 — 기존 환경변수 키는 어떻게 되나

김영 계정 키는 **sy 기업(id=1)의 자격증명으로 1회 이관**합니다. 마이그레이션에서 자동 변환하지 않고(환경변수를 마이그레이션이 읽는 건 추적이 어렵습니다), **dev 전용 1회 스크립트**로 옮깁니다:

```
python scripts/import_env_credential.py   # .env의 NAVER_* → sy 기업 자격증명으로 저장
```

이관 후 `settings.NAVER_SEARCHAD_*`는 **제거**합니다. 남겨 두면 폴백 유혹이 생깁니다.

## 3. API 설계

기업 자신의 설정이므로 `/api/company/credentials` 아래 둡니다 (dev 전용 `/api/dev/*`와 구분).

| 메서드 | 경로 | 권한 | 설명 |
|---|---|---|---|
| `GET` | `/api/company/credentials/naver` | admin | 연결 상태 조회 — **키 값은 반환하지 않음** |
| `PUT` | `/api/company/credentials/naver` | admin | 키 등록·교체 |
| `POST` | `/api/company/credentials/naver/verify` | admin | 저장된 키로 실제 연결 테스트 |
| `DELETE` | `/api/company/credentials/naver` | admin | 연결 해제 |

### 3-1. GET 응답 — 비밀값은 절대 돌려주지 않습니다

```json
{
  "connected": true,
  "customer_id": "41612",
  "api_key_masked": "0100000000ee…9500",
  "is_active": true,
  "last_verified_at": "2026-11-26T09:00:00+09:00",
  "last_error_code": null,
  "updated_at": "2026-11-26T08:55:00+09:00"
}
```

- `api_key_masked`: 앞 12자 + `…` + 뒤 4자. **"내가 넣은 그 키가 맞나"를 확인할 수 있을 만큼만** 보여주고 복원은 불가능하게.
- `secret_key`는 마스킹조차 반환하지 않습니다 — 길이 정보도 주지 않습니다.

### 3-2. PUT — 검증 후 저장

```json
{ "customer_id": "41612", "api_key": "...", "secret_key": "..." }
```

1. 형식 검증 (빈 값·공백 제거)
2. **실제 API 호출로 연결 확인** (`GET /ncc/campaigns` 1회) — 틀린 키를 저장해 두고 다음 날 크론에서 실패하는 것보다, 입력 즉시 알려주는 편이 낫습니다
3. 성공하면 암호화 저장 + `last_verified_at` 기록
4. 실패하면 **저장하지 않고** 오류코드별 안내 반환 (`AUTH_ERROR` → "키가 맞는지, 해당 계정에 API 권한이 있는지 확인하세요")
5. 감사 로그 `company.credential.update` 기록 — **키 값은 로그에 절대 남기지 않고** 고객 ID만

### 3-3. 응답에서 비밀값이 새지 않게 하는 구조적 장치

스키마를 두 개로 완전히 분리합니다.

```
CredentialUpsertRequest   # 입력 전용 — api_key, secret_key 포함
CredentialStatusResponse  # 출력 전용 — 평문 키 필드 자체가 존재하지 않음
```

출력 스키마에 비밀 필드가 **없으면** 실수로 넣을 수가 없습니다. 타입 코드젠(FS1)이 이 계약을 프런트까지 전파하므로, 프런트에서도 키를 다룰 방법이 없습니다.

**위치**: 관리자 영역에 `/admin/integrations` 신설 (기업 admin 접근).

```
┌─ 네이버 검색광고 ────────────────── [연결됨] ─┐
│ 고객 ID        41612                          │
│ 액세스 라이선스 0100000000ee…9500              │
│ 마지막 확인    2026-11-26 09:00 · 정상         │
│                                                │
│          [연결 테스트]  [키 변경]  [연결 해제] │
└────────────────────────────────────────────────┘
```

**미연결 상태**
```
┌─ 네이버 검색광고 ─────────────── [미연결] ─┐
│ 키워드 순위 자동 수집을 쓰려면 광고 계정을   │
│ 연결해야 합니다.                             │
│                      [연결하기]              │
└──────────────────────────────────────────────┘
```

### 4-1. 입력 폼에서 지킬 것

| 항목 | 처리 |
|---|---|
| 비밀키 입력칸 | `type="password"` + 자동완성 끄기 |
| 기존 키 수정 | 값을 미리 채우지 않음. **빈칸 = 변경 안 함**, 입력 = 교체 |
| 발급 안내 | "네이버 검색광고 → 도구 → API 관리" 경로를 폼 안에 적어둠 — 어디서 받는지 몰라 막히는 게 가장 흔한 이탈 지점 |
| 저장 중 | 연결 테스트 때문에 수 초 걸림 → 진행 표시 + 모달 잠금 |

### 4-2. 순위 모니터링 화면 연결

현재 "API 키가 설정되지 않았습니다" 안내를, **키 등록 화면으로 가는 버튼**과 함께 보여줍니다. 지금은 사용자가 그 문구를 봐도 할 수 있는 일이 없습니다.

## 5. 크론 — 기업 루프로 전환

지금 일일 수집은 전역 1회 실행이라, 기업이 늘면 동작하지 않습니다.

```python
def _collect_ranks() -> None:
    for company_id in companies_with_active_credential(db):   # 키 등록 기업만
        try:
            collect_ranks(db, company_id=company_id)
            run_rank_alerts(db, company_id)
            db.commit()
        except Exception:
            db.rollback()
            logger.exception("기업 %s 수집 실패 — 다음 기업 계속", company_id)
```

**한 기업의 실패가 다른 기업을 막지 않아야 합니다.** 지금 구조(전역 try)에서는 첫 기업에서 터지면 나머지가 통째로 날아갑니다.

> 알림 수신자(`RANK_ALERT_RECIPIENTS`)도 아직 전역입니다. 기업별 수신자는 **이 작업과 같은 묶음으로 처리**해야 합니다 — 안 그러면 A기업 하락 알림이 B기업 수신자에게 갑니다. 이건 자격증명보다 더 급한 격리 위반입니다.

| 단계 | 내용 | 규모 |
|---|---|---|
| **1** | 모델 + 마이그레이션(0017) + 암호화 유틸 + 단위 테스트 | 0.5일 |

| 키별 세분 권한 | 기업 admin 1종으로 충분. 역할이 늘면 그때 |

## 8. 결정이 필요한 것

진행 전에 확인 부탁드립니다.

1. **sy 기업 키 이관** — 현재 `.env`의 김영 계정 키를 sy(id=1) 기업 자격증명으로 옮기는 게 맞는지. (김영이 sy 소속 고객이라면 맞고, 별도 기업으로 분리할 예정이면 그 기업으로 넣어야 합니다.)
2. **암호화 키 보관처** — `CREDENTIAL_ENCRYPTION_KEY`를 VM `app.env`에 둘지, 별도 보관할지. **이 키를 잃으면 저장된 모든 자격증명이 복구 불가**이므로 백업 위치를 정해야 합니다.
3. **우선순위** — 12/1 제출 전에 넣을지, 제출 후로 미룰지. 제출물 관점에서는 **5단계(기업별 알림 수신자)가 더 급한 격리 위반**이라, 시간이 빠듯하면 그쪽을 먼저 하는 선택지도 있습니다.
