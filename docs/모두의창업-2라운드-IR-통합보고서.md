# 1. 총괄 — 한 문단 요약

**마지막 묶음의 의미**: 11월 22일, 기능이 아니라 **배치**를 고쳤습니다. 액션 제안과 AI 코멘트는 11월 10일에 이미 만들어 놓고도 화면 맨 아래 접힌 자리에 두어, 담당자가 "무엇을 해야 하는지"를 스크롤 끝에서야 만나고 있었습니다. 만든 가치가 전달되지 않던 구간을 닫은 작업입니다.

**IR 핵심 스토리 한 줄**: 경쟁사는 "소재 제작 → 집행 → 성과"로 흐르지만, 저희는 **"실데이터 성과 분석 → 액션 제안 → 소재 제작 → 순위 감시"의 역방향 루프**입니다. 리포트가 "소재를 점검하라"고 말하면 같은 화면에서 바로 소재를 고치고, 고친 소재의 키워드 순위가 떨어지면 아침에 메일로 알려줍니다.

## 3-1. 경쟁 3사와 저희의 위치

국내에서 기능이 겹치는 대표 플레이어는 3곳이며, 각자 한 조각에 특화되어 있습니다. **"분석 → 액션 → 소재 → 감시" 네 조각을 한 제품에 담은 곳은 없습니다.**

| 경쟁사 | 특화 영역 | 과금 구조 | 저희와의 관계 |
|---|---|---|---|
| **이미지팩토리** (엠제이스튜디오) | AI 소재 제작 · 1,400+ 지면 리사이즈 · 다채널 집행 | 포인트 종량제(배너 1장 ≈ $1) + 구독($20~95/월) | 크리에이티브 영역이 겹침 — 단, 성과 "분석"은 집행 후 관리 수준 |

## 3-2. 우위에 있는 부분 (구체적 근거와 함께)

1. **역방향 루프 — 유일한 연결 구조입니다.** 진단(액션 제안)과 처방(소재 편집·배경 시안)이 분리된 경쟁 구도에서, "CTR 하락 → 소재 점검 제안 → 같은 화면에서 소재 수정"이 이어지는 제품은 저희뿐입니다.
2. **엑셀 호환성 — 당일 시작이 가능합니다.** 실무에서 쓰던 엑셀 리포트 양식('전월'·'전년동월' 행)과 지표 정의가 1:1로 일치하므로, API 연동·셋업 없이 쓰던 파일을 올리는 것만으로 과거 35개월치 비교가 즉시 가동됩니다. 실제로 양식이 전혀 다른 대행사 주간 리포트(25MB `.xlsb`)를 업로드 기능으로 적재해 19개월 → 35개월로 늘린 사례가 있습니다(2026-11-24). 대시보드 숫자와 보고서 숫자가 어긋나는 범용 툴의 고질 문제가 없습니다.
3. **원가 구조 — 배경 시안 기준 20배 이상 유리합니다.** 이미지팩토리는 이미지 1장 ≈ $1의 포인트 종량제이지만, 저희는 AI 원가 그대로(1장 ≈ $0.04, 4안 1클릭 ≈ $0.16)입니다. 액션 제안(룰 엔진)·규격 변환(이미지 처리)·순위 적재는 아예 0원이라 "일단 여러 안 뽑아보고, 매일 쓰는" 사용 방식이 성립합니다.
4. **임의 업로드 이미지의 요소 편집 — 경쟁사의 자인된 한계 지점을 타깃했습니다.** 이미지팩토리의 간판 기능인 레이어 편집은 자사 워크스페이스에서 생성한 이미지에서만 완전 동작하고(공식 블로그에서 인정), 임의 업로드 이미지는 사용자가 영역을 직접 칠하는 마스킹으로 후퇴합니다. 저희는 **이미 갖고 있는 소재**에서 AI가 요소 12개를 자동 검출하고 클릭 1번으로 영역을 특정합니다.
5. **결정적 룰 엔진 — 비용 0 · 즉시 · 재현 가능합니다.** 아드리엘의 'AI 인사이트'는 LLM 기반이라 구독·토큰 비용이 들고 결과가 매번 달라질 수 있습니다. 저희 액션 제안은 모든 제안에 근거 수치를 병기(예: "구글 ROAS 83.3% (계정 전체 159.7%)")해 담당자가 타당성을 바로 검증할 수 있습니다.
6. **약관을 지키는 순위 모니터링 — 리포트와 결합됩니다.** 경쟁 솔루션의 "분 단위 실시간 순위"는 검색 결과 화면 직접 수집이라 매체 약관 위반 소지가 있습니다. 저희는 공식 데이터(키워드 보고서 → 추후 공식 API) 기반으로 "매일 아침 순위를 대신 확인하고 이상이 있으면 알려주는" 포지션을 택했고, 이는 리포트 자동화라는 제품 중심과 맞닿아 있습니다.
7. **데이터 소유권 — 성과 데이터가 외부 SaaS에 있지 않습니다.** 자체 구축이라 보안을 직접 통제하고, 되돌리기(undo)·스냅샷 같은 자사 워크플로우 맞춤 보호 장치를 넣을 수 있습니다. 이번 라운드에서 그 자체 구축의 약점이던 안정성을 SaaS 수준으로 끌어올렸습니다.

# 4. 무엇을 했나 — 3단계 타임라인 (6하원칙)

## 4-1. 기능 고도화 — "숫자를 보여주는 도구"에서 "행동을 알려주는 도구"로

**결론: 리포트가 방향(YoY/MoM)과 처방(액션 제안)을 말하고, 그 처방을 실행할 크리에이티브 도구 3종이 같은 제품 안에 생겼습니다.**

## 4-6. 멀티테넌시 전환 (2026-11-25) — "한 회사용 도구"를 "여러 고객사를 받는 서비스"로

### 왜 했나 — 먼저 들어온 도입 문의가 구조의 한계를 드러냈습니다

**계기는 저희 계획이 아니라 외부에서 들어온 요청이었습니다.** 지인에게 제품을 소개하며 **소개 페이지(`/`)를 전달했고, 그 페이지를 확인한 뒤 11-23~24경 Slack DM으로 "자기 기업에서 한번 써보고 싶다"는 문의를 받았습니다.** 별도 데모나 추가 설명 없이 **페이지만 보고** 나온 요청이었습니다 — 순위 모니터링·대시보드·이미지 정제·리포트 발송 4종을 화면 목업과 함께 보여주는 페이지입니다(목업 수치는 전부 예시값이며 '예시 데이터' 배지를 달고 있습니다).

지인이 소속된 곳은 **광고대행사**이고, 본인은 광고 운영 담당 부서가 아니어서 **"계정을 받으면 담당 부서에 전달해 사용해 보게 하겠다"** 는 내용이었습니다. 개인의 호기심이 아니라 **사내 담당 조직으로 전달될 검토 요청**이었다는 점이 중요합니다. 다만 소개 자체는 저희가 먼저 했으므로 **완전한 인바운드(모르는 방문자의 유입)는 아닙니다** — 소개가 선행했고, 그 뒤의 설득은 페이지가 했다는 것이 정확한 사실입니다.

그런데 이 요청을 받아 줄 수단이 제품에 없었습니다. 손님에게 줄 계정을 만들면 그 계정이 **기존 고객사의 실데이터를 그대로 보게 되는** 구조였기 때문입니다. 즉 "한번 써보게 해달라"는 가장 자연스러운 영업 요청 하나를 기술적으로 받을 수 없는 상태였고, **손님용(체험) 계정을 기획하게 된 직접적인 출발점**이 이 DM입니다.

구조적 배경도 같은 곳을 가리키고 있었습니다. 2R 성장전략의 핵심은 대행사 영업망 확대인데, 제품은 전 데이터가 한 덩어리로 공유되는 구조였습니다. 두 번째 고객사가 가입하는 순간 서로의 광고 데이터가 그대로 보이는 상태였고, 권한도 일반/관리자 2단계뿐이라 **플랫폼 운영자(저희)와 고객사 관리자가 구분되지 않았습니다.** 즉 "고객사 간 데이터 격리"라는 B2B 도입의 1번 요구사항이 코드에 아예 없었습니다.

### 체험 계정 — 영업 도구를 제품 안에 넣다

**발급 버튼 한 번에 예비 고객용 샌드박스가 통째로 만들어집니다.** 전용 기업과 로그인 계정, 소액 AI 예산, 그리고 예시 데이터 두 종류가 함께 생성됩니다.

**체험 손님은 빈 화면을 보지 않습니다.** 발급 시점에 최근 2개월치 매체별 일별 실적(네이버·카카오·구글 검색광고)과, 키워드 순위 감시 4건의 14일 이력·알림 기록이 함께 깔립니다.

순위 예시는 **하락·안정·회복·노출 없음 네 가지 상태를 일부러 모두** 담았습니다. 제품의 핵심 가치가 순위 하락 감지이므로, 손님이 첫 화면에서 "이 제품이 무엇을 잡아 주는지"를 바로 보아야 하기 때문입니다.

예시를 만드는 방식에도 두 가지 원칙을 두었습니다. 첫째, **하락 상태를 숫자로 박지 않고 실제 판정 로직으로 역산**했습니다. 숫자를 박아 두면 목표 순위를 조정할 때 화면이 "연속 이탈 4회"와 "2회에 도달하면 알림이 나갑니다"를 나란히 띄워 스스로 모순됩니다. 둘째, 이력의 출처를 **"업로드"로 표시**했습니다. 체험 기업에는 광고 계정이 연결돼 있지 않으므로, "자동 수집"으로 적으면 하지도 않은 일을 했다고 말하게 됩니다.

**AI 토큰 예산은 표시용이 아니라 강제입니다.** 체험 기업에는 월 20만 토큰이 걸리고, **예산을 넘어선 뒤의 호출은 막힙니다**(429). 호출 전에는 쓸 토큰 수를 알 수 없어 선차감이 불가능하므로, 예산선을 넘는 마지막 1건은 완료됩니다 — 초과분이 한 건을 넘지 않는다는 뜻입니다. 체험 계정이 자기 예산을 올릴 수도 없습니다 — 예산 변경은 기업 관리자 권한인데, 체험 기업에는 관리자가 없기 때문입니다.

초기 비밀번호는 발급 화면에서 **한 번만** 표시됩니다. 서버에는 **복호화할 수 없는 해시**만 남으므로, 발급 이후에는 저희도 그 비밀번호를 다시 볼 수 없습니다 — 분실 시 재설정만 가능합니다.

설계의 핵심은 **체험을 특별 권한으로 만들지 않은 것**입니다. 전용 기업을 하나 만들어 주는 방식이라, **데이터 열람에 관해서는** "실데이터는 못 보고 샘플만 조작할 수 있다"가 별도 규칙이 아니라 **격리 구조 자체로 자동 보장**됩니다. 예외 규칙을 권한 로직에 심을수록 구멍이 생기기 때문입니다.

다만 격리로 덮이지 않는 축이 두 개 있었고, 둘 다 아래에 적었습니다 — **외부 광고 계정 연결**과 **메일 발송**입니다. 전자는 "누구 데이터를 보는가"가 아니라 "서버가 누구 계정에 조회를 보내는가"의 문제이고, 후자는 "데이터가 어디로 나가는가"의 문제라 테넌시 격리가 다루는 범위 밖입니다.

만료는 2중으로 처리합니다. 기간이 지나면 **모든 요청에서 즉시 차단**되고, 매일 04시에 도는 정리 작업이 기업 데이터째 삭제합니다.

차단이 로그인에만 걸리지 않는다는 점이 중요합니다. 이미 발급된 토큰으로 들어오는 요청도 **매번 소속 기업의 만료 여부를 확인**하므로, 토큰 유효기간 동안 접근이 열려 있는 구간이 없습니다. 정리 작업이 하루 늦어도 접근은 이미 막혀 있습니다.

### 어떻게 검증했나 — 실제로 띄워서 돌렸습니다

| 검증 | 내용 |
|---|---|
| 격리 자동 테스트 15건 신설 | 두 기업을 심어 두고 "A 계정으로 B 데이터 접근 → 404"를 전 경로에서 고정. 조회·삭제·되돌리기·백그라운드 작업·계정 관리까지 포함하며, 이후 기능을 추가해도 격리가 깨지면 테스트가 막습니다 |
| 운영자 기능 테스트 13건 | 기업 생성, 관리자 중복 발급 거절, 체험 발급 → 만료 차단 → 자동 삭제까지 전 수명주기. "새 테이블을 추가하고 삭제 목록에 빠뜨리면 실패하는" 가드 테스트 포함 |
| 마이그레이션 테스트 10건 | 기존 운영 DB 모습을 재현해 전환 경로를 고정 — 기존 데이터 귀속, 중복 관리자 정리, 두 번 실행해도 안전한지까지 |
| **실기동 검증** | 로컬에 전체 스택을 띄워 API 18개 항목, 브라우저 화면 8개 항목 전부 통과. 운영자 로그인 → 기업 생성 → 관리자 발급 → 체험 발급 → 체험 계정으로 실제 로그인 → 샘플 데이터 확인 → 타 기업 데이터 차단 확인 → 체험 삭제 후 로그인 불가까지 한 바퀴 |

**실기동이 아니었으면 놓쳤을 결함도 잡았습니다.** 체험 계정의 자동 생성 이메일 주소가 내부용 도메인이라, 계정은 만들어지는데 **로그인은 거부되는** 상태였습니다. 단위 테스트는 로그인 단계를 거치지 않아 통과했고, 실제로 로그인해 보니 드러났습니다. 유효 도메인으로 고치고 "자동 생성 계정은 반드시 로그인 가능해야 한다"는 테스트를 추가했습니다.

### 임시방편을 남기지 않았습니다

전환 중에 넣었던 과도기 장치(소속 기업을 비워 두면 자동으로 첫 기업에 넣어 주던 기본값)를 작업 마지막에 제거했습니다. 편의 장치지만 **새로 짠 코드가 소속을 빠뜨려도 조용히 기존 고객사 데이터에 섞여 들어가는** 위험이 있기 때문입니다. 제거하자마자 테스트가 누락 지점들을 잡아냈고, 전부 명시하도록 고쳤습니다. 체험 기간·예산·이메일 도메인·정리 시각도 코드에 박지 않고 설정으로 뺐습니다 — 영업 정책이 바뀔 때 배포 없이 조정하기 위해서입니다.

### 격리에서 빠져 있던 축 — 외부 API 계정 (11-27 보완)

**데이터는 기업별로 갈라놓았지만, 외부 광고 계정 연결은 격리 대상에 들어 있지 않았습니다.** 네이버 검색광고 API 키가 서버 환경변수 1벌이라, 키를 소유하지 않은 기업이 자동 수집·입찰가·경쟁지표를 요청하면 **소유 기업의 광고 계정이 조회되는** 경로가 남아 있었습니다. 위 ③의 "전 경로"는 데이터베이스 접근 경로를 뜻했고, 외부 계정 연결은 그 점검 범위 밖이었습니다.

격리를 다시 훑다 직접 발견해 **소유 기업 외의 외부 호출을 차단**했습니다. 두 가지를 지켰습니다. 키 설정 여부와 소유권 판정을 **분리**한 것 — 섞으면 외부 API와 무관한 업로드 알림까지 키에 묶여 끊기고, 실제로 그렇게 끊어진 것을 테스트가 잡았습니다. 그리고 외부 호출이 없는 **보고서 업로드 경로는 그대로 열어 둔 것** — 안전장치가 기능을 통째로 막아서는 안 되기 때문입니다. 차단 지점마다 테스트를 세워 12건으로 고정했습니다.

기업이 자기 광고 계정을 직접 등록하는 근본 해결(암호화 저장·기업별 자격증명)은 설계를 확정해 다음 과제로 두었습니다. 그때까지는 이 차단이 격리를 담당합니다.

### 체험 계정 약속 전수 점검 (11-27) — 기획서와 코드를 한 줄씩 맞춰 봤습니다

**손님 계정을 실제로 발급하기 전에, 기획서에 적은 제약이 코드에 전부 들어가 있는지 확인했습니다.** 예비 고객에게 넘기는 계정이라 "되는 것"보다 **"안 되게 해둔 것"이 실제로 안 되는지**가 중요했습니다. 세 가지를 점검했습니다.

1. 타 기업의 정보·데이터를 볼 수 없는가
2. 아이디·비밀번호는 발급 시에만, 운영자만 확인할 수 있는가
3. 토큰 사용에 상한이 있는가

**①과 ②는 기획대로 구현돼 있었습니다.** 데이터 접근 기준 기업은 로그인 정보에서만 나오고, 요청에 다른 기업을 가리키는 값을 넣어도 무시됩니다. 비밀번호는 해시만 저장돼 발급 이후 열람이 원리적으로 불가능하며, 전체 API에서 비밀번호를 내보내는 응답은 체험 발급 1곳뿐입니다.

**③에서 결함 2건이 나왔습니다.** 둘 다 "기획서에는 있는데 코드에는 없던" 종류입니다.

| 발견 | 무엇이 잘못돼 있었나 | 어떻게 고쳤나 |
|---|---|---|
| **체험 계정이 외부로 메일을 보낼 수 있었습니다** | 기획서의 "외부로 나가는 기능 차단"이 **작업 단계로 분해되지 않아** 구현에서 누락됐습니다. 수신자를 요청에 임의로 적을 수 있어, 예비 고객에게 넘기는 계정이 발신 도메인을 쓰는 통로가 될 수 있었습니다 | 외부 발송 전용 권한 가드를 신설해 발송 경로 2곳에 적용. **미리보기는 열어 두었습니다** — 외부로 나가지 않으므로, 함께 막으면 "맛보기"라는 체험의 목적이 사라집니다 |
| **AI 업스케일이 예산 검사 단계에서 죽고 있었습니다** | 멀티테넌시 전환 때 예산 검사에 소속 기업을 넘기도록 바뀌었는데 이 호출부 하나가 빠졌습니다. 요청하면 예산 확인 대신 **서버 오류**가 났습니다. 토큰은 쓰이지 않았지만 기능 자체가 동작하지 않는 상태였습니다 | 소속 기업을 넘기도록 수정. 사용량이 올바른 기업에 귀속되는 것까지 함께 고정 |

**왜 테스트가 통과하는 동안 기능이 죽어 있었는가** — 예산 검사는 함수를 직접 부르는 테스트만 있었고, **화면에서 실제로 요청하는 경로를 거치는 테스트가 없었습니다.** 그래서 이번에는 회귀 테스트 8건을 전부 HTTP 요청 경로로 세웠습니다. 그리고 두 수정을 각각 일부러 되돌려 **해당 테스트가 실제로 실패하는 것까지 확인**했습니다 — 통과만 보고 끝내면 테스트가 아무것도 지키지 않을 수 있기 때문입니다.

**점검 중 스스로 잡은 설계 오류도 하나 있었습니다.** 처음 만든 권한 가드를 "체험 계정만 막는" 방식으로 짰는데, 이러면 **나중에 역할이 하나 추가될 때 그 역할이 아무 심사 없이 발송 권한을 얻습니다.** 보안 가드가 기본값으로 열려 있는 셈이라, "허용된 역할만 통과"하는 방식으로 되돌려 역할이 늘어날 때 반드시 결정을 거치게 했습니다.

**토큰 상한의 실제 금액도 환산해 두었습니다.** 체험 예산 20만 토큰은 공급자 정가 기준 **약 800원~4,100원**입니다. 용처에 따라 5배까지 차이가 납니다 — 텍스트 위주면 하단, 이미지 생성 위주면 상단입니다.

그래서 **체험 계정의 비용 위험은 사실상 없다**고 판단했습니다. 체험에서 관리해야 할 위험은 비용이 아니라 **외부 발송 같은 평판 리스크**이며, 위 우선순위를 그 기준으로 정했습니다.

**필드를 새로 추가하는 이유를 명시합니다.** 같은 필드에 다른 의미를 넣으면, 이미 저장된 과거 생성 기록이 **이력 화면에서 "추천 이유"를 "본문 카피"로 표시**하게 됩니다. 과거 기록은 실제로 이유만 들고 있으므로 이는 화면이 거짓을 말하는 상태입니다. 그래서 필드를 분리하고, 이력 화면은 그 문구가 어느 시점 형식인지에 따라 레이블을 나눠 보여줍니다.

**비용 영향**: 본문 카피가 추천 이유(85자)보다 길어지므로 1회 생성의 출력 분량이 늘어납니다. 매체별 규격으로 계산하면 문구 10개 기준 본문 총량이 약 850자에서 **약 1,000자**로 늘어 **대략 1.2배**입니다 — 생성 개수가 4배가 되는 ③과 비교하면 작은 폭입니다. 다만 현재 출력 상한(4,000토큰)에 여유가 있는지는 **구현 시 실제 응답으로 확인한 뒤 올립니다** — 상한에 걸리면 10개를 다 못 받고 잘립니다.

**영향 범위**: 백엔드 응답 스키마·AI 지시문·길이 보정 로직, 프론트 타입 재생성, 문구 카드, 이력 화면의 전체 복사 형식, 관련 자동 테스트 2건.

### ② 이미지 정제 — (A) 프롬프트를 바로 쓰게, (B) 작업물을 남게

제보는 한 문장이지만 **성격이 전혀 다른 두 건**입니다. A는 프론트 화면만의 문제이고, B는 저장 정책의 문제입니다. 나눠서 적습니다.

#### ②-A. 프롬프트 입력 — 상설 입력칸을 되살립니다

**지금 어떻게 되어 있나.** 프롬프트를 쓸 수 있는 입력칸은 **지시 편집 모달 안에만** 있습니다. 이미지를 올리면 "아직 지시가 없어요"라는 안내만 뜨고, `지시 추가`를 눌러 모달을 띄워야 비로소 타이핑할 수 있습니다. 게다가 그 버튼은 고정 영역이 아니라 **스크롤되는 목록 안**에 있어, 지시가 쌓이면 버튼이 화면 밖으로 밀립니다.

**왜 이 요구가 나왔는지.** 11-26 재설계에서 인라인 입력칸을 없앤 데에는 이유가 있었습니다 — 그때는 **써 놓은 지시가 보이지도, 수정·삭제되지도 않는** 상태였습니다. 그래서 입력을 모달로 모으고 지시를 카드 목록으로 드러냈습니다. 문제는 **입력까지 모달로 가져간 것**입니다. 지시가 카드로 보이는 지금은, 인라인 입력을 되살려도 당시 문제가 재발하지 않습니다. **되돌리는 것이 아니라 양쪽의 장점을 합치는 수정입니다.**

**어떻게 고칠 것인가.**

| 구분 | 방향 |
|---|---|
| 상설 입력칸 | 오른쪽 패널 **고정 푸터에 한 줄 입력칸**을 상설로 둡니다. 치고 엔터를 누르면 지시 1건이 바로 목록에 쌓입니다 |
| 모달의 역할 축소 | 모달은 **긴 글을 쓰거나 대상 요소를 지정할 때만** 엽니다 — 기본 동선에서 빠집니다 |
| 버튼 위치 | `지시 추가`를 스크롤 영역에서 **고정 푸터로 승격**해, 지시가 쌓여도 밀리지 않게 합니다 |
| 첨부 직후 | 모달을 자동으로 띄우지 **않습니다** — 캔버스를 덮어 요소 지정 동선을 가로막기 때문입니다. 대신 입력칸에 포커스만 둡니다 |
| 한글 입력 | 엔터로 지시를 추가하므로 **한글 조합 중 엔터**가 지시를 두 번 넣지 않도록 기존 재설계 기획의 IME 안전장치를 그대로 적용합니다 |

**영향 범위**: 프론트 전용(패널·클라이언트 2개 파일). 백엔드·스키마 변경 없음. **3건 중 가장 작고 독립적이라 먼저 처리하기에 적합합니다.**

#### ②-B. 작업물 목록 — 설계 원칙을 바꾸는 결정이 먼저입니다

**지금 어떻게 되어 있나.** 결과 이미지는 **브라우저 메모리에만** 존재합니다. 전용 테이블도, 스토리지 업로드도, 조회 API도, 목록 화면도 없습니다. **새로고침하거나 다른 메뉴로 넘어가면 그 자리에서 사라집니다.** 사용자가 직접 내려받은 것만 남습니다. 서버에 남는 기록은 파일명·프롬프트·토큰뿐이고 이미지 자체는 없습니다.

**이것이 실수가 아니라 의도였다는 점을 분명히 합니다.** 화면에도 "이미지는 서버에 저장되지 않아요"라고 적어 두었습니다. **따라서 이 제보는 기능 누락 신고가 아니라, 설계 원칙을 바꿔 달라는 요구입니다.** 단순 화면 추가로 처리할 수 없고 정책 결정이 선행돼야 합니다.

**선택지 3개와 판단.**

| 안 | 내용 | 평가 |
|---|---|---|
| B1 | 브라우저 자체 저장소에 보관 | 서버 미저장 원칙은 지켜집니다. 다만 **기기·브라우저를 바꾸면 사라지고** 용량 한계가 있어 "계속 볼 수 있다"는 요구를 절반만 충족합니다 |
| **B2 (권장)** | **서버 보관 + 작업물 목록 화면** | 요구를 그대로 충족합니다. **같은 제품의 문구 추천 기능이 이미 이 구조(결과 DB 저장 + 이미지 스토리지 + 이력 조회·이미지 열람·삭제)를 갖고 있어, 설계를 새로 만드는 게 아니라 복제하면 됩니다** |
| B3 | 현상 유지 + 다운로드 안내 강화 | 요구 미충족. 기각합니다 |

**B2를 택할 때 함께 확정해야 하는 것** — 이 중 하나라도 비우면 구현에 착수하지 않습니다.

1. **보관 기간: 14일로 확정했습니다 (2026-11-27)**. 무기한 보관은 선택하지 않았습니다. 기간은 설정값으로 빼서 정책이 바뀔 때 재배포 없이 조정합니다. **지우는 대상이 세 층으로 갈리므로 구분해 확정했습니다.**

   | 층 | 무엇이 들어 있나 | 14일 경과 시 |
   |---|---|---|
   | ① 이미지 파일 | 스토리지의 **결과물 이미지** (업로드 원본은 애초에 올리지 않습니다 — 아래 부속 절에서 확정) | **삭제합니다** — 보관 기간의 실제 대상입니다 |

   | ③ 사용량 로그 | 프롬프트·토큰·파일명 | **유지합니다** — 과금 원장이라 보관 기간과 무관합니다. 지금도 이미지 바이트 없이 텍스트만 남습니다 |

   삭제 작업을 걸 자리는 이미 있습니다 — **체험 계정 정리용 매일 04시 크론**이 돌고 있어 거기에 만료 이미지 정리를 함께 붙입니다. 기간 경과분을 찾아 지우는 리포지토리 패턴(배경 작업·되돌리기 스냅샷 정리)도 그대로 재사용합니다. 즉 **새 스케줄러를 만들 필요가 없습니다.**

5. **용량 추산 (산정 완료)**: ③이 적용되면 1회 전송이 4장이 됩니다. 장당 약 1.5MB × 4장 × 하루 5회 = **일 30MB**이고, 보관 14일이면 **고객사 1곳당 약 420MB**입니다. 현재 스토리지 무료 구간이 1GB이므로 **고객사 2곳까지는 지금 구성으로 버티고, 3곳째부터 유료 구간 전환이 필요합니다.** 보관 기간을 30일로 잡으면 1곳만으로 900MB가 되어 한 곳에서 한계에 닿기 때문에 14일을 택했습니다. **단가 재산정의 입력값이므로 과금 모델 설계에 그대로 넣습니다**

6. **체험 계정은 예외적으로 더 짧습니다**: 체험 기업은 3일 뒤 기업째 삭제되므로 **14일을 기다리지 않고 체험 종료 시점에 작업물도 함께 사라집니다.** 영업 시연으로 생긴 이미지가 스토리지에 쌓이지 않습니다

**영향 범위**: 신규 테이블 1개 + 마이그레이션, 스토리지 업로드 경로, 조회·열람·삭제 엔드포인트 3종, 목록 화면 신설, 약관·화면 문구 수정. **3건 중 가장 큽니다.**

| **처리위탁 (최우선)** | **업로드 이미지가 외부로 전송돼 처리된다는 사실.** 전송 경로상 주체가 **둘**입니다 — **중계 라우터(`monogpt.kr`) → 구글 Gemini.** 두 곳을 모두 기재합니다. 이것은 보관과 무관하게 **지금 이미 일어나는 일이고 어디에도 고지돼 있지 않습니다** — 보관 고지보다 먼저 닫아야 합니다 |

**(3) 이 묶음에서 새로 생긴 미결 2건**

| 항목 | 상태 | 내용 |
|---|---|---|
| **원본 이미지 보관 여부** | **확정 (2026-11-27)** | **보관하지 않습니다. 생성 결과물만 보관합니다.** 아래에 근거와 파급을 정리했습니다 |
| **국외 이전 고지 필요 여부** | **확정 (2026-11-27 · 리전 실측)** | **저장은 국내, AI 처리는 국외입니다. 따라서 고지는 필요하며, 대상은 "보관"이 아니라 "AI 처리"입니다.** 아래에 확인 내용을 정리했습니다 |

**국외 이전 고지가 무엇인지 먼저 적습니다.** 개인정보를 해외 서버로 보내는 경우, 법은 이를 국내 처리위탁과 **별개 항목으로** 보고 처리방침에 ① 이전 항목 ② 이전받는 자 ③ 이전 국가·시기·방법 ④ 이전받는 자의 이용 목적·보유 기간 ⑤ 거부 방법을 적도록 요구합니다. **광고 소재에 사람 얼굴이 들어가면 그 사진 자체가 개인정보**이므로, 고객사가 모델·행사 사진을 올리는 순간 해당됩니다 — "광고 이미지니까 개인정보가 아니다"로 넘길 수 없습니다.

**리전을 실제로 확인한 결과입니다.**

| 경로 | 확인된 위치 | 국외 이전 해당 |
|---|---|---|
| **저장** (작업물 14일 보관) | 저장소 리전이 **AWS 서울**입니다 | **해당 없음** — 국내 저장입니다 |
| **AI 처리** (이미지 생성·요소 분석) | 구글 Gemini — **처리 리전이 한국으로 고정되지 않습니다** | **해당됩니다** |

**결론이 중요합니다. 14일 보관은 국외 이전 문제를 일으키지 않습니다** — 서울 리전이라 국내에 머무릅니다. 국외로 나가는 것은 **AI에 이미지를 보내는 처리**이고, 이것은 **보관 기능과 무관하게 지금 이미 매일 일어나고 있습니다.** 즉 이 고지의 성격은 "새 기능 때문에 생기는 의무"가 아니라 **"이미 발생 중인데 비어 있는 의무"** 입니다.

**확인 과정에서 처리위탁 대상이 하나 더 나왔습니다.** AI 호출이 구글로 직접 가지 않고 **중계 라우터(`monogpt.kr`)를 거쳐** 도달합니다. 따라서 **고객 이미지가 지나가는 외부 주체는 둘**입니다(중계 서비스 → 구글). 고지에 **두 곳을 모두 기재**해야 하고, **중계 서비스가 요청 내용을 보관하는지 여부도 확인 대상**입니다 — 보관한다면 그 사실까지 적어야 합니다.

**중계 라우터와 구글의 공개 정책을 확인했습니다 (2026-11-27).** 공개된 약관·처리방침을 직접 읽고 정리한 내용입니다.

| 확인 대상 | 확인된 내용 | 저희에게 주는 의미 |
|---|---|---|
| **중계 라우터 (`monogpt.kr`)** | 개인정보처리방침이 **「이용자 콘텐츠(프롬프트/대화/업로드 파일 등)」를 수집 항목으로 명시**하고, 보관 기간을 **"서비스 이용 목적 달성 시 또는 회원 탈퇴 시"** 로 적고 있습니다. 클라우드 수탁자는 AWS이며, 국외 이전은 "해당 시 사전 고지" 수준으로만 기재돼 있습니다 | **중계 단계에서 이미지와 프롬프트가 보관될 수 있습니다.** 보관 기간에 사실상 상한이 없고, **API 경유(라우터) 호출에 이 조항이 어떻게 적용되는지는 방침에 별도로 적혀 있지 않습니다** — 직접 문의해 확인해야 합니다. AI 학습 활용 여부도 방침에 언급이 없습니다 |
| **구글 Gemini (최종 처리자)** | 약관이 등급으로 갈립니다. **무료 등급**: "Google uses the content you submit… to provide, improve, and develop Google products and services" 이고 **"human reviewers may read, annotate, and process your API input and output"** 입니다. **유료 등급**: "Google doesn't use your prompts… or responses to improve our products" 이며, 위반 탐지 목적으로만 제한 기간 로깅합니다 | **저희 호출은 유료 등급입니다 (2026-11-27 확인).** 따라서 **고객사가 올린 이미지는 구글의 모델 학습에 쓰이지 않고, 사람이 검토하지도 않습니다.** 보관도 위반 탐지 목적의 제한 기간 로깅뿐입니다 |

**가장 무거운 쟁점은 해소됐습니다.** 등급 확인 전에는 "고객 광고 소재가 AI 학습에 쓰이고 사람이 열람할 수 있다"는 최악의 경우를 배제할 수 없었는데, **유료 등급이므로 그 경우는 해당되지 않습니다.** B2B 실사에서 가장 먼저 받는 질문("우리 데이터가 AI 학습에 쓰입니까?")에 **"쓰이지 않습니다"로 답할 근거가 생겼습니다** — 다만 이 문장을 영업 자료에 쓰려면 아래 남은 항목 하나를 먼저 닫아야 합니다.

**남은 것은 중계 단계 하나입니다.** 최종 처리자(구글)는 깨끗하지만, **중간의 중계 라우터는 자체 방침에서 「이용자 콘텐츠」를 수집 항목으로 명시**하고 있습니다. 그 조항이 API 경유 호출에도 적용되는지가 방침에 없어, **"프롬프트·이미지를 보관하는지"를 중계 서비스에 직접 확인해야 합니다.** 보관한다면 고지에 그 사실을 적어야 하고, 보관하지 않는다면 고지가 한 줄로 끝납니다.

**직접 결제로 전환하면 이 마지막 항목까지 사라집니다.** 각 AI 제공사와 직접 계약하면 ⓐ **중계 주체가 사라져 처리위탁 대상이 둘에서 하나로 줄고**(고지가 단순해지고, 확인할 상대도 없어집니다), ⓑ 유료 등급 조건이 **계약 당사자인 저희 명의로 직접 확보**되며, ⓒ 제공사에 따라 **데이터 미보관(zero data retention) 설정**까지 조직 단위로 걸 수 있습니다(예: Anthropic API는 조직 설정으로 제공). 즉 **직접 결제 전환은 비용 구조 변경이 아니라 고지·보안 조건의 개선**입니다 — 영업 자료에 쓸 수 있는 근거이므로, 전환 시점을 고지 문서 작성 일정과 함께 잡는 것이 유리합니다.

**단서를 달아 둡니다.** 위 내용은 코드·설정과 공개 약관에서 확인한 **사실관계 정리**이고, 동의를 별도로 받아야 하는지 처리방침 공개로 충분한지 같은 **법적 판단은 외부 확인을 받아 확정합니다.** 저희 판단으로 문안을 끝내지 않습니다.

**원본 미보관을 택한 근거.** 보관 대상을 결과물로 좁히면 **고지 범위와 위험이 함께 줄어듭니다.** 고객이 올리는 원본에는 인물 사진·타사 제품 이미지·계약서 캡처 같은 것이 섞여 들어올 수 있고, 그것을 저희가 14일 들고 있으면 초상·저작물 책임이 저희 쪽으로 넘어옵니다. **반면 결과물은 저희 제품이 만들어 낸 산출물이라 성격이 다릅니다.** 저장 용량도 절반이 됩니다(원본까지 보관하면 고객사 1곳당 약 840MB로, 무료 구간 1GB에 한 곳만으로 닿습니다).

**이 결정이 포기하는 것도 명시합니다.** 작업물 목록에서 **전후 비교를 볼 수 없습니다** — 원본이 없으니 "무엇을 어떻게 바꿨는지"는 결과물과 프롬프트 기록으로만 유추합니다. 백로그의 "전후 비교 뷰" 항목은 따라서 **작업 세션 안에서만 성립하는 기능**으로 범위가 고정됩니다. 목록에서까지 전후 비교를 원한다는 요구가 나오면 그때 원본 보관을 다시 논의합니다 — **지금 쓰이지도 않을 원본을 미리 쌓아 두지는 않습니다.**

업로드 원본의 처리 방식은 **지금과 똑같이 유지됩니다** — 메모리에서 처리한 뒤 폐기합니다. 즉 ②-B는 "원본을 저장하기 시작하는 변경"이 아니라 **"결과물만 저장하기 시작하는 변경"** 입니다. 고지 문안도 이 범위로 씁니다.

**(4) 일정상 중요한 점**

**이 묶음은 ②-B 구현보다 먼저 시작해야 합니다.** 테이블과 화면은 하루 작업이지만 **고지 문안 확정은 개발 속도로 끝나는 일이 아닙니다**(법적 성격이 있어 필요하면 외부 확인도 받아야 합니다). 순서는 ⓐ 처리위탁·국외이전 문안 확정 → ⓑ 약관·처리방침 페이지 신설 및 링크 노출 → ⓒ 화면 문구 4곳 정정 → ⓓ 코드 주석 갱신입니다. **ⓐ·ⓑ가 닫히기 전에는 이미지 보관 기능을 운영에 올리지 않습니다.**

### ③ 이미지 생성 다건 출력 — 기본 4장, 개수는 사용자가 정합니다

**지금 어떻게 되어 있나.** 편집 결과는 **1장 고정**입니다. 개수 설정이 입력 폼·서버 스키마 어디에도 없고, 모델이 여러 후보를 돌려주더라도 코드가 첫 번째 하나만 꺼내 씁니다. 응답도 이미지 한 장을 그대로 흘려보내는 형태라 애초에 여러 장을 담을 수 없습니다.

**예외가 하나 있습니다.** 배경 시안 기능은 이미 여러 장을 냅니다 — 다만 그것은 **서로 다른 프롬프트를 여러 번 호출**하는 것이고, 같은 지시로 변형을 여러 개 뽑는 것이 아닙니다. **그래도 "여러 번 병렬 호출해 토큰을 합산 기록하고, 일부 실패해도 성공분을 보여주는" 골격이 이미 있어 그대로 재사용합니다.**

**어떻게 고칠 것인가.**

| 구분 | 방향 | 근거 |
|---|---|---|
| 생성 방식 | 같은 프롬프트로 **N회 병렬 호출** | 이미지 모델의 "후보 여러 개" 옵션에 의존하지 않습니다 — 개수가 보장되지 않아 "4장 설정했는데 2장만 나오는" 상황이 생길 수 있습니다 |
| 기본값·범위 | **기본 4장**, 사용자가 **1~6장** 사이로 조절 | 제보 내용 그대로이고, **상한 6장으로 확정했습니다 (2026-11-27)** |
| 상한 근거 | 6장 | 무제한은 토큰·시간·예산이 한 번에 터지는 경로입니다. 배경 시안의 동시 생성 상한(최대 7장)과 같은 급으로 맞춰 **한 요청이 서버에 주는 부담의 최대치를 제품 전체에서 일정하게** 유지합니다 |
| 응답 형태 | 단일 이미지 전송 → **배경 시안과 같은 다건 응답 형식으로 통일** | 한 장만 보낼 수 있는 현재 형태로는 불가능합니다. 전송량이 늘어나는 단점은 백로그의 "배경 시안 전송 형식 개선"과 **한 묶음으로 함께** 처리합니다 |
| 부분 실패 | 성공한 장수만 보여주고 **실패 개수를 함께 표시** | 배경 시안이 이미 쓰는 방식입니다. 4장 중 1장 실패를 전체 실패로 처리하면 토큰만 버립니다 |
| 결과 선택 | 4장을 **후보 트레이**로 보여주고, 고른 1장만 다음 버전으로 승격 | 4장을 모두 버전 계보에 넣으면 2회만 돌려도 계보가 감당 불가로 불어납니다. **채택하지 않은 장은 ②-B 작업물 목록에 남깁니다 — 그래서 ③과 ②-B를 묶으면 자연스럽게 맞물립니다** |

**비용을 솔직하게 적습니다.** 1회 전송이 모델 호출 4회가 되므로 **토큰 소비가 4배**이고, 사용자가 상한인 6장까지 올리면 **6배**입니다. 요청 횟수 제한에는 걸리지 않지만(요청 1건으로 계산됩니다) **기업별 월 토큰 예산은 그 배수만큼 빠르게 소진됩니다.** 즉 기본값을 4장으로 바꾸는 순간, 지금 설정된 예산은 체감상 1/4로 줄어듭니다. 따라서 ⓐ **개수 설정을 열기 전에 기업별 예산 기본값을 다시 산정**하고, ⓑ **화면에서 개수를 올릴 때 "소비가 n배" 라는 사실을 사용자에게 보여 줘야 합니다** — 모르고 6장으로 올려 둔 채 쓰면 월 중반에 예산이 막혀 "갑자기 안 된다"가 됩니다. 소요 시간은 병렬이라 1장과 비슷하지만, 여러 사용자가 동시에 6장씩 요청하는 경우를 대비해 동시 호출 상한을 함께 둡니다.

**체험 계정은 기본값을 낮춥니다.** 체험 예산이 20만 토큰인데 6장 생성을 몇 번만 돌려도 소진됩니다. **체험 계정은 기본 1~2장으로 시작**하게 해, 예비 고객이 시연 중에 예산 초과 메시지를 보는 상황을 막습니다.

**이어진 요청 ② — 지난 작업을 DM 대화로 열람하고, 그 안에서 바로 이어가기.** 레일에서 작업 하나를 누르면 이제 **대화 스레드**가 열립니다: 그때 보낸 지시들이 시간순 말풍선으로 펼쳐지고, 하단 입력대에 이미지를 올리는 순간 그 지시 전체가 걸린 작업 화면으로 바로 전환됩니다. 함께 들어온 "그때의 결과 **이미지**도 자동으로 불러와 달라"는 요청은 **지금은 불가능하다고 답했습니다** — 이미지는 서버에 보관하지 않기로 한 상태(②-B, 약관 신설 선행)라 서버에 남는 것이 지시 텍스트뿐이기 때문입니다. 스레드 첫 말풍선이 그 사실을 먼저 알리고 "이미지를 올리면 이어진다"로 안내합니다. 열람(스레드)과 이어붙이기(작업 중 클릭 시 지시 추가)를 구분했고, 열림·말풍선 순서·스레드 내 첨부·닫기 시 시드 해제까지 자동 브라우저로 검증했습니다. ②-B(이미지 보관)가 열리면 이 스레드에 결과 이미지 말풍선이 채워지는 구조입니다.

### ②-B 구현 — 결과 이미지 서버 보관 (2026-11-28)

**"불가능하다"고 답한 바로 그 지점을, 사용자가 보류를 해제 지시해 당일 열었습니다.** 원래 이 항목은 "이용약관·개인정보처리방침 신설 전에는 운영에 올리지 않는다"로 묶여 있었는데, 사용자가 **이미지 보관을 진행하라고 결정**했습니다. 기능은 확정 정책(2026-11-27) 그대로 구현했고, **약관·고지 문서 신설은 여전히 백로그에 남아 있습니다** — 아래 "남은 것"에 명시합니다.

**스레드가 완성됐습니다.** 전날 "지시 텍스트만" 보여 주던 대화가 이제 **지시 말풍선 + 그 아래 결과 시안 썸네일**로 채워집니다. 시안을 누르면 **그 이미지를 새 원본으로 이어서 작업**하고 — 이때 지시는 걸지 않습니다. 그 시안에는 이미 적용돼 있기 때문입니다. 입력대에 **새 이미지**를 올리면 반대로 지시 전체가 걸립니다. "같은 결과에서 계속"과 "같은 지시를 다른 이미지에"가 한 화면에서 갈립니다.

**남은 것 — 사용자 결정으로도 사라지지 않는 항목입니다.** ① **이용약관·개인정보처리방침 신설**: 이제 보관이 실제로 시작되므로 기획 당시보다 **더 시급**해졌습니다(보관 기간·삭제 수단·처리위탁 고지가 들어갈 자리). ② **운영 반영 체크**: 마이그레이션 1건(새 테이블)이 배포에 포함돼야 하고, 스토리지 버킷이 살아 있어야 합니다.

**이어진 요청 ① — 지난 작업을 "대화 목록"처럼.** 사이드바를 접으면 빈 왼쪽 자리에 **지난 작업 레일**이 서고(펼치면 첫 화면 가운데 블록으로 돌아갑니다 — 내비게이션과 겹쳐 왼쪽이 두 겹이 되지 않게), 레일에서 작업 하나를 누르면 **그때 보낸 지시 전체가 시간순으로 다시 로드**됩니다. 첨부 전이면 "첨부하면 N건 등록" 대기 목록으로, 작업 중이면 현재 이미지의 지시 목록에 바로 추가되며 실행취소도 됩니다. 레일은 작업 중에도 옆에 남아 과거 작업을 언제든 이어받을 수 있습니다. 펼침/접힘 양쪽 표시, 첨부 전 불러오기 → 시간순 등록, 작업 중 추가·실행취소까지 자동 브라우저로 검증했습니다(프런트만의 변경 — 백엔드는 손대지 않았습니다).

### 배포 안전성 — 버전 어긋남 구간을 막았습니다

**구현 직후 점검에서 배포 사고로 이어질 수 있는 지점을 하나 찾아 고쳤습니다.** 이번 변경으로 이미지 편집 응답이 **단일 바이너리에서 JSON(시안 여러 장)으로** 바뀌는데, 프런트와 백엔드는 따로 배포되고 **이미 열어 둔 탭은 옛 화면 코드를 그대로 쥐고 있습니다.** 그 구간에 새 서버가 JSON을 돌려주면 옛 화면은 그것을 이미지로 믿고 받아 **깨진 결과물을 조용히 만듭니다 — 오류조차 나지 않습니다.**

# 6. 신규 기능 로드맵 — 키워드 순위 모니터링 (M1~M6 전부 완성)

**결론: 2026-11-23 기준 로드맵 여섯 단계를 모두 완료했고, 실제 광고 계정(캠페인 18개·광고그룹 330개)에 연결해 자동 수집→이탈 판정→알림→리포트 결합까지 끝에서 끝으로 검증했습니다.** 설정만 해 두면 매일 순위가 쌓이고, 목표를 벗어나면 메일이 나가며, 그 키워드가 얼마나 치열하고 되돌리는 데 얼마가 드는지까지 한 화면에서 봅니다 — 그리고 그 결과가 매달 나가는 리포트 안으로 흘러듭니다.

| 단계 | 핵심 질문 | 상태 | 검증 |
|---|---|---|---|
| M1 적재·판정 | 순위를 어디에 어떻게 쌓을 것인가 | **완료 (11-18)** | 멱등 적재·연속 이탈 재계산 테스트 고정 |
| M3 알림 | 하락을 어떻게 알릴 것인가 (다이제스트·쿨다운·회복) | **완료 (11-18)** | 로컬 SMTP로 실수신 확인 |
| M4 화면 | 사람이 어떻게 보고 다룰 것인가 (추이 차트·수정 모달·알림 이력) | **완료 (11-18)** | 브라우저 E2E |
| M2 자동 수집 | 데이터를 누가 가져올 것인가 (네이버 검색광고 공식 API) | **완료 (11-22)** | 실계정 수집 — ID 캐시로 57초→0.5초, 오류코드 체계(인증·계정에 없음·한도·장애) |
| M5 예상 입찰가 | 비용까지 함께 볼 것인가 ("N위 유지에 예상 얼마") | **완료 (11-22)** | 실계정 조회 — 1~10위, PC·모바일 분리(1위 1,610 vs 2,430원), 목표 순위 줄 강조 |
| M6 경쟁·리포트 결합 | 경쟁 상황까지 보고, 리포트로 흘려보낼 것인가 | **완료 (11-23)** | 검색량·경쟁정도·평균 노출 광고 수 + 월간 리포트에 "목표를 벗어난 키워드 + 유지 예상 CPC" 구역 |

설계상 특징: 중복 알림을 구조로 차단(행 잠금 + 재알림 간격), 보내지 못했으면 보냈다고 기록하지 않음, 키워드별이 아닌 다이제스트 1통, 보고서 포맷을 가리지 않는 헤더 라벨 탐색, **매체 응답 기반 자동 폴백**(디바이스 분리 허용 창이 바뀌어도 수집이 멈추지 않음).

의도적으로 만들지 않은 것: 시간대별 목표(일 단위 데이터로는 판정 불가 — 동작하지 않을 설정을 화면에 두지 않음), 경쟁사 "누구인지" 식별(검색결과 수집 필요 = 약관 위반 소지 — 공식 키워드 도구의 경쟁 밀도로 대체).

# 7. IR에서 솔직하게 밝힐 전제

과장으로 읽히지 않도록 아래를 함께 말씀드리는 편이 좋습니다.

1. **AI 호출 절감 효과는 사용 패턴에 비례합니다.** 매달 새 데이터가 들어오는 정상 흐름에서는 원래대로 생성됩니다 — 절감은 "같은 달을 몇 번 다시 보느냐"에 달려 있어, 수치 주장 전 운영 로그의 재호출 비율 확인을 권합니다.
2. **동시 처리 수치(2.40→1.21초)는 동시 요청 2건 기준**입니다. 더 큰 부하의 처리량은 별도 측정이 필요합니다.
3. **순위 데이터는 일 단위(전일 확정치)입니다.** "분 단위 실시간"은 약관 위반 소지가 있어 의도적으로 선택하지 않았습니다.
4. **Gemini 이미지 생성은 유료 등급 API 키가 전제**입니다 (무료 등급 허용량 0건).
5. **플랫폼 기반 작업(P0~P3)은 기능 추가가 아니라 기반 정비**입니다 — 사용자 눈에 보이는 변화는 취소 버튼·미리보기·재사용 안내 정도이지만, 동시 사용과 데이터 신뢰성이라는 전제를 만든 작업입니다.
