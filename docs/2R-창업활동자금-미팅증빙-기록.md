# 2R 창업활동자금 — 직무별 미팅 증빙 기록

> **용도**: 창업활동자금 건별 증빙(여비·회의비)의 「고객사/미팅대상 · 출장 목적 · 참석자」 작성 원본 + 활동보고서 문항2(자금 사용 → 아이디어 고도화 기여) 연결 자료.
> **원칙**: 날짜·장소·금액은 반드시 **클린카드 승인 내역과 일치**시킵니다. 피드백 문구는 실제 들은 내용만 적습니다(허위·부풀림 기재 시 자금 환수·참여 제한 리스크 — 안내 책자 명시).
> **개인정보**: 상대방 실명·소속사명은 증빙에 필수가 아니면 쓰지 않습니다(양식의 "평가에 불필요한 개인정보 포함 주의" 지침). 직무·업종 수준으로 표기합니다.

## 2. 「출장 목적」 공통 문안 템플릿

아래 3형 중 미팅 성격에 맞는 것을 고르고, ◆ 부분만 교체합니다.

- **A형 (사용 후기·에러 수집)**: `개발 중인 마케팅 데이터 분석 서비스의 ◆(리포트 대시보드/AI 코멘트/이미지 소재 도구) 기능에 대한 실무자 사용 피드백 및 오류 사례 수집`
- **B형 (고도화 검증)**: `◆월 적용한 ◆(기능명) 개선안이 실무 흐름에 부합하는지 ◆(직무) 관점 검증 및 추가 요구사항 수렴`
- **C형 (영업·수요 검증)**: `서비스 시연 및 도입 의향·적정 과금 수준에 대한 잠재 고객 의견 청취`

## 4. 직무별 피드백 ↔ 고도화 반영 매칭표

통합보고서(docs/모두의창업-2라운드-IR-통합보고서.md)의 역할별 완료 항목 중, **외부 실무자 피드백과 연결 가능한 것만** 추린 후보입니다. 3장 표의 "제품 반영" 칸에는 실제 그 미팅에서 다룬 항목의 번호만 적습니다.

각 항목은 「문제 → 왜 문제인가 → 반영 내용 → 적용 효과」 4단으로 구성했습니다. 활동보고서 문항2에 옮길 때는 이 중 "왜 문제인가"가 **피드백의 의미**, "적용 효과"가 **아이디어 고도화 기여**에 해당합니다. 효과 중 실측치는 `[실측]`, 구조상 효과는 `[구조]`로 구분했습니다 — 실측 표기가 없는 수치를 임의로 만들어 넣지 않습니다.

### 마케터 (M) — 실사용 관점

**M-1. 코멘트·액션 제안의 발견 지연** `(4-4 ①, 11-22)`
- **문제**: AI 코멘트와 액션 제안이 대시보드 맨 아래 접힌 자리에 있어, 담당자가 "무엇을 해야 하는지"를 스크롤 끝에서야 만남.
- **왜 문제인가**: 이 제품의 핵심 가치가 바로 그 해석·처방 문장인데, 가장 안 보이는 자리에 있었음. 기능을 만들어도 사용자가 만나지 못하면 없는 것과 같고, 실무자는 숫자 확인에서 멈춘 채 "다음 행동" 판단을 다시 자기 경험에 의존하게 됨.
- **반영**: 리포트 순서를 「점검 필요 배너 → KPI → 액션 제안·코멘트 → 차트·매체표」로 역전. AI 코멘트 기본 펼침, 상단 배너가 경고 건수를 먼저 띄우고 클릭 시 해당 섹션 이동.
- **효과**: 할 일의 위치가 4번째 → 첫 화면 `[실측: 렌더 순서 검증]`. 리포트를 연 순간 "점검 필요 2건"부터 보이므로, 보고서 확인 → 조치 판단 사이의 탐색 과정이 사라짐 `[구조]`.

**M-2. 전월 비교만으로는 계절성 왜곡** `(4-1 ①, 4-2 YoY, 11-10/17)`
- **문제**: 광고 성과를 전월과만 비교하면 성수기 직후의 자연스러운 하락이 "성과 악화"로 읽힘. 전년 동월을 보려면 달을 오가며 수기 비교해야 했음.
- **왜 문제인가**: 계절성이 강한 광고 데이터에서 잘못된 기준 기간은 잘못된 의사결정(불필요한 소재 교체·예산 삭감)으로 직결됨. 수기 비교는 매달 반복되는 시간 비용이면서 실수 여지도 큼.
- **반영**: KPI 카드 10종에 전월·전년 증감 칩 동시 표기 + 3개 기간 비교 표. AI 코멘트도 당월 vs 전월 vs 전년 동월 3각 비교로 작성하고, "전월·전년 방향이 엇갈리면 계절 요인을 먼저 짚으라"는 해석 지침 내장.
- **효과**: 기간 왜곡에 의한 오판 여지를 화면 설계 단계에서 차단 `[구조]`. 비교 달이 없으면 칩을 숨겨 거짓 증감 표시 자체가 불가능 `[구조]`. 19개월 축적 데이터가 비교 자산으로 즉시 활용됨.

**M-3. "그래서 뭘 해야 하는지"가 담당자 숙련도에 의존** `(4-1 ②, 11-10)`
- **문제**: 같은 리포트를 보고도 숙련자는 조치를 떠올리고 신입은 못 떠올림. 판단 품질이 사람에 따라 갈림.
- **왜 문제인가**: 대행사는 담당자가 여럿이고 이직이 잦음. 판단이 개인 머릿속에만 있으면 담당자 교체 때마다 품질이 리셋되고, 광고주에게 나가는 조언의 수준이 들쭉날쭉해짐.
- **반영**: ROAS<100%→입찰 하향 검토, CTR 하락→소재 점검 등 7종 룰 카드. 모든 제안에 근거 수치 병기(예: "구글 ROAS 83.3% (계정 전체 159.7%)").
- **효과**: 판단의 최저선이 도구로 보장됨 — 누가 봐도 같은 데이터에선 같은 제안 `[구조]`. AI 호출 없는 결정적 룰 엔진이라 토큰 비용 0원·즉시 응답·재현 가능 `[구조]`. 근거 수치가 붙어 있어 담당자가 제안의 타당성을 바로 검증 가능.

**M-4. 검토 안 된 AI 문구가 외부 수신자에게 직행** `(그룹3, 11-22)`
- **문제**: AI가 쓴 코멘트가 사람 검토 없이 광고주 메일로 바로 나갈 수 있는 구조였음.
- **왜 문제인가**: 대행사는 이 리포트를 자기 이름으로 클라이언트에게 보냄. AI의 오독 한 줄이 그대로 대행사의 신뢰 손상이 됨 — 기능 버그가 아니라 브랜드 리스크.
- **반영**: 발송 전 미리보기 모달 — 실제 나갈 메일 HTML을 그대로 확인하고 "이대로 발송"을 눌러야 발송. 미리본 코멘트는 캐시로 재사용해 확인 때문에 AI 비용이 이중으로 들지 않음.
- **효과**: 외부로 나가는 모든 문장이 사람의 확인을 거침 `[구조]`. 미리보기→발송 간 기간 변경 시 다른 기간이 나가던 결함도 함께 차단. 확인 단계 추가에 따른 추가 AI 비용 0원 `[실측: 캐시 재사용분 예산 미차감]`.

**M-5. 매일 아침 키워드 순위 수동 확인** `(4-3, 11-18)`
- **문제**: 주요 키워드의 광고 순위를 매일 아침 사람이 직접 검색해 확인하는 반복 작업.
- **왜 문제인가**: 키워드가 수십~수백 개면 확인 자체가 업무가 되고, 놓친 날 순위 이탈이 발생하면 매출 손실을 뒤늦게 발견함. 경쟁 솔루션의 "분 단위 실시간 순위"는 검색 화면 직접 수집이라 매체 약관 위반 소지가 있어 도입이 꺼려짐.
- **반영**: 감시 키워드 등록 → 보고서 적재(멱등) → 연속 이탈 판정 → 하락·회복 다이제스트 메일 1통 → 추이 차트. 공식 데이터 기반(약관 준수), 행 잠금으로 중복 발송 차단.
- **효과**: 매일 아침 수동 확인이 "메일 1통 확인"으로 대체 `[구조]`. 키워드별 알림이 아닌 다이제스트 1통이라 알림 피로 없음 `[구조]`. 약관 리스크 없이 운영 가능한 유일한 포지션.

**M-6. 소재 부분 수정의 디자이너 왕복** `(4-1 ④⑤, 11-10)`
- **문제**: 배너의 특정 영역(문구·버튼 등)만 고치고 싶을 때 수정 위치를 말로 설명해야 했고, AI 생성 결과가 불안정해 디자이너와의 왕복이 반복됨.
- **왜 문제인가**: 소재 수정 한 건의 리드타임이 왕복 횟수에 비례해 늘어나고, 그 사이 성과 낮은 소재가 계속 집행되며 광고비가 샘. 경쟁사(이미지팩토리)의 레이어 편집도 자사 생성 이미지에서만 완전 동작한다고 자인 — 이미 갖고 있는 소재는 사각지대.
- **반영**: 업로드한 임의 이미지에서 AI가 요소 최대 12개를 좌표와 함께 자동 검출, 클릭 1번으로 영역 지정 → 그 영역만 수정. 스타일 프리셋 4종 배경 시안을 1클릭 그리드로 병렬 생성.
- **효과**: "말로 설명 → 결과 복불복" 왕복이 "클릭 → 해당 영역만 수정"으로 단축 `[구조]`. 시안 비교가 1장씩이 아니라 4안 동시 비교로 가능. 배경 시안 1장 ≈ $0.04로 경쟁사 종량제($1/장) 대비 원가 구조상 20배 이상 유리.

**M-7. 지면별 규격 수동 변환과 찌그러짐** `(4-1 ⑥, 11-10)`
- **문제**: 같은 소재를 지면 수만큼 규격별로 수동 변환해야 했고, 비율이 다르면 이미지가 찌그러짐.
- **왜 문제인가**: 소재 1장을 집행하려면 지면 수만큼의 단순 반복 작업이 필수로 붙음 — 제작보다 변환에 시간이 더 드는 역전이 발생. 찌그러진 소재는 브랜드 품질 문제로 직결.
- **반영**: 국내 핵심 8개 지면 프리셋 일괄 변환 + zip 다운로드. 비율 유지 중앙 크롭으로 찌그러짐 원천 차단. 순수 이미지 처리라 AI 비용 0원.
- **효과**: 지면 수 × 수동 변환 → 1클릭 1회 `[구조]`. 변환 품질(비율)이 사람 숙련도와 무관하게 일정. 반복 작업의 AI 비용 0원이라 사용량 제약 없이 매일 쓰는 패턴이 성립 `[구조]`.

**M-8. 순위 확인의 마지막 수작업(매일 업로드)과 "목표 순위의 근거 부재"** `(M2·M5·M6, 11-22~23)`
- **문제**: 순위 모니터링(M-5)을 만든 뒤에도 데이터는 담당자가 매일 보고서를 내려받아 올려야 쌓였음. 또 목표를 "3위"로 잡아도 그 순위가 실제 얼마짜리인지, 그 키워드가 얼마나 치열한지 알 길이 없어 목표 설정이 감에 의존함.
- **왜 문제인가**: 업로드를 하루 빠뜨리면 그날 하락은 아무도 모름 — 자동화 도구인데 사람이 매일 먹이를 줘야 하는 모순. 근거 없는 목표는 과잉 입찰(비용 낭비) 또는 과소 목표(기회 손실)로 이어짐.
- **반영**: 네이버 검색광고 공식 API 일일 자동 수집(11-22, 실제 광고 계정 검증 — 키워드 ID 캐시로 2회차부터 0.5초). 키워드 상세에 순위별(1~10위) 예상 입찰가를 PC·모바일 분리 표기(실측: 같은 키워드 1위가 PC 1,610원 vs 모바일 2,430원), 경쟁 지표(월간 검색량·경쟁정도·평균 노출 광고 수) 병기. 하락 키워드는 "목표 유지 예상 CPC"와 함께 월간 리포트에 자동 수록(11-23).
- **효과**: 순위 수집의 사람 개입 1회/일 → 0회 `[실측: 실계정 자동 수집 검증]`. 목표 설정이 "감" → "비용·경쟁 밀도 근거" `[구조]`. 순위 현황이 따로 보는 화면이 아니라 매달 받는 리포트의 일부가 됨 `[구조]`.

### PM (P) — 운영·리스크 관점

**P-1. 위험 액션에 확인 단계 부재** `(4-4 ③, 11-22)`
- **문제**: 내부 데이터 삭제에는 키 입력 확인까지 있는데, 정작 외부 메일 발송·권한 변경·계정 비활성화·기능 차단에는 확인이 없었음 — 영향 범위와 보호 수준이 거꾸로.
- **왜 문제인가**: 오클릭 한 번이 "외부 수신자에게 잘못된 메일 발송", "동료 계정 잠금", "전사 기능 차단"이 되는 구조. 되돌릴 수 없거나 외부에 노출되는 실수일수록 비용이 큼.
- **반영**: 공용 확인 모달 1종을 만들어 6개 경로(메일 발송·재발송·권한 변경·계정 비활성화·기능 차단·로그인 이메일 변경)에 일괄 적용. 복구 방향(재활성화·기능 켜기)은 확인 없이 통과시켜 마찰은 늘리지 않음.
- **효과**: 위험 액션 가드 0건 → 6건 `[실측: 경로 수]`. 실수 비용이 "복구 작업"에서 "취소 클릭 1번"으로 축소 `[구조]`. 공용 컴포넌트 1곳이라 이후 새 위험 액션에도 일관 적용 가능.

**P-2. 백그라운드 발송 실패의 늦은 인지** `(4-4 ⑤, 11-22)`
- **문제**: 리포트 메일이 백그라운드로 나가므로, 실패해도 관리자가 로그 페이지를 직접 열지 않으면 모름. 고객에게 리포트가 안 나간 것을 며칠 뒤에 알게 되는 구조.
- **왜 문제인가**: "매월 리포트가 온다"는 서비스의 기본 약속인데, 그 약속이 깨진 것을 서비스 제공자가 가장 늦게 아는 것은 신뢰 상품으로서 치명적. 실패 신호가 하위 페이지에 격리돼 있던 것이 원인.
- **반영**: 헤더 알림 센터(관리자 전용) — 최근 7일 발송 실패·AI 예산 90% 초과를 벨 뱃지로 집계, 클릭 시 해당 페이지로 이동. 7일 제한은 오래된 실패로 뱃지가 영영 꺼지지 않는 노이즈를 막기 위한 설계.
- **효과**: 실패 인지 시점이 "로그 페이지를 우연히 연 날" → "다음 로그인 직후" `[구조]`. 함께 고친 "메일 실패가 '발송됨'으로 기록되던 은폐"와 묶여, 실패가 기록되고·보이고·조치되는 경로가 완성됨.

**P-3. AI 비용 집계와 실소비 불일치** `(그룹1, 11-22)`
- **문제**: 재시도로 버려진 토큰과 백그라운드 발송분이 사용량 로그에서 누락 — 월간 AI 예산이 로그 합계로 차단되는데 기록이 실제보다 적어, 예산 상한을 넘겨 쓸 수 있었음.
- **왜 문제인가**: 과금 기준(사용량)이 부정확하면 ① 원가 계산·가격 결정이 틀어지고 ② 고객별 내역서를 신뢰할 수 없고 ③ 예산 상한이라는 안전장치가 무력화됨. 종량 과금 사업의 원장이 새는 것과 같음.
- **반영**: 실패 경로에도 과금분을 예외에 실어 기록, 백그라운드 발송의 사용량 로그 누락 수정, 코멘트 캐시 재사용분은 예산 미차감, Gemini 예외 전수 로깅. 회귀 테스트 9건.
- **효과**: 예산 집계 = 실소비 일치 `[구조: 회귀 테스트로 고정]`. 같은 질문의 답을 두 번 사지 않아 재발송·재조회 시 AI 호출 4회 → 2회 `[실측]`. AI 비용 리포트를 근거로 가격·상한 의사결정 가능.

**P-4. 하락 키워드가 표 안에 묻힘** `(4-4 ②, 11-22)`
- **문제**: 수백 건을 감시하면 "하락" 상태가 표 안 어딘가에만 떠서 스크롤로 찾아야 했고, 키워드 비교에서는 가장 많이 빠진 키워드가 표 맨 아래로 밀림.
- **왜 문제인가**: 모니터링 도구의 존재 이유는 "이상을 가장 먼저 보여주는 것"인데, 정렬이 등록순이면 이상 탐지 비용이 감시 수에 비례해 커짐 — 많이 쓸수록 나빠지는 역설.
- **반영**: 기본 정렬을 상태순(하락·주의 우선)으로, 상태 요약 바("목표를 벗어난 키워드 3건")와 필터 칩 신설. 키워드 비교는 감소 큰 순 우선. 상태 판정을 단일 함수로 모아 뱃지·요약·필터·정렬이 같은 기준을 공유.
- **효과**: 이상 건이 항상 첫 줄 `[실측: 정렬 검증]`. 감시 수가 늘어도 확인 비용이 일정 `[구조]`. 판정 기준이 한 곳이라 화면 간 숫자 불일치가 구조적으로 불가능 `[구조]`.

### 프론트엔드 개발자 (FE) — 화면 성능·상태 관리 관점

**FE-1. 화면 간 복붙된 로직과 메모리 누수** `(F1·F2, 11-16)`
- **문제**: 이미지 업로드·비율 연동·드래그앤드롭이 화면마다 복사돼 2개 화면이 ~80% 중복, 드래그앤드롭 4곳 복붙. 미리보기 URL 해제가 첫 렌더 값에 묶여 실제로는 아무것도 해제하지 못하는 누수(objectURL)도 있었음. 에러 메시지 추출 8벌, 다운로드 코드 4벌.
- **왜 문제인가**: 같은 로직이 N벌이면 버그 수정도 N번 — 한 곳만 고치면 화면마다 동작이 갈라짐. 에러 추출이 8벌이면 같은 서버 오류가 화면마다 다른 문구로 보여 사용자가 혼란스럽고, 누수는 장시간 사용 시 브라우저 메모리를 잠식함.
- **반영**: 공용 훅 3종(`useImageUpload`·`useAspectRatioInputs`·`useFileDrop`)으로 추출, URL 해제를 훅이 전담. 에러 추출 8벌 → 1벌, 다운로드 4벌 → 1벌로 통합. 11-22에는 확인 모달도 공용 `ConfirmDialog` 1곳으로.
- **효과**: 수정이 한 곳 → 전 화면 일관 반영 `[구조]`. 누수 경로 제거로 장시간 사용 안정성 확보 `[구조]`. 서버가 준 오류 사유가 유실되지 않고 같은 규칙으로 표시됨.

**FE-2. 수천 행 표에서 화면 멈춤** `(F4·그룹4, 11-16/22)`
- **문제**: 키워드 비교 표가 수천 행을 한 번에 렌더해 필터·정렬 시 화면이 멈춤. 행 키가 불안정해 중복 조합에서 행이 화면에서 사라지는 결함도 있었음. 이미지 컴포저는 타이핑 한 글자마다 이미지+박스 N개가 전부 다시 그려짐.
- **왜 문제인가**: 대행사 실무 데이터는 기본이 수천 행 — "실데이터를 올리면 멈추는 도구"는 데모용일 뿐 실무 도입이 불가능. 행이 말없이 사라지는 것은 성능 문제를 넘어 데이터 신뢰 문제.
- **반영**: 300행 청크 렌더 + "더 보기", 행 키를 안정 식별자로 교체. 컴포저는 memo+참조 고정으로 격리해 타이핑 시 재렌더 차단.
- **효과**: 수천 행에서도 즉시 반응 `[실측: 500행 청크 등 화면 단위 검증]`. 사라지던 행 복원 — 보이는 데이터와 실제 데이터의 일치 `[구조]`. 입력 지연 제거로 편집 작업 흐름이 끊기지 않음.

**FE-3. 네트워크 무한 대기와 끊을 수 없는 요청** `(F3·F8, 11-16)`
- **문제**: 서버가 무응답이면 화면이 무한 스피너로 멈추고, 진행 중인 AI 작업을 끊을 방법이 없었음. 타임아웃 구현이 최신 브라우저 API(`AbortSignal.any`)에 의존해 구형 브라우저에선 상한이 아예 없었음.
- **왜 문제인가**: 프론트가 서버 상태를 통제할 수 없는 이상, 사용자를 보호하는 마지막 선은 클라이언트의 시간 상한과 취소 수단. 그게 없으면 서버 장애가 곧 "브라우저 강제 새로고침"이 되고, 작성 중이던 컨텍스트를 다 잃음.
- **반영**: 조회 30초 상한 + AbortController, AI 작업 4종(이미지 편집·요소 분석·배경 시안·헤딩) 취소 버튼, 타임아웃 합성을 직접 구현해 브라우저 의존 제거. 사용자가 직접 취소한 것은 오류로 표시하지 않음.
- **효과**: 서버가 멈춰도 화면은 30초 안에 복귀 `[구조]`. 수십 초짜리 AI 작업을 새로고침 없이 중단 가능 — 잘못 누른 생성의 시간·비용 낭비 차단. 브라우저에 따라 보호가 있다가 없다가 하던 구멍 폐쇄 `[구조]`.

**FE-4. 비동기 경합 — 늦게 도착한 응답이 새 상태를 덮어씀** `(F5·F6, 11-16)`
- **문제**: 큰 이미지 → 작은 이미지로 빠르게 바꾸면 먼저 보낸 요청의 응답이 늦게 도착해 새 파일의 값을 덮어씀. 같은 파일을 재선택하면 이전 시안이 화면에 남아 있었음.
- **왜 문제인가**: 경합 버그는 재현이 간헐적이라 사용자는 "가끔 이상하다"고만 느끼고 원인을 설명할 수 없음 — 신뢰를 가장 조용히 깎는 종류의 결함. AI 생성 결과물이 섞이면 잘못된 소재가 그대로 집행될 수도 있음.
- **반영**: 선택 세대(generation) 가드 — 늦게 도착한 구세대 응답은 폐기. prop 리셋을 key/렌더 중 파생으로 바꿔 재선택 잔존 해결.
- **효과**: 어떤 클릭 순서·속도에서도 화면이 항상 마지막 선택을 반영 `[구조]`. "가끔 이상한" 간헐 결함군 제거로 반복 문의·불신 요인 소거.

**FE-5. 로그인 진입 직후 클릭이 조용히 먹히지 않던 실버그** `(11-23)`
- **문제**: 로그인 화면의 장식용 곡선 패널이 폼보다 위층에 그려지는데 클릭 통과 처리가 없어, 페이지 진입 직후 ~1.2초(초기 배치+슬라이드 애니메이션)와 패널 경계 좌표에서 입력창·로그인 버튼 클릭이 소리 없이 삼켜짐.
- **왜 문제인가**: 로그인은 모든 사용의 관문 — 첫 화면에서 "클릭했는데 반응이 없는" 경험은 서비스 전체의 첫인상을 깎음. 에러도 없이 무반응이라 사용자는 원인을 알 수 없고, 간헐적이라 제보도 재현도 어려운 종류의 결함.
- **반영**: 장식 요소에 클릭 통과(pointer-events-none) 적용 — 순수 장식이 입력을 가로채지 않도록 근본 수정. 이전에 실패하던 데스크톱 화면 폭·같은 좌표에서 로그인되는 것을 재검증.
- **효과**: 진입 직후·애니메이션 중에도 클릭이 항상 폼에 닿음 `[실측: 이전 실패 좌표에서 로그인 재검증]`. "가끔 안 눌리는" 간헐 결함 제거로 첫 화면 신뢰 확보 `[구조]`.

### 백엔드 개발자 (BE) — 동시성·데이터·비용 관점

**BE-1. 동시 접속 2명이 서로를 막는 구조** `(B1·B9, 11-16)`
- **문제**: async 경로 19개 지점의 블로킹으로 동시 요청 2건이 직렬 처리 — AI 작업 1건이 서버 전체를 멈춤. 워커 스레드 수와 DB 커넥션 풀이 어긋나 스레드는 남는데 커넥션이 없어 대기하다 실패하는 조합도 있었음.
- **왜 문제인가**: "여러 명이 쓰는 서비스"의 전제 자체가 성립하지 않음. 심사·데모 중 두 명만 접속해도 체감 멈춤이 발생할 수 있었고, 유료 전환 시 첫 번째로 터질 결함.
- **반영**: 가짜 async를 동기+스레드풀 패턴으로 통일(코드베이스의 올바른 선례 따름), 유지가 필요한 곳은 블로킹 구간만 분리. 워커 스레드를 DB 커넥션 풀 크기에 기동 시 자동 정렬.
- **효과**: 동시 요청 2건 처리 2.40초 → 1.21초 `[실측: 대조군 비교]` — 직렬이 병렬로 바뀌었다는 구조 증명. 사용자 수 증가가 곧바로 상호 대기로 이어지던 경로 제거 `[구조]`.

**BE-2. 업로드 실패 1번에 한 달치 데이터 유실 가능** `(B2, 11-16)`
- **문제**: 저장 경로가 "기존 데이터 삭제 → 새 데이터 저장" 순서라, 저장 단계에서 실패하면 기존 달 데이터가 복구 불가로 소실. 엑셀 교체 경로도 동일.
- **왜 문제인가**: 이 제품의 핵심 자산이 "쌓인 기간 데이터"임 — 19개월치 축적이 세일즈 포인트인데, 업로드 실패 한 번이 그 자산을 지울 수 있다면 제품의 약속과 모순. 데이터 신뢰가 무너지면 리포트 신뢰도 같이 무너짐.
- **반영**: 쓰기 순서를 「복구 지점 확보 → 삭제 → 저장」으로 역전, 실패 시 자동 복구. 엑셀 교체 경로에도 동일 적용.
- **효과**: 업로드 실패 시 데이터 유실 경로 자체가 제거 `[구조]`. "쌓일수록 가치가 오른다"는 제품 명제의 기술적 전제가 완성됨.

**BE-3. 데이터 증가에 비례해 느려지는 쿼리** `(B4·그룹4, 11-16/22)`
- **문제**: 월별 조회가 `extract()` 함수 조건이라 인덱스를 못 타고, AI 예산 집계는 전체 로드 후 합산, 순위 적재는 감시 키워드 수 N에 비례한 1+2N 쿼리.
- **왜 문제인가**: "쌓일수록 가치가 오르는" 제품이 "쌓일수록 느려지는" 구현이면 성장이 곧 성능 저하가 됨. 지금 빠른 것은 데이터가 적어서일 뿐, 고객 10곳 시점에 반드시 터질 부채.
- **반영**: `created_at` 인덱스 2종(마이그레이션), `extract()` → 날짜 범위 조건 6곳(인덱스 활용 형태), 예산 조회를 SQL 1행 집계로, 순위 적재를 IN+윈도 함수 벌크 조회로 배치화.
- **효과**: 순위 적재 쿼리 수 1+2N → 4로 고정 — 감시 수와 무관 `[실측: 쿼리 수]`. 조회 성능이 데이터 축적량과 분리돼 "19개월 → 수년치"로 쌓여도 구조 유지 `[구조]`.

**BE-4. 외부 LLM 무응답 시 무한 대기** `(B3, 11-16)`
- **문제**: LLM 3사 클라이언트에 타임아웃·재시도 정책이 없거나 공급자마다 달라, 공급자 무응답이 곧 서비스 무한 대기가 됨. Gemini 생성 지점이 4곳에 흩어져 정책을 한 번에 바꿀 수도 없었음.
- **왜 문제인가**: 외부 의존성의 장애는 통제 불가 — 통제 가능한 것은 "얼마나 기다리고 몇 번 다시 시도할지"뿐. 이 한도가 없으면 외부 장애가 그대로 자사 장애가 되고, 공급자별 정책 불일치는 장애 양상을 예측 불가능하게 만듦.
- **반영**: 3사 공통 타임아웃(텍스트 60초/이미지 180초)·재시도 정책, Gemini 생성 지점 4곳 → 1곳 통합, `attempts` 의미 차이 보정.
- **효과**: 외부 장애 시에도 응답 시간의 상한이 보장됨 `[구조]`. AI 제공자를 Claude·Gemini·OpenAI 중에서 교체 가능한 멀티 프로바이더 구조와 결합해, 특정사 종속·장애 리스크를 이중으로 방어.

**BE-5. 인증·오류 정책이 경로마다 제각각** `(B5·B6·B8, 11-16)`
- **문제**: 비밀번호 검증이 경로마다 달라 1자리 비밀번호로 가입 가능한 구멍이 있었고, 내부 예외 메시지가 사용자 화면에 노출되던 지점이 14곳. 메일 발송이 GET 요청이라 브라우저 프리페치만으로 메일이 나갈 수 있는 경로도 있었음.
- **왜 문제인가**: 보안 정책은 가장 약한 경로가 전체 수준을 결정함 — 가입 경로 하나가 뚫려 있으면 나머지 경로의 강도는 무의미. 내부 예외 노출은 공격자에게 구조 힌트를 주고, 사용자에겐 이해 불가한 문구를 보여줌. B2B 심사·실사에서 바로 지적되는 항목들.
- **반영**: 검증 함수 1개를 4경로(가입·관리자 생성·변경·재설정)에 적용, 전역 예외 핸들러(5xx 사유는 로그에만·4xx는 그대로), 발송을 POST+관리자 권한+예산 게이트로 전환.
- **효과**: 정책 수정이 한 곳 → 전 경로 동시 적용 `[구조]`. 심사·실사 지적 대상 사전 제거. 프리페치 오발송이라는 "사용자 행동 없이 발생하는 사고" 경로 폐쇄 `[구조]`.

**BE-6. 테스트 공백 구간에서 버그 반복** `(B10, 11-16)`
- **문제**: 버그가 반복되던 이유가 "테스트가 없는 곳이라 통과"였음 — 테스트·타입검사·빌드가 전부 초록인데도 결함이 배포됨.
- **왜 문제인가**: 1인 개발 체제에서 안전망 없는 변경은 회귀를 눈치챌 방법이 없음. 기능이 늘수록 수동 확인 범위는 커지는데 사람은 한 명 — 테스트가 없으면 개발 속도가 역설적으로 느려짐.
- **반영**: 테스트 322 → 631건(+309) — 업로드 입구 48, 작업 상태 저장소 22, 캐시 24, YoY 17 등 핵심 경로 우선. 추가 방식 자체를 검증 — 운영 코드를 일부러 되돌려 테스트가 실제로 실패하는지 확인(장식 테스트 방지). 사후 교차검증 절차로 회귀 2건·신규 기능 결함 13건·실버그 3건을 배포 전 차단.
- **효과**: 배포 전 차단 결함 18건+ `[실측: 교차검증 기록]`. "돌아가는지"가 아니라 "약속이 지켜지는지"가 테스트로 고정돼, 이후 모든 변경의 회귀 위험이 상시 감시됨 `[구조]`.

**BE-7. "일단 되게" 넣은 임시방편의 전수 제거 — 전제가 바뀌어도 틀리지 않게** `(11-23)`
- **문제**: 개발 중 우회로 넣었던 하드코딩이 남아 있었음 — 반복 헤더를 "키워드"라는 금지어로 거르고, 매체의 "7일 이내" 제한을 날짜 계산에 박고, 같은 타입 정의를 4개 파일에 복사하고, 수집 튜너블이 코드에 고정돼 있었음.
- **왜 문제인가**: 임시방편은 넣는 순간엔 무해해 보이지만 전제가 바뀌는 순간 조용히 틀림 — 매체가 정책을 바꾸면 수집이 깨지고, '키워드'라는 브랜드 검색어를 실제로 쓰는 광고주는 영영 막히고, 복사된 정의는 한 곳을 빠뜨리는 순간 환경별로 동작이 갈라짐(실제로 로컬 부팅이 깨진 전례 있음).
- **반영**: 각 임시방편의 원인을 먼저 분석한 뒤 근본 방식으로 교체 — 반복 헤더는 이름이 아니라 구조(순위 칸도 라벨일 때만)로 판별, 디바이스 분리 제한은 매체 거부 응답 기반 자동 폴백으로(날짜 계산은 최적화로 강등), 타입 정의는 공용 1곳으로, 튜너블 4종은 설정(환경변수)으로. 각 수정을 되돌리면 실패하는 회귀 테스트로 고정.
- **효과**: 매체가 분리 허용 창을 바꿔도 수집이 멈추지 않음 `[실측: 거부 응답 폴백 테스트]`. 정책 조정이 코드 배포 없이 가능 `[구조]`. "하드코딩이냐"가 아니라 "전제가 바뀌면 조용히 틀리느냐"를 판단 기준으로 문서화 — 이후 개발의 기준선이 됨.

### 풀스택 개발자 (FS) — 프론트↔백 경계 관점

**FS-1. 계약 없는 수동 동기화 — 서버가 바뀌면 화면이 조용히 빈칸** `(FS1·FS6, 11-16)`
- **문제**: 프론트와 백엔드가 응답 구조를 각자 수동으로 맞추고 있어, 백엔드 파서가 키 하나를 바꾸면 프론트 화면이 오류 없이 빈칸이 됨. 이름만 같고 필드가 다른 스키마 충돌로 타입 자동 생성도 불가능한 상태.
- **왜 문제인가**: "조용한 빈칸"은 가장 악성인 장애 유형 — 에러가 안 나니 모니터링에도 안 잡히고, 사용자가 "숫자가 왜 없지?"라고 물어야 발견됨. 숫자 신뢰가 제품 1번 약속인 서비스에서 치명적.
- **반영**: 엑셀 리포트 응답에 Pydantic 스키마 + `response_model` — 구조가 어긋나면 서버에서 즉시 걸림. 동명 스키마 충돌·미등록 API를 정리해 OpenAPI 기반 타입 코드젠의 장애물 제거.
- **효과**: 구조 드리프트가 "화면의 조용한 빈칸" → "서버의 즉각 오류"로 전환 — 발견 시점이 사용자 신고에서 배포 전으로 당겨짐 `[구조]`. 계약이 OpenAPI에 실려 이후 타입 자동 생성의 기반 확보.

**FS-2. 응답 크기 제한이 만든 우회 경로** `(FS2, 11-16)`
- **문제**: BFF가 파일 바디를 통째로 버퍼링해 큰 엑셀은 응답 크기 제한에 걸림 — "다운로드가 안 되면 메일로 받기"라는 우회 경로가 존재. 압축 응답의 Content-Length 불일치로 파일이 잘릴 수 있는 잠복 버그도 있었음.
- **왜 문제인가**: 우회 경로는 "원래 동작이 안 된다"의 다른 표현 — 신규 사용자는 우회법을 모르므로 그냥 실패를 경험함. 데이터가 쌓여 파일이 커질수록(제품의 성장 방향) 실패 빈도가 늘어나는 역방향 구조.
- **반영**: BFF 파일 패스스루(버퍼링 없이 스트리밍), 압축 응답 Content-Length 버그 동시 차단.
- **효과**: 파일 크기와 무관하게 단일 다운로드 경로로 통일 — 516KB 엑셀 스트리밍 검증 `[실측]`. 데이터 성장이 기능 실패로 이어지던 역방향 구조 해소 `[구조]`.

**FS-3. 같은 오류가 화면마다 다른 문구로 표시** `(FS3, 11-16)`
- **문제**: 백엔드의 오류 응답 형식과 프론트의 오류 추출 규칙이 쌍으로 관리되지 않아, 같은 서버 오류가 화면마다 다른 문구로 보임.
- **왜 문제인가**: 오류 문구가 제각각이면 사용자는 같은 문제를 다른 문제로 인식하고, 문의 대응도 "어느 화면에서 봤느냐"부터 물어야 함. 원인 파악 비용이 화면 수에 비례해 증가.
- **반영**: 백엔드 전역 예외 핸들러와 프론트 공용 오류 추출을 같은 규칙 한 쌍으로 정렬.
- **효과**: 같은 원인 → 같은 문구 — 사용자 혼란과 문의 대응 비용 동시 감소 `[구조]`. 오류 규칙 변경 시 수정 지점이 양끝 각 1곳.

**FS-4. 끊김·상태가 경계를 관통하지 못함** `(FS4·FS5, 11-16/22)`
- **문제**: 브라우저는 요청을 끊었는데 서버는 계속 돌아 중복 실행(메일 재발송 이중 발송 등)이 발생. 서버의 판단(코멘트 재사용 여부, 계정 잠금 사유)이 화면까지 전달되지 않아 UI가 실제 상태를 표현하지 못함.
- **왜 문제인가**: 프론트-백이 각자 옳아도 경계에서 어긋나면 "눌렀는데 두 번 발송", "잠겼는데 비밀번호 틀림으로 표시" 같은, 어느 쪽 코드만 봐서는 원인을 못 찾는 결함이 됨. 1인 개발이라도 경계는 2인분의 규율이 필요한 지점.
- **반영**: 취소 체계 관통(프론트 AbortSignal ↔ 서버 경로 설계 — 조회는 30초 상한, AI는 상한 대신 취소), 상태 플래그 관통(`cached`가 백엔드→BFF→화면까지, 계정 잠금 사유가 FastAPI 429→Auth.js `code`→로그인 화면까지).
- **효과**: 중복 실행 경로(이중 발송 등) 제거 `[구조]`. UI가 서버의 실제 판단을 그대로 표현 — "N분 후 재시도" 같은 행동 가능한 안내가 끝까지 전달됨 `[구조]`.

**FS-5. 타입 코드젠 — "서버가 바뀌면 빌드가 막게"** `(FS1 완결, 11-23)`
- **문제**: FS-1에서 계약(Pydantic)을 세웠지만, 프론트 타입 12종은 여전히 손으로 백엔드와 맞추고 있었음 — 백엔드가 필드를 바꿔도 프론트는 모른 채 지나감.
- **왜 문제인가**: 수동 동기화는 "잊는 순간"이 곧 결함 — 그리고 사람은 반드시 잊음. 어긋남이 런타임의 조용한 빈칸으로 드러나는 구조라, 발견 시점이 항상 가장 늦은 곳(사용자 화면)이었음.
- **반영**: 백엔드 OpenAPI에서 프론트 타입을 자동 생성하는 2명령 체계(생성 `types:generate` / 어긋남 검사 `types:check`) 도입, 수동 타입 12종을 생성 타입 별칭으로 전환. 도입 즉시 숨어 있던 계약 결함 7건이 타입 오류로 드러나 전부 백엔드를 정직하게 수정(응답 전용 모델의 잘못된 '선택' 표기, 권한 값이 자유 문자열이던 것, 응답 모양이 계약에 아예 없던 API 2곳, 기능 플래그 키 수동 동기화 등).
- **효과**: 백엔드 변경 시 발견 시점이 "사용자 화면" → "빌드 실패" `[구조]`. 도입 하루에 잠복 결함 7건 선제 제거 `[실측: 타입 오류 목록]`. 기능 플래그 오타가 영원히 통과하던 조용한 구멍(fail-open)을 테스트로 차단.

### 디자이너 (U) — UX·접근성 관점 *(실제 만난 경우에만 사용)*

**U-1. 긴 AI 작업을 끊을 수 없는 기다림** `(P1, 11-16)`
- **문제**: AI 생성 작업이 시작되면 끝나거나 실패할 때까지 사용자가 할 수 있는 것이 없었음.
- **왜 문제인가**: 잘못 누른 생성, 조건을 바꾸고 싶은 생성을 기다려야만 하는 것은 시간 낭비이자 AI 비용 낭비. "기다리기만 하는 화면"은 도구에 대한 통제감을 깎음.
- **반영**: AI 작업 4종에 취소 버튼(AbortSignal이 서버 경로까지 관통). 사용자가 직접 취소한 것은 오류로 표시하지 않음.
- **효과**: 사용자가 작업을 끊을 수 있는 통제권 확보 `[구조]`. 불필요한 생성의 대기 시간·비용 절감. 취소와 오류를 구분해 "내가 멈춘 것"이 "고장"으로 보이지 않음.

**U-2. 실패가 무한 스피너로 위장** `(그룹2, 11-22)`
- **문제**: 관리자 사용량 패널이 조회 실패 시 무한 스피너로 멈춰 있었고, 메일 발송 실패가 "발송됨"으로 기록되던 경로가 있었음.
- **왜 문제인가**: 실패를 숨기는 UI는 사용자가 잘못된 믿음으로 다음 행동을 하게 만듦 — "보냈다"고 믿고 안 보낸 상태가 최악. 기다림의 끝이 있는지 없는지조차 알 수 없는 스피너는 신뢰를 깎음.
- **반영**: 실패 시 에러 메시지+재시도 버튼으로 전환. 메일 발송은 응답 본문까지 검사해 실패를 실패로 기록(테스트 4건 포함).
- **효과**: 모든 실패가 "보이고, 재시도 가능한" 상태로 전환 `[구조]`. 발송 기록과 실제 발송의 일치 — P-2 알림 센터가 이 위에서 동작함.

**U-3. 숫자 오타가 조용히 0으로 저장** `(4-4 ④, 11-22)`
- **문제**: 숫자 입력칸의 오타가 경고 없이 0으로 저장됨(`Number(v)||0`). 저장 성공 토스트가 있는 화면과 없는 화면이 갈려 있었음.
- **왜 문제인가**: 광고비 한 칸이 조용히 0이 되면 그 달 ROAS·CPC가 전부 틀어짐 — "틀린 숫자가 들어갈 수 없다"는 제품의 1번 약속을 입력 단계에서 위반하는 구멍. 피드백이 들쭉날쭉하면 사용자는 저장 여부를 확신하지 못해 같은 작업을 반복함.
- **반영**: 오타 입력 차단 + 에러를 문제 있는 입력칸 바로 옆에 표시, 성공 토스트 누락 4개 경로 보강, 작업 중 모달 잠금 연결.
- **효과**: 지표 전체를 오염시키던 조용한 0 저장이 원천 차단 `[실측: 음수 입력 차단 검증]`. 저장 피드백이 전 화면 일관 — "됐는지 안 됐는지"를 추측하지 않음 `[구조]`.

**U-4. 색에만 의존한 증감 표시** `(접근성)`
- **문제**: 증감을 색으로만 구분하면 색이 벗겨지는 메일 클라이언트, 색 구별이 어려운 사용자에게 방향 정보가 사라짐.
- **왜 문제인가**: 리포트는 메일로 전달되는 제품이라 수신 환경을 통제할 수 없음 — 색이 빠져도 의미가 남아야 "어디서 열어도 같은 보고서"라는 약속이 지켜짐.
- **반영**: 증감을 색이 아닌 부호로 표시, 순위 추이 차트의 키보드 탐색·스크린리더 낭독, 업로드 영역 Space 키 지원, 관리자 오류 경계.
- **효과**: 수신 환경·사용자 특성과 무관하게 방향 정보 보존 `[구조]`. 접근성 지침 준수가 B2B 납품 문서로서의 품질 요건을 겸함.

## 5. 활동보고서 문항2 연결 문단 구조 (작성 시 재사용)

각 미팅을 한 문단으로 쓸 때 이 순서를 고정합니다:

1. **지출**: ◆월 ◆일 ◆(직무) 미팅 — 회의비/여비 ◆원 (붙임1 순번 ◆)
2. **결과물**: 수집한 피드백 ◆건 (핵심 문구 1개 직접 인용)
3. **기여**: 해당 피드백이 반영된 개선 — 4장 매칭번호의 항목명 + 적용일
4. **변화**: 적용 전/후 한 줄 대비 (예: "코멘트 위치 4번째→첫 화면")
