# 서비스 개선 점검 보고서 — 역할별 관점 정리

> **작성 목적**: 모두의 창업 2차 2라운드 준비를 위한 front/back 전체 코드 점검 결과입니다.
> **작성일**: 2026-11-16
> **점검 범위**: `back/` (FastAPI) 전체, `front/` (Next.js) 전체

---

## 한눈에 보는 결론

**전반적으로 완성도가 높은 코드베이스입니다.** 설정 검증·업로드 방어·레이트리밋(백엔드), 서버 컴포넌트 분리·상태 관리 원칙·API 프록시 추상화(프론트엔드)는 이미 모범적으로 구현되어 있습니다.

다만 **즉시 해결이 필요한 리스크 4건(P0)** 이 확인되었습니다:

| 순위 | 리스크 | 한 줄 요약 |
|---|---|---|
| 1 | 서버 전체 정지 | AI 작업 1건이 실행되는 동안 **다른 모든 사용자의 요청이 멈춥니다** |
| 2 | 데이터 유실 | 성과 데이터 업로드 실패 시 **기존 데이터가 복구 불가능하게 사라질 수 있습니다** |
| 3 | 보안 구멍 | 회원가입 시 **1자리 비밀번호도 통과됩니다** |
| 4 | 무한 대기 | AI 공급자가 응답하지 않으면 **요청이 영원히 매달립니다** |

네 건 모두 변경 범위가 작고 코드베이스 안에 올바른 선례가 이미 있어, **하루 안에 수정 가능한 수준**입니다.

# 1. 역할별 관점 정리

## 👨‍💻 FRONT 개발자 관점

**결론부터 말씀드리면, 프론트는 구조가 좋아서 "중복 제거"와 "대용량 렌더 1곳"만 잡으면 됩니다.**

### 이미 잘 되어 있는 것
- 모든 페이지가 서버 컴포넌트 → 클라이언트 컴포넌트 패턴을 일관되게 유지합니다 (`'use client'` 남용 없음).
- 이미지 미리보기 objectURL 해제가 교체/언마운트 시 모두 처리되어 메모리 누수가 없습니다.
- "파생 상태는 effect가 아닌 렌더 중 계산" 원칙이 주석과 함께 지켜지고 있습니다.
- react-query 키가 `queryKeys.ts`로 중앙화되어 있고, BFF 프록시(`bffProxy.ts`)는 48개 라우트를 깔끔하게 추상화했습니다.
- 차트는 외부 라이브러리 없이 자체 SVG로 구현되어 있고 키보드 접근성까지 갖췄습니다.

### 개선 대상

| # | 항목 | 위치 | 중요도 |
|---|---|---|---|
| F1 | 이미지 리사이즈/필터 클라이언트의 **~80% 중복 로직** → `useImageUpload`, `useAspectRatioDimensions` 훅으로 추출 | `ImageResizeClient.tsx` ↔ `ImageFilterClient.tsx` | 중간 |

## 🔧 BACK 개발자 관점

**결론부터 말씀드리면, 백엔드의 핵심 과제는 단 하나 — "async 엔드포인트 안의 블로킹 호출 제거"입니다.** 이것 하나가 동시성·안정성 문제의 뿌리입니다.

### 이미 잘 되어 있는 것
- 설정 검증(`settings.py`)이 운영 환경 필수값을 강제하고, 개발용 임시 키에 경고를 줍니다.
- 업로드 크기를 헤더+실제 바이트 2중으로 방어합니다.
- 레이트리밋이 서명 검증 후 사용자 키를 쓰는 등 설계가 탄탄합니다.
- DB 커넥션 안정성(pre_ping, recycle, keepalive)이 잘 잡혀 있습니다.
- 작업 상태 저장소(`task_store`)가 이미 인메모리에서 DB 기반으로 이전되어 멀티 인스턴스에 안전합니다.
- 핵심 파싱·계산 로직(키워드 비교, 토큰 집계, 엑셀 리더 등)은 테스트가 탄탄합니다.

## 신규 기능 개발 — 키워드 순위 모니터링 + 하락 알림

**매일 아침 키워드 순위를 수동 확인하던 작업을 자동화하는 기능으로, M1·M3·M4를 완료했습니다.** 감시할 키워드와 목표 순위를 등록해 두면, 순위 이력이 자동 적재되고 목표 이탈이 연속되면 알림 메일이 발송됩니다. 경쟁 솔루션(네이버 검색광고 자동입찰 서비스)의 상태값·오류코드 체계를 벤치마킹하되, 약관 리스크가 있는 실시간 수집 대신 **공식 데이터(키워드 보고서 업로드 → 추후 네이버 검색광고 API)** 기반으로 설계했습니다.

| 단계 | 범위 | 상태 |
|---|---|---|
| M1 | 감시 키워드 등록(대량·행별 결과)·목록·이력 모델 + 보고서 업로드 적재 + 이탈 판정 | **완료** |
| M3 | 하락·회복 알림 다이제스트 메일 + 쿨다운 + 발송 이력 + 일일 스케줄러 | **완료** |
| M4 | 전용 화면 — 순위 추이 그래프·상태 뱃지·상세 모달·알림 이력 | **완료** |
| M2 | 네이버 검색광고 API 연동 자동 수집 | API 라이선스 발급 후 착수 (상세는 4장 로드맵) |

### 설계상 특징

- **중복 알림을 구조로 막습니다.** "이미 알림" 상태와 재알림 간격(기본 24시간)을 함께 두어, 같은 하락으로 메일이 반복되지 않고 목표 복귀 시에만 회복 알림이 한 번 나갑니다.
- **보내지 못했으면 보냈다고 기록하지 않습니다.** 수신자 미설정·메일 설정 누락·발송 실패 상황에서 상태를 바꾸지 않아, 설정을 고치면 그 하락이 그대로 알려집니다.
- **키워드마다 메일을 보내지 않습니다.** 한 번의 평가를 한 통의 다이제스트로 묶습니다 — 알림이 많아지면 사용자는 알림을 꺼버리기 때문입니다.
- **포맷을 가리지 않습니다.** 보고서의 컬럼 위치를 고정하지 않고 헤더 라벨로 찾으며, utf-8·cp949와 보조 컬럼·제목 행을 모두 흡수합니다. 같은 날짜를 다시 올리면 새 행이 아니라 갱신입니다.

### 개발 직후 수행한 다중 관점 코드 리뷰

기능 완성 후 **백엔드·프론트엔드 두 관점에서 독립 리뷰를 수행해, 테스트가 통과하는 상태에서 숨어 있던 결함 13건을 발견·수정**했습니다. 주요 항목은 다음과 같습니다.

| 영역 | 발견된 결함 | 영향 |
|---|---|---|
| 알림 판정 | 기준 미달이지만 **여전히 이탈 중**인 상태를 "목표 복귀"로 오판 | 순위가 나빠지는 중에 "돌아왔습니다" 메일 발송 |
| 설정 반영 | 설정값 하나가 모델에 전달되지 않아 조용히 기본값으로 저장 | 사용자가 지정한 재알림 간격이 무시됨 |
| 설정 반영 | 목표 순위를 수정해도 이탈 상태가 다음 업로드까지 갱신 안 됨 | '하락' 뱃지가 잘못된 채로 눌어붙음 |
| 메일 설정 | 설정 누락 시 업로드마다 30초 SMTP 대기 후 실패, 오류 이력 무한 누적 | 업로드 지연 + 이력 테이블 증가 |
| 동시성 | 업로드 평가와 일일 크론이 겹치면 같은 하락이 두 번 발송 | 행 잠금 후 재판정으로 차단 |
| 파서 | 무한대 값이 처리되지 않은 예외(500)로 누출 | 422 안내 대신 서버 오류 |
| 파서 | 띄어쓰기·대소문자만 다른 키워드가 중복 등록 | 보고서 한 줄이 두 감시에 꽂혀 이력이 갈라짐 |
| 차트 | 노출이 끊기는 키워드의 그래프가 **통째로 백지** | 기록이 있는데 아무것도 안 보임 |
| 화면 | 업로드 실패 후 직전 성공 결과가 그대로 남음 | 실패를 성공으로 오인 |
| 접근성 | 차트 값이 보조기술로 읽히지 않음, 키보드 조작이 첫 항목 건너뜀 | 스크린리더 사용자 접근 불가 |

수정한 항목은 모두 **고치기 전 코드로 되돌려 테스트가 실제로 실패하는 것을 확인**했습니다. 또한 마이그레이션이 모델과 같은 스키마를 만드는지 검증하는 테스트를 추가해, "모델에 컬럼을 추가하고 마이그레이션에는 빠뜨리는" 실수가 배포 전에 드러나도록 했습니다. 테스트는 531건 → **597건**이 되었습니다.

# 4. 전체 로드맵 — 순위 모니터링 기능

**결론부터 말씀드리면, 기능의 뼈대(M1·M3·M4)는 이미 동작하고 있으며, 남은 M2는 "사람이 올리던 데이터를 서버가 직접 받아오는" 단계입니다.** M2가 붙으면 사용자가 아무것도 하지 않아도 매일 순위가 쌓이고 하락이 통보됩니다. M2 이후의 확장은 선택지로 열어 두되, 매체 약관을 넘지 않는 범위로 한정했습니다.

## 한눈에 보는 단계

| 단계 | 핵심 질문 | 범위 | 상태 | 선행 조건 |
|---|---|---|---|---|
| **M1** | 순위를 어디에 어떻게 쌓을 것인가 | 감시 키워드 등록·목록·삭제, 보고서 업로드 적재(멱등), 연속 이탈 판정 | **완료** | 없음 |
| **M3** | 하락을 어떻게 알릴 것인가 | 하락·회복 다이제스트 메일, 재알림 간격, 발송 이력, 일일 스케줄러 | **완료** | 기존 메일 인프라 |
| **M4** | 사람이 어떻게 보고 다룰 것인가 | 순위 추이 그래프, 상태 뱃지, 상세·알림 이력, 대량 등록 | **완료** | 없음 |
| **M2** | 데이터를 누가 가져올 것인가 | 네이버 검색광고 API 자동 수집, 오류코드 체계, 수집 상태 표시 | **대기** | **API 라이선스 발급** |
| **M5** | 비용까지 함께 볼 것인가 | 순위별 예상 입찰가 조회, 리포트에 "목표 순위 유지 예상 비용" 결합 | 후보 | M2 완료 |
| **M6** | 경쟁 상황까지 볼 것인가 | 경쟁사 노출 비교, 시간대별 목표 설정(스케줄) | 후보 | M2 완료 + 데이터 축적 |

## M2 — 네이버 검색광고 API 연동 (다음 단계)

**지금 막혀 있는 것은 코드가 아니라 권한입니다.** 네이버 검색광고 관리시스템에서 발급하는 **API 라이선스(API Key · Secret Key · Customer ID)** 가 있어야 하는데, 발급 주체가 광고주 또는 대행사 계정이라 사내 확인이 선행되어야 합니다. 라이선스를 받으면 코드 작업은 **2~3일 규모**로 예상합니다 — M1에서 데이터 공급자를 추상화해 두었기 때문입니다.

### 무엇이 달라지는가

| 구분 | 현재 (M1·M3·M4) | M2 적용 후 |
|---|---|---|
| 데이터 수집 | 담당자가 보고서를 내려받아 업로드 | **서버가 매일 자동 조회** |
| 사람의 개입 | 매일 업로드 1회 | **없음** (설정만 한 번) |
| 하락 인지 시점 | 업로드한 시점 | 매일 정해진 시각 |
| 빠뜨릴 위험 | 바쁘면 업로드를 건너뛰어 하락을 놓침 | 없음 |

즉 M2는 새 기능이라기보다 **"기능이 사람 손을 떠나는" 단계**입니다. 지금도 제품은 동작하지만, M2가 붙어야 "설정해 두면 알아서 지켜준다"는 약속이 완성됩니다.

### 설계 방향 (이미 준비된 부분)

M1에서 순위 데이터를 가져오는 자리를 **공급자 추상화**로 분리해 두었습니다. 상위 로직(적재·판정·알림)은 데이터가 어디서 왔는지 모르기 때문에, API 공급자를 **끼워 넣기만 하면** 나머지는 그대로 동작합니다. 기존 AI 공급자(Claude·Gemini·OpenAI)와 메일 공급자(Resend·SMTP)를 교체 가능하게 만든 것과 같은 방식입니다.

구체적으로 M2에서 추가할 것은 세 가지입니다.

1. **API 공급자 구현** — HMAC 서명 인증으로 통계 조회, 키워드 다건을 한 번에 묶어 호출량 절약, 일시 오류는 재시도
2. **오류코드 체계** — 경쟁 솔루션을 벤치마킹한 부분입니다. 실패를 "오류"로 뭉뚱그리지 않고 **권한 없음 · 키워드 접근 불가 · 호출 한도 초과 · 매체 응답 없음**으로 나눠, 사용자가 직접 해결할 수 있게 합니다
3. **수집 상태 표시** — 화면에 마지막 수집 시각과 실패 사유를 노출

### 솔직한 한계

**공식 API로 얻는 값은 "전일 확정된 평균 노출 순위"로, 일 단위입니다.** 경쟁 솔루션이 광고하는 "분 단위 실시간 순위"는 검색 결과 화면을 직접 수집해야 가능한데, 이는 매체 약관 위반 소지가 있어 선택하지 않았습니다. 따라서 본 서비스의 포지션은 "실시간 자동입찰"이 아니라 **"매일 아침 순위를 대신 확인하고, 이상이 있으면 알려주는 모니터링"** 입니다. 리포트 자동화라는 본 제품의 중심과도 이 쪽이 맞닿아 있습니다.

## M5 · M6 — 확장 후보

M2 완료 후 데이터가 쌓이면 다음 두 방향으로 넓힐 수 있습니다. 둘 다 **기존 리포트 기능과 결합될 때 가치가 커지는** 항목입니다.

- **M5 · 순위별 예상 입찰가** — 네이버 API의 예상 입찰가 조회를 붙여, 월간 리포트에 "이 키워드를 N위로 유지하려면 예상 얼마"를 함께 제시합니다. 순위 모니터링이 "무슨 일이 있었나"라면, 이쪽은 "그래서 얼마가 드나"에 답합니다.
- **M6 · 경쟁 상황과 시간대 전략** — 같은 키워드에서 경쟁사 노출을 비교하고, 요일·시간대별로 목표 순위를 다르게 두는 설정입니다. 경쟁 솔루션의 드래그 방식 스케줄 UI를 참고하되, 입찰 자동 실행이 아니라 **목표 이탈 감시 기준**으로 번안합니다.

## 로드맵이 보여주는 것

이 기능은 **"광고 데이터를 정리하는 시간을 성과를 올리는 시간으로"** 라는 제품 방향의 연장선입니다. 기존 기능이 *이미 지난 달의 데이터를 정리하는 일*을 없앴다면, 순위 모니터링은 *매일 반복되는 확인 작업*을 없앱니다. M2는 그 마지막 수작업(업로드)마저 제거하는 단계이고, M5·M6은 "확인"에서 "판단 근거 제공"으로 한 걸음 더 나아가는 방향입니다.

## 맺음말

이번 라운드의 개선은 "기능을 늘리는 일"보다 **"있는 기능이 조용히 틀리지 않게 만드는 일"**에 집중했습니다. 테스트가 통과하는데도 숨어 있던 회귀를 적대적 재검증으로 찾아낸 것, 비용 절감 장치(코멘트 캐시)가 실패해도 기능 자체는 동작하도록 설계한 것, 신규 기능을 만든 직후 다시 리뷰해 13건을 걷어낸 것이 그 방향성을 보여줍니다.

신규 기능인 키워드 순위 모니터링은 **제품의 약속을 한 단계 넓혔습니다.** 지금까지가 "지난 달 데이터를 정리하는 시간"을 없앤 것이었다면, 이 기능은 "매일 반복되는 확인"을 없앱니다. 남은 M2(API 자동 수집)는 사내 API 라이선스 확인이 선행 조건이며, 코드 쪽 준비(공급자 추상화)는 이미 끝나 있어 라이선스를 받는 즉시 착수할 수 있습니다. 그 외 과제로는 타입 코드젠 도입(FS1)이 남아 있습니다.
