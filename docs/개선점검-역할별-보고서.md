# 서비스 개선 점검 보고서 — 역할별 관점 정리

> **작성 목적**: 모두의 창업 2차 2라운드 준비를 위한 front/back 전체 코드 점검 결과입니다.
> **작성일**: 2026-11-16
> **점검 범위**: `back/` (FastAPI) 전체, `front/` (Next.js) 전체

---

## 한눈에 보는 결론

**전반적으로 완성도가 높은 코드베이스입니다.** 설정 검증·업로드 방어·레이트리밋(백엔드), 서버 컴포넌트 분리·상태 관리 원칙·API 프록시 추상화(프론트엔드)는 이미 모범적으로 구현되어 있습니다.

다만 **즉시 해결이 필요한 리스크 4건(P0)** 이 확인되었습니다:

| 순위 | 리스크 | 한 줄 요약 |
|---|---|---|
| 1 | 서버 전체 정지 | AI 작업 1건이 실행되는 동안 **다른 모든 사용자의 요청이 멈춥니다** |
| 2 | 데이터 유실 | 성과 데이터 업로드 실패 시 **기존 데이터가 복구 불가능하게 사라질 수 있습니다** |
| 3 | 보안 구멍 | 회원가입 시 **1자리 비밀번호도 통과됩니다** |
| 4 | 무한 대기 | AI 공급자가 응답하지 않으면 **요청이 영원히 매달립니다** |

네 건 모두 변경 범위가 작고 코드베이스 안에 올바른 선례가 이미 있어, **하루 안에 수정 가능한 수준**입니다.

# 1. 역할별 관점 정리

## 👨‍💻 FRONT 개발자 관점

**결론부터 말씀드리면, 프론트는 구조가 좋아서 "중복 제거"와 "대용량 렌더 1곳"만 잡으면 됩니다.**

### 이미 잘 되어 있는 것
- 모든 페이지가 서버 컴포넌트 → 클라이언트 컴포넌트 패턴을 일관되게 유지합니다 (`'use client'` 남용 없음).
- 이미지 미리보기 objectURL 해제가 교체/언마운트 시 모두 처리되어 메모리 누수가 없습니다.
- "파생 상태는 effect가 아닌 렌더 중 계산" 원칙이 주석과 함께 지켜지고 있습니다.
- react-query 키가 `queryKeys.ts`로 중앙화되어 있고, BFF 프록시(`bffProxy.ts`)는 48개 라우트를 깔끔하게 추상화했습니다.
- 차트는 외부 라이브러리 없이 자체 SVG로 구현되어 있고 키보드 접근성까지 갖췄습니다.

### 개선 대상

| # | 항목 | 위치 | 중요도 |
|---|---|---|---|

## 🔧 BACK 개발자 관점

**결론부터 말씀드리면, 백엔드의 핵심 과제는 단 하나 — "async 엔드포인트 안의 블로킹 호출 제거"입니다.** 이것 하나가 동시성·안정성 문제의 뿌리입니다.

### 이미 잘 되어 있는 것
- 설정 검증(`settings.py`)이 운영 환경 필수값을 강제하고, 개발용 임시 키에 경고를 줍니다.
- 업로드 크기를 헤더+실제 바이트 2중으로 방어합니다.
- 레이트리밋이 서명 검증 후 사용자 키를 쓰는 등 설계가 탄탄합니다.
- DB 커넥션 안정성(pre_ping, recycle, keepalive)이 잘 잡혀 있습니다.
- 작업 상태 저장소(`task_store`)가 이미 인메모리에서 DB 기반으로 이전되어 멀티 인스턴스에 안전합니다.
- 핵심 파싱·계산 로직(키워드 비교, 토큰 집계, 엑셀 리더 등)은 테스트가 탄탄합니다.

## 신규 기능 개발 — 키워드 순위 모니터링 + 하락 알림

**매일 아침 키워드 순위를 수동 확인하던 작업을 자동화하는 기능으로, M1·M3·M4를 완료했습니다.** 감시할 키워드와 목표 순위를 등록해 두면, 순위 이력이 자동 적재되고 목표 이탈이 연속되면 알림 메일이 발송됩니다. 경쟁 솔루션(네이버 검색광고 자동입찰 서비스)의 상태값·오류코드 체계를 벤치마킹하되, 약관 리스크가 있는 실시간 수집 대신 **공식 데이터(키워드 보고서 업로드 → 추후 네이버 검색광고 API)** 기반으로 설계했습니다.

| 단계 | 범위 | 상태 |
|---|---|---|
| M1 | 감시 키워드 등록(대량·행별 결과)·목록·이력 모델 + 보고서 업로드 적재 + 이탈 판정 | **완료** |
| M3 | 하락·회복 알림 다이제스트 메일 + 쿨다운 + 발송 이력 + 일일 스케줄러 | **완료** |
| M4 | 전용 화면 — 순위 추이 그래프·상태 뱃지·상세 모달·알림 이력 | **완료** |
| M2 | 네이버 검색광고 API 연동 자동 수집 | **완료** (실계정 검증, 상세는 4장 로드맵) |

### 설계상 특징

- **중복 알림을 구조로 막습니다.** "이미 알림" 상태와 재알림 간격(기본 24시간)을 함께 두어, 같은 하락으로 메일이 반복되지 않고 목표 복귀 시에만 회복 알림이 한 번 나갑니다.
- **보내지 못했으면 보냈다고 기록하지 않습니다.** 수신자 미설정·메일 설정 누락·발송 실패 상황에서 상태를 바꾸지 않아, 설정을 고치면 그 하락이 그대로 알려집니다.
- **키워드마다 메일을 보내지 않습니다.** 한 번의 평가를 한 통의 다이제스트로 묶습니다 — 알림이 많아지면 사용자는 알림을 꺼버리기 때문입니다.
- **포맷을 가리지 않습니다.** 보고서의 컬럼 위치를 고정하지 않고 헤더 라벨로 찾으며, utf-8·cp949와 보조 컬럼·제목 행을 모두 흡수합니다. 같은 날짜를 다시 올리면 새 행이 아니라 갱신입니다.

### 개발 직후 수행한 다중 관점 코드 리뷰

기능 완성 후 **백엔드·프론트엔드 두 관점에서 독립 리뷰를 수행해, 테스트가 통과하는 상태에서 숨어 있던 결함 13건을 발견·수정**했습니다. 주요 항목은 다음과 같습니다.

| 영역 | 발견된 결함 | 영향 |
|---|---|---|
| 알림 판정 | 기준 미달이지만 **여전히 이탈 중**인 상태를 "목표 복귀"로 오판 | 순위가 나빠지는 중에 "돌아왔습니다" 메일 발송 |
| 설정 반영 | 설정값 하나가 모델에 전달되지 않아 조용히 기본값으로 저장 | 사용자가 지정한 재알림 간격이 무시됨 |
| 설정 반영 | 목표 순위를 수정해도 이탈 상태가 다음 업로드까지 갱신 안 됨 | '하락' 뱃지가 잘못된 채로 눌어붙음 |
| 메일 설정 | 설정 누락 시 업로드마다 30초 SMTP 대기 후 실패, 오류 이력 무한 누적 | 업로드 지연 + 이력 테이블 증가 |
| 동시성 | 업로드 평가와 일일 크론이 겹치면 같은 하락이 두 번 발송 | 행 잠금 후 재판정으로 차단 |
| 파서 | 무한대 값이 처리되지 않은 예외(500)로 누출 | 422 안내 대신 서버 오류 |
| 파서 | 띄어쓰기·대소문자만 다른 키워드가 중복 등록 | 보고서 한 줄이 두 감시에 꽂혀 이력이 갈라짐 |
| 차트 | 노출이 끊기는 키워드의 그래프가 **통째로 백지** | 기록이 있는데 아무것도 안 보임 |
| 화면 | 업로드 실패 후 직전 성공 결과가 그대로 남음 | 실패를 성공으로 오인 |
| 접근성 | 차트 값이 보조기술로 읽히지 않음, 키보드 조작이 첫 항목 건너뜀 | 스크린리더 사용자 접근 불가 |

수정한 항목은 모두 **고치기 전 코드로 되돌려 테스트가 실제로 실패하는 것을 확인**했습니다. 또한 마이그레이션이 모델과 같은 스키마를 만드는지 검증하는 테스트를 추가해, "모델에 컬럼을 추가하고 마이그레이션에는 빠뜨리는" 실수가 배포 전에 드러나도록 했습니다. 테스트는 531건 → **597건**이 되었습니다.

# 4. 전체 로드맵 — 순위 모니터링 기능

**결론부터 말씀드리면, 계획한 M1~M6을 모두 완료했습니다.** 설정만 해 두면 매일 자동으로 순위가 쌓이고, 목표를 벗어나면 메일이 나가며, 그 키워드가 얼마나 치열하고 되돌리는 데 얼마가 드는지까지 한 화면에서 봅니다. 그리고 그 결과가 **매달 나가는 리포트 안으로 흘러듭니다.** 전 과정을 매체 약관을 넘지 않는 공식 API만으로 구현했습니다.

## 한눈에 보는 단계

| 단계 | 핵심 질문 | 범위 | 상태 | 선행 조건 |
|---|---|---|---|---|
| **M1** | 순위를 어디에 어떻게 쌓을 것인가 | 감시 키워드 등록·목록·삭제, 보고서 업로드 적재(멱등), 연속 이탈 판정 | **완료** | 없음 |
| **M3** | 하락을 어떻게 알릴 것인가 | 하락·회복 다이제스트 메일, 재알림 간격, 발송 이력, 일일 스케줄러 | **완료** | 기존 메일 인프라 |
| **M4** | 사람이 어떻게 보고 다룰 것인가 | 순위 추이 그래프, 상태 뱃지, 상세·알림 이력, 대량 등록 | **완료** | 없음 |
| **M2** | 데이터를 누가 가져올 것인가 | 네이버 검색광고 API 자동 수집, 키워드 ID 캐시, 오류코드 체계, 수집 상태 표시 | **완료** | API 라이선스(발급 완료) |
| **M5** | 비용까지 함께 볼 것인가 | 순위별 예상 입찰가 조회(PC·모바일 분리), 목표 순위 비용 표시 | **완료** | API 라이선스 |
| **M6** | 경쟁 상황까지 볼 것인가 | 경쟁 지표(검색량·경쟁정도·광고 밀도), 월간 리포트 결합 | **완료** | API 라이선스 |

## M2 — 네이버 검색광고 API 연동 (완료)

**결론부터 말씀드리면, 실제 광고 계정에 연결해 자동 수집이 동작하는 것까지 확인했습니다.** 담당자가 매일 보고서를 내려받아 올리던 과정이 사라졌습니다.

### 무엇이 달라졌는가

| 구분 | M2 이전 | M2 이후 |
|---|---|---|
| 데이터 수집 | 담당자가 보고서를 내려받아 업로드 | **서버가 매일 자동 조회** |
| 사람의 개입 | 매일 업로드 1회 | **없음** (설정만 한 번) |
| 하락 인지 시점 | 업로드한 시점 | 매일 정해진 시각 |
| 빠뜨릴 위험 | 바쁘면 업로드를 건너뛰어 하락을 놓침 | 없음 |

업로드 기능은 없애지 않고 남겨 두었습니다 — 과거 데이터를 채우거나 수동으로 보정할 때 쓰는 보조 경로입니다.

### 구현한 것

M1에서 순위 데이터를 가져오는 자리를 **공급자 추상화**로 분리해 둔 덕분에, 적재·판정·알림 로직은 한 줄도 바꾸지 않았습니다. API로 받아온 값이 업로드와 **같은 모양으로 수렴해 같은 경로로 합류**합니다. 기존 AI 공급자(Claude·Gemini·OpenAI)와 메일 공급자(Resend·SMTP)를 교체 가능하게 만든 것과 같은 방식입니다.

1. **API 공급자** — HMAC 서명 인증, 키워드 다건을 묶어 호출량 절약, 일시 오류(네트워크·5xx·한도)는 짧은 백오프로 재시도하되 권한 오류는 즉시 중단
2. **키워드 ID 캐시** — 이 기능의 성능을 가르는 지점입니다. 광고 키워드 ID는 계정 전체를 훑어야 얻는데(실측 계정은 광고그룹 330개 ≈ **57초**), 한 번 찾은 값을 저장해 재사용하도록 해 **이후 수집은 0.5초**로 끝납니다
3. **오류코드 체계** — 경쟁 솔루션을 벤치마킹한 부분입니다. 실패를 "오류"로 뭉뚱그리지 않고 **인증 실패 · 계정에 없는 키워드 · 호출 한도 초과 · 매체 응답 없음**으로 나눠 화면에 조치 방법과 함께 띄웁니다
4. **수집 상태 표시** — API 연결 여부 안내, 키워드별 수집 오류 뱃지, "지금 수집" 수동 실행

### 실계정 검증 결과

실제 광고 계정(캠페인 18개 · 광고그룹 330개)에 연결해 확인한 내용입니다.

| 확인 항목 | 결과 |
|---|---|
| 인증·조회 | 성공 (읽기 전용 호출만 사용, 광고 설정 변경 없음) |
| 평균 노출 순위 수신 | 성공 — 소수점까지 (예: 3.7위 · 1.76위) |
| PC/모바일 분리 | 성공 — 디바이스별로 나눠 적재 |
| 여러 광고그룹 합산 | 성공 — 노출수 가중 평균 |
| 계정에 없는 키워드 | `계정에 없음`으로 구분 표시 |
| 두 번째 수집 속도 | 57초 → **0.5초** (ID 캐시) |

검증 중 **중요한 결함 하나를 발견해 고쳤습니다.** 계정에 없는 키워드(오타 등)가 "아직 안 찾아봄"으로 잘못 판정돼, 그런 키워드가 하나라도 있으면 **매일 계정 전체를 다시 훑고 있었습니다.** "찾아봤지만 없었다"는 결론과 "아직 안 찾아봤다"를 구분하도록 고쳐 2회차 수집이 36.7초에서 0.5초로 줄었습니다.

또한 API 경로에서는 업로드 경로에 있던 한계 하나를 해소했습니다. 보고서에서는 키워드가 빠졌을 때 "노출이 없었던 것"인지 "보고서 범위 밖"인지 구분할 수 없지만, API는 **콕 집어 물어본 결과**라 응답이 없으면 노출 0이 확정입니다. 그래서 '노출 없음도 이탈로 본다' 설정이 API 경로에서는 정확히 동작합니다.

### 솔직한 한계

**공식 API로 얻는 값은 "전일 확정된 평균 노출 순위"로, 일 단위입니다.** 경쟁 솔루션이 광고하는 "분 단위 실시간 순위"는 검색 결과 화면을 직접 수집해야 가능한데, 이는 매체 약관 위반 소지가 있어 선택하지 않았습니다. 추가로 확인한 제약으로, **PC/모바일 분리 데이터는 최근 7일 이내만 제공**되어 그 이전 기간은 합산값으로 받습니다(코드가 자동으로 전환합니다).

따라서 본 서비스의 포지션은 "실시간 자동입찰"이 아니라 **"매일 아침 순위를 대신 확인하고, 이상이 있으면 알려주는 모니터링"** 입니다. 리포트 자동화라는 본 제품의 중심과도 이 쪽이 맞닿아 있습니다.

## M5 — 순위별 예상 입찰가 (완료)

**순위 모니터링이 "무슨 일이 있었나"에 답한다면, 이 기능은 "그래서 얼마가 드나"에 답합니다.** 목표를 3위로 잡아 둔 키워드가 실제로 얼마짜리인지 모르면 목표를 정할 근거가 없습니다. 키워드 상세 화면에서 1~5위까지의 예상 클릭당 비용을 PC·모바일로 나눠 보여 주고, **현재 목표 순위에 해당하는 줄을 짚어** 줍니다.

실계정 조회 예시(키워드 "수학과편입", 목표 2위):

| 순위 | PC | 모바일 |
|---|---|---|
| 1위 | 1,610원 | 2,430원 |
| **2위 (목표)** | **1,520원** | **2,030원** |
| 3위 | 1,490원 | 1,740원 |
| 5위 | 1,130원 | 980원 |

확인한 사실 두 가지를 설계에 반영했습니다.

- **PC와 모바일 입찰가는 크게 다릅니다** (1위 기준 1,610원 vs 2,430원). 하나로 합쳐 보여 주면 잘못된 판단을 부르므로 끝까지 분리했습니다.
- **조회 가능한 순위는 1~10위**입니다(11위를 섞으면 요청 전체가 거부됩니다). 코드가 상한을 넘겨 보내지 않도록 막아 두었습니다.

한계도 화면에 함께 적었습니다 — 매체가 주는 **추정치**이며 실제 입찰 결과는 품질지수와 경쟁 상황에 따라 달라집니다. 또 검색량이 거의 없는 키워드도 최소 입찰가를 돌려주므로, 값이 나왔다고 해서 수요가 있다는 뜻은 아닙니다.

## M6 — 경쟁 지표와 리포트 결합 (완료)

**이 단계에서 순위 모니터링이 독립된 화면을 벗어나 제품의 본체인 월간 리포트로 합류했습니다.**

### 경쟁 지표 — "왜 그 값이 나오는가"

순위가 "무슨 일이 있었나", 예상 입찰가가 "얼마가 드나"라면, 경쟁 지표는 **"목표 1위가 현실적인 목표인가"** 에 답합니다. 상세 화면에 월간 검색 수, 매체의 경쟁정도 판정, **평균 노출 광고 수**를 띄웁니다. 마지막 항목이 핵심인데, 이 키워드에 평균 몇 개 광고가 함께 붙는지를 뜻해 경쟁 밀도를 그대로 보여 줍니다(실측 예: 7개).

데이터 처리에서 한 가지를 특별히 다뤘습니다. 검색량이 적은 키워드는 매체가 숫자가 아니라 **`"< 10"` 문자열**을 돌려줍니다. 그대로 숫자로 바꾸면 오류가 나므로, "10 미만"으로 구분해 표시하고 합계는 내지 않습니다 — 한쪽을 모르면 합계를 말할 수 없기 때문입니다.

### 리포트 결합 — 순위가 리포트로 흘러든다

월간 리포트 메일에 **키워드 순위 현황** 구역을 더했습니다. 실제 발송 예시입니다.

> **키워드 순위 현황** — 감시 중인 4개 중 **2개**가 목표 순위를 벗어났습니다.
>
> | 키워드 | 현재 | 목표 | 연속 | 목표가 유지 예상 CPC |
> |---|---|---|---|---|
> | 대학편입수학 | 노출 없음 | 2위 | 1회 | PC 2,570원 · 모바일 2,330원 |
> | 수학과편입 | 3.7위 | 2위 | 1회 | PC 1,520원 · 모바일 2,030원 |

설계에서 지킨 원칙이 셋 있습니다.

1. **목표를 벗어난 키워드만 싣습니다.** 잘 되고 있는 것까지 나열하면 정작 손봐야 할 것이 묻힙니다. 대신 전부 정상이면 "모두 목표를 지키고 있습니다"라고 한 줄로 알려, 감시가 돌고 있다는 사실 자체는 전달합니다.
2. **조용히 자르지 않습니다.** 상한(8건)을 넘으면 "외 N개"로 밝힙니다.
3. **순위 때문에 리포트가 멈추지 않습니다.** 외부 API 조회가 실패해도 그 구역만 비거나 빠지고, 리포트 본체(지난달 실적)는 그대로 나갑니다. 입찰가를 못 받은 키워드도 행은 남깁니다.

리포트 본문은 지난달 실적이지만 순위는 '지금' 상태라 섞이면 오해를 부릅니다. 그래서 **"이 메일을 보내는 시점 기준"** 임을 구역 안에 명시했습니다.

### 계획을 바꾼 부분 — 시간대별 목표는 만들지 않았습니다

원래 M6에 넣었던 "시간대별 목표 설정"은 **만들 수 없다고 판단해 제외했습니다.** 우리가 받는 데이터는 전일 확정된 *일 단위* 평균 순위라, 오후 3시의 순위를 알 방법이 없어 시간대별 목표를 판정할 수 없습니다. 경쟁 솔루션이 이 기능을 갖는 것은 몇 분마다 실시간으로 입찰하기 때문이며, 우리와는 데이터의 성격이 다릅니다. 판정할 수 없는 설정을 화면에 두면 사용자는 동작한다고 믿게 되므로, 만들지 않는 편이 정직합니다.

마찬가지로 "경쟁사가 누구인지"도 다루지 않았습니다. 그건 검색결과 화면을 수집해야 알 수 있어 약관 문제가 있습니다. 대신 공식 키워드 도구가 주는 **경쟁 밀도**로 같은 질문에 답했습니다.

## 로드맵이 보여주는 것

이 기능은 **"광고 데이터를 정리하는 시간을 성과를 올리는 시간으로"** 라는 제품 방향의 연장선입니다. 기존 기능이 *이미 지난 달의 데이터를 정리하는 일*을 없앴다면, 순위 모니터링은 *매일 반복되는 확인 작업*을 없앴고, M2가 그 마지막 수작업(업로드)마저 제거했습니다. M5·M6은 거기서 한 걸음 더 나아가 **"확인"에서 "판단 근거 제공"으로** 성격을 넓혔습니다 — 순위가 떨어졌다는 사실과 함께, 그 키워드가 얼마나 치열하고 되돌리려면 얼마가 드는지를 같은 화면에서 봅니다.

그리고 M6의 리포트 결합으로 **한 바퀴가 닫혔습니다.** 매달 나가던 리포트에 순위 현황이 들어가면서, 새 기능이 따로 노는 화면이 아니라 기존 제품의 일부가 되었습니다.

## 맺음말

이번 라운드의 개선은 "기능을 늘리는 일"보다 **"있는 기능이 조용히 틀리지 않게 만드는 일"**에 집중했습니다. 테스트가 통과하는데도 숨어 있던 회귀를 적대적 재검증으로 찾아낸 것, 비용 절감 장치(코멘트 캐시)가 실패해도 기능 자체는 동작하도록 설계한 것, 신규 기능을 만든 직후 다시 리뷰해 13건을 걷어낸 것이 그 방향성을 보여줍니다.

신규 기능인 키워드 순위 모니터링은 **제품의 약속을 한 단계 넓혔습니다.** 지금까지가 "지난 달 데이터를 정리하는 시간"을 없앤 것이었다면, 이 기능은 "매일 반복되는 확인"을 없앴고, 계획한 M1~M6을 모두 완료해 실제 광고 계정에서 자동으로 도는 것까지 확인했습니다. 마지막 단계에서 순위 현황이 월간 리포트로 합류하면서 새 기능이 기존 제품의 일부가 되었습니다.

과정에서 **만들 수 있는 것과 만들어선 안 되는 것을 구분한 것**도 기록해 둘 만합니다. 경쟁사 실시간 순위 수집은 약관 문제로, 시간대별 목표는 일 단위 데이터로 판정할 수 없어 각각 제외하고 공식 API로 답할 수 있는 형태로 번안했습니다.

마지막으로 남아 있던 FS1(타입 코드젠)까지 도입해, **점검에서 제기된 과제를 모두 닫았습니다** — 상세는 아래 5장입니다.

# 5. 타입 코드젠 도입 (FS1 · FS3)

**결론부터 말씀드리면, 프런트가 백엔드 응답 모양을 손으로 적어 두던 구조를 없앴습니다.** 이제 백엔드 스키마가 유일한 출처이고, 프런트 타입은 거기서 생성됩니다. 백엔드를 고쳤는데 화면을 안 고치면 **빌드가 실패**합니다 — 예전처럼 런타임에 빈 값으로 드러나지 않습니다.

## 어떻게 동작하는가

```
FastAPI 스키마 ──▶ OpenAPI ──▶ front/types/api.generated.ts ──▶ 화면 코드
                 (스크립트 한 번)              (타입 별칭)
```

- `npm run types:generate` — 백엔드에서 OpenAPI를 뽑아 타입을 다시 만듭니다(서버를 띄우지 않아도 됩니다).
- `npm run types:check` — 백엔드와 어긋났는지만 확인합니다. 배포 전 검사에 걸어 두면 "백엔드만 고치고 타입을 안 만든" 상태가 통과하지 못합니다.

생성물(`api.generated.ts`, 약 5,200줄)은 저장소에 커밋합니다. 그래야 프런트 빌드가 파이썬 백엔드에 묶이지 않습니다.

기존 타입 파일은 지우지 않고 **생성 타입을 가리키는 별칭**으로 바꿨습니다. 화면 코드는 그대로 `import type { RankWatch } from '@/types/rankMonitor'` 를 쓰면서, 실제 정의는 백엔드를 따라옵니다.

## 전환하며 드러난 계약 결함

코드젠을 붙이자마자 **손으로 적은 타입과 실제 API가 어긋난 지점이 타입 오류로 쏟아졌습니다.** 모두 백엔드 쪽을 정직하게 고쳐 해결했습니다.

| 발견 | 무엇이 문제였나 |
|---|---|
| 응답 전용 모델에 기본값이 붙어 있었음 | 서버는 항상 보내는데 OpenAPI는 "없을 수도 있음"으로 내보내, 화면이 쓰지 않아도 될 방어 코드를 쓰게 됨 (엑셀 리포트·수집 결과·예상 입찰가 등) |
| `role: str` | 실제 값은 `user`/`admin` 뿐인데 문자열로 열려 있어, 생성 타입에서 권한 비교가 느슨해짐 |
| `UserRole` 정의가 두 모듈에 중복 | 한쪽만 고치면 조용히 갈림 → 한 곳으로 모음 |
| `/keyword-compare/parse` 가 `-> dict` | 응답 모양이 OpenAPI에 아예 없어 프런트가 통째로 손으로 적고 있었음 → Pydantic 계약 신설 |
| `/marketing/excel-periods` 가 `-> dict` | 위와 같음 → 계약 신설 |
| 순위 모니터링의 `status`·`device`·`source` 가 문자열 | 실제로는 정해진 값만 오므로 Literal로 좁힘 |
| 기능 플래그 키를 양쪽에서 손으로 관리 (FS3) | 백엔드 Literal 하나로 모으고, 기동 기본값과 어긋나지 않는지 **테스트로 고정** |

마지막 항목은 특히 조용한 종류의 버그였습니다. 기능 플래그 가드에 오타가 나면 그 가드는 "등록되지 않은 플래그"로 취급돼 **영원히 통과**합니다(fail-open 정책). 이제 선언되지 않은 키를 쓰면 테스트가 잡습니다.

## 남긴 것

화면에만 있는 타입(폼 상태, 컴포넌트 props, `'전체'` 같은 탭 필터)은 API 계약이 아니므로 그대로 손으로 둡니다. 어디까지가 계약이고 어디부터가 화면 사정인지 파일 안에 주석으로 구분해 두었습니다.

**결론부터 말씀드리면, 개발 중 "일단 되게" 넣어 두었던 우회·하드코딩을 전수 추적해, 각각의 원인을 분석한 뒤 근본 방식으로 다시 고쳤습니다.** 임시방편은 넣는 순간에는 무해해 보이지만, 전제가 바뀌는 순간(매체 정책 변경, 예상 밖의 입력) 조용히 틀리기 시작합니다. 전부 테스트로 고정했고, 백엔드 693건 · 프런트 타입검사 · **ESLint 전체 통과** · 프로덕션 빌드까지 확인했습니다.

## 판단 기준

제거 여부는 "하드코딩이냐"가 아니라 **"전제가 바뀌면 조용히 틀리느냐"** 로 갈랐습니다. API 가 명시적으로 거부하는 상한(예: 예상 입찰가 10위)처럼 전제 자체가 계약인 값은 상수로 두고 주석과 테스트로 고정했습니다 — 모든 값을 설정으로 빼는 것은 유연함이 아니라 책임 전가이기 때문입니다.
