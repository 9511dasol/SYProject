## 3. 이미지팩토리 구현 방식 리서치 — 2026-11-10 완료

**목적** — 크리에이티브 고도화(4~6번)의 구현 방향을 벤치마크 리서치로 확정.

**결과 요약** (상세: [imagefactory-research.md](imagefactory-research.md))
- 요소 편집: 임의 업로드 이미지는 "요소 인식 → 클릭 선택 → 선택 영역만 수정(인페인팅)"이 업계 표준 — 4번 과제의 구현 방향으로 채택
- 배경/변형: 스타일 프리셋 기반 병렬 변형 생성 → 그리드 제시 — 5번 과제 방향
- 리사이즈: 비율 차이에 따른 전략 자동 선택(단순 리사이즈 ↔ AI 아웃페인팅) + 동일 비율 생성 공유로 비용 절감 — 6번 과제 방향
- IR 포인트: 경쟁사는 "소재 제작→집행→성과" 루프가 해자. 우리는 실데이터 리포트·액션 제안(1·2번)이 크리에이티브 도구(4~6번)로 이어지는 역방향 흐름이 차별점.

## 4. 요소 분석 기반 이미지 간편 편집 — 2026-11-10 완료

**배경 / 문제**
- 기존 '이미지 정제'는 자유 텍스트 프롬프트만 받아서, "왼쪽 위의 할인 문구만 바꿔줘" 같은 부분 수정은 사용자가 위치를 말로 설명해야 했고 결과도 불안정했다.
- 벤치마크(이미지팩토리) 리서치 결과, 임의 업로드 이미지의 부분 수정은 "요소 인식 → 클릭 선택 → 선택 영역만 수정"이 업계 표준 방식.

**개선 내용**
- **요소 분석 단계 신설**: Gemini Vision이 업로드 이미지에서 구성 요소(헤드라인·로고·제품·뱃지·버튼·배경 등 최대 12개)를 bounding box와 함께 자동 검출.
- **클릭 선택 UI**: 검출된 요소를 이미지 위에 박스 오버레이로 표시 — 박스나 칩을 클릭해 수정 대상을 특정. 선택하지 않으면 기존 전체 편집 그대로.
- **정밀 편집 지시 자동 조합**: 선택한 요소의 이름·위치(비율 좌표)를 "이 영역만 수정, 나머지는 유지" 지시문으로 자동 변환해 편집 모델에 전달 — 사용자는 "문구를 겨울 세일로 바꿔줘"만 쓰면 된다.
- 요소 분석도 관리자 AI 사용량 로그·월 예산 게이트에 연동 (도구명: 이미지 요소 분석).

**기대 효과**
- 디자인 비전문가도 클릭 한 번으로 수정 지점을 특정 — 부분 수정의 지시 정확도와 재현성 향상.
- 광고 소재의 흔한 수정 요청(문구 교체, 뱃지 숫자 변경, 로고 정리)을 디자이너 왕복 없이 처리.

**검증**: 실제 광고형 배너로 요소 12개 검출·오버레이·선택 흐름을 화면으로 확인. 응답 파싱 견고성 테스트 6건 추가(전체 328건 통과). 구현 중 발견한 함정 — gemini-2.5는 thinking 토큰이 출력 한도를 소모해 JSON이 잘릴 수 있어 탐지 작업은 thinking을 끄고 호출한다.

## 5. 이미지 배경 자동 제안 — 2026-11-10 완료

**배경 / 문제**
- 광고 소재의 배경 교체는 수요가 많은 작업인데, 기존에는 프롬프트를 직접 써서 1장씩 만들어야 했다 — "여러 안을 놓고 고르는" 시안 비교가 불가능했다.

**개선 내용**
- 이미지 정제 화면에 **"배경 시안 제안" 카드** 신설: 버튼 한 번으로 피사체(제품·인물·문구)는 유지한 채 배경만 바꾼 시안 4종을 자동 생성해 그리드로 제시.
- 스타일 프리셋: 스튜디오 화이트 · 밝은 그라데이션 · 자연광 야외 · 럭셔리 다크 (광고 소재 수요 순).
- Gemini 이미지 생성을 **프리셋별 병렬 호출** — 일부 스타일이 실패해도 성공한 시안만 보여주고, 토큰은 합산해 사용량 로그 한 줄로 기록(도구명: 배경 시안 생성). 월 예산 게이트 연동.
- 마음에 드는 시안은 그 자리에서 다운로드, "다시 만들기"로 재생성.

**기대 효과**
- 배경 A/B 시안 제작이 "프롬프트 작성 → 1장 확인"의 반복에서 "클릭 한 번 → 4안 비교"로 단축.
- 벤치마크(이미지팩토리)의 변형(Vary) 개념을 배경에 특화해 적용한 첫 사례 — 추후 카피·레이아웃 변형으로 확장 가능.

**검증**: 병렬 호출·부분 실패·토큰 합산 로직 모킹 테스트 4건(전체 332건 통과), 업로드→생성→4종 그리드→다운로드 버튼까지 UI 전체 흐름 화면 확인(생성 호출만 로컬 목업). ※ Gemini 이미지 생성 모델(gemini-2.5-flash-image)은 **무료 등급 허용량이 0건**이라 실제 생성은 유료 결제가 연결된 API 키에서만 동작 — 기존 이미지 정제·AI 업스케일도 같은 모델을 쓰므로 운영 키는 유료 등급이어야 한다.

## 6. 이미지 리사이징 고도화 (매체 규격 일괄 변환) — 2026-11-10 완료

**배경 / 문제**
- 기존 리사이저는 지정 크기로 "늘려서" 맞추는 방식이라 비율이 다른 지면에선 이미지가 찌그러졌고, 매체마다 규격이 달라 소재 1장을 지면별로 일일이 변환해야 했다.

**개선 내용**
- **매체 규격 프리셋 8종** 내장: Meta 피드 1:1 / 4:5 / 스토리·릴스 9:16, Google 디스플레이 1.91:1 / 1:1, YouTube 썸네일 16:9, Naver 모바일 DA, Kakao 비즈보드.
- **비율 유지 중앙 크롭(cover) 변환** — 찌그러짐 없이 각 지면을 가득 채운다.
- **일괄 ZIP 다운로드**: 원하는 규격을 체크(또는 전체 선택)하면 소재 1장이 선택 규격 전부로 변환되어 zip 한 파일로 떨어진다. 파일명에 매체·크기가 들어가 입고 시 헷갈리지 않는다.
- 순수 Pillow 경로라 AI 비용 0 — 무제한 사용 가능.

**기대 효과**
- "소재 1장 → 전 매체 입고본" 제작이 클릭 한 번으로 단축 (기존: 지면 수만큼 수동 변환).
- 벤치마크(이미지팩토리)의 1,400개 지면 자동 변환을 국내 핵심 지면 8종으로 경량 구현한 1단계. 비율 차이가 큰 띠배너의 AI 아웃페인팅 채움, 스토리 세이프존 대응은 다음 확장 지점.

**검증**: cover 크롭 기하·zip 구성 테스트 5건(전체 337건 통과). 실화면 E2E — 업로드 → 전체 선택 → zip 다운로드 → 압축 해제 후 8개 파일 모두 규격 일치 확인.

## 1. YoY/MoM 기간 비교 리포트 — 2026-11-10 완료

**배경 / 문제**
- 월간 리뷰 화면은 선택한 달의 실적만 보여줘서, "지난달보다 좋아졌는가", "작년 이맘때와 비교하면 어떤가"를 보려면 달을 오가며 수치를 수기로 비교해야 했다.
- 광고는 계절성이 강해(예: 10월 성수기) 전월 비교만으로는 성과 판단이 왜곡된다 — 전년동월(YoY) 비교가 필수.

**개선 내용**
- 리포트 API가 당월 실적과 함께 **전월(MoM)·전년동월(YoY) 합계를 같이 반환**하도록 확장. 파생지표(CTR·CPC·ROAS)는 당월 리포트와 동일한 공식으로 계산해 증감률 왜곡을 방지.
- 대시보드 요약 탭에 두 가지 뷰 추가:
  - **KPI 카드 증감 칩**: 지표 10종 카드마다 `전월 +16.3% · 전년 -24.2%` 식 증감 표시. 양(量) 지표는 %, CTR·ROAS 같은 비율 지표는 %p로 표기. 색상은 "개선 여부" 기준(CPC는 하락이 초록, 광고비는 중립).
  - **기간 비교 표**: 전년동월 | 전월 | 당월 3개 기간을 지표별로 나란히 놓고 전년比·전월比를 함께 표시 (예: 25년 10월 vs 26년 9월 vs 26년 10월).
- 비교 달 데이터가 없으면 비교 블록을 숨겨 "-100%" 같은 거짓 증감이 나오지 않게 처리.

**기대 효과**
- 월간 리뷰에서 성과의 "방향"이 한눈에 보임 — 달을 오가며 수기로 비교하던 작업 제거.
- 계절성을 걷어낸 전년동월 비교로 성과 해석 정확도 향상. DB에 쌓인 과거 기간 데이터(2025-01~)의 활용 가치가 커짐.
- 백엔드 회귀 테스트 3건 추가, 전체 테스트 322건 통과로 안정성 확보.

## 2. CTR/ROAS 지표 기반 액션 제안 — 2026-11-10 완료

**배경 / 문제**
- 대시보드가 CTR(클릭률)·ROAS(비용 대비 매출) 수치를 보여주지만, 그래서 **무엇을 해야 하는지**는 담당자가 경험으로 판단해야 했다. 수치를 읽는 사람의 숙련도에 따라 대응 속도와 품질이 달라졌다.

**개선 내용**
- 요약 탭에 **"액션 제안" 섹션** 신설. 지표 상태를 읽어 점검이 필요한 신호와 권장 액션을 카드로 제시:
  - **ROAS 100% 미만** (광고비 > 매출) → 키워드 입찰가 하향 검토, 저효율 키워드 제외, 예산 재배분
  - **ROAS 전월 대비 급락** → 키워드 입찰가 확인, 매출 상위 키워드 집중
  - **CTR 하락** (소재 피로도 의심) → 소재 점검·교체, 카피/이미지 A·B 테스트
  - **CPC 급등** (입찰 경쟁 심화) → 입찰가 확인, 품질지수 점검
  - **전환율 하락** → 랜딩페이지·전환 경로 점검
  - **매체별 진단**: 특정 매체만 ROAS 100% 미만이거나 CTR이 계정 평균의 절반 이하이면 해당 매체를 지목해 제안
  - **긍정 신호**: CTR·ROAS 동반 개선 시 "잘 되는 소재·키워드 예산 확대" 제안
- 모든 제안에 **근거 수치를 함께 표기** (예: "구글 ROAS 83.3% (계정 전체 159.7%)") — 담당자가 제안의 타당성을 바로 검증 가능.
- AI 호출 없는 **결정적 룰 엔진**이라 토큰 비용 0, 리포트 열 때마다 즉시 계산. 임계값은 상수로 모아 운영하며 조정 가능. (1번에서 만든 전월/전년 비교 데이터를 재사용)

**기대 효과**
- 대시보드가 "수치 조회 도구"에서 **"다음 행동을 알려주는 도구"로 전환** — 주니어 담당자도 데이터 기반 대응 가능.
- 소재 교체·입찰가 조정 같은 핵심 운영 액션의 착수 시점이 빨라짐 (월말 리뷰 때가 아니라 리포트를 여는 즉시).

## 7. 동시성·데이터 안정성 개선 (P0) — 2026-11-16 완료

**배경 / 문제**

front/back 전수 점검에서 사용자 증가 직전에 반드시 해소해야 할 리스크 4건이 확인됐다.

1. **AI 작업 1건이 서버 전체를 멈춤** — CSV 분석·이미지 생성·LLM 코멘트가 `async` 함수 안에서 동기(블로킹)로 실행돼 그동안 이벤트 루프가 점유됐다. 특히 업로드 분석은 `async def`를 `BackgroundTasks`에 넘겨 스레드풀이 아닌 이벤트 루프에서 돌았고, 수십 MB CSV를 처리하는 내내 다른 모든 요청과 진행률 폴링까지 멈췄다. 동시 접속 2명이면 바로 드러나는 문제.
2. **업로드 실패 시 기존 데이터 영구 유실 가능** — 데이터 저장(`_upsert`)이 ①기존 행 DELETE 커밋 → ②INSERT(별도 트랜잭션) → ③되돌리기 스냅샷 저장 순서였다. ②가 끝내 실패하면 기존 행은 이미 지워졌는데 되돌릴 스냅샷도 아직 없어, 한 달치 성과 데이터가 복구 불가능하게 사라질 수 있었다.
3. **1자리 비밀번호로 가입 가능** — 길이 검증이 비밀번호 변경·재설정 경로에만 복사돼 있고 회원가입과 관리자 계정 생성에는 아예 없었다.
4. **LLM 호출에 타임아웃·재시도 없음** — Claude/OpenAI/Gemini 클라이언트 어디에도 한도가 없어, 공급자가 응답을 멈추면 요청이 무한정 매달렸다. 1번의 블로킹과 겹치면 전체 장애로 번진다.

**개선 내용**

- **블로킹 제거 (1번)**: 가짜 `async`(본문에 `await`가 없는) 함수를 동기로 되돌려 FastAPI가 스레드풀에서 실행하도록 하고, 업로드 읽기 때문에 `async`를 유지해야 하는 엔드포인트는 블로킹 구간만 `run_in_threadpool`로 넘겼다. 적용 범위는 마케팅 업로드 분석·미리보기·엑셀 내보내기·AI 코멘트, 이미지 편집/리사이즈/일괄변환, 헤딩 추천의 썸네일 업로드까지 총 19개 지점. 이미 올바르게 구현돼 있던 `_run_export_task`(동기 함수 + 스레드풀)를 기준 패턴으로 삼아 통일했다.
- **데이터 보존 (2번)**: 쓰기 순서를 **읽기 → 스냅샷 저장 → (삭제 + 삽입)** 으로 바꿔, 무엇이든 지우기 전에 복구 지점을 먼저 확보한다. 쓰기가 실패하면 스냅샷으로 자동 복구하고, 복구마저 실패해도 스냅샷이 DB에 남아 `undo_id`로 되돌릴 수 있다. INSERT를 작은 트랜잭션으로 쪼개는 기존 설계(Supabase 풀러 커넥션 리셋 회피)는 그대로 유지했다. 엑셀 '덮어쓰기' 경로는 기간 전체를 먼저 삭제·커밋한 뒤 저장하는 별도 구조라 같은 위험이 있어, 여기도 삭제 전 스냅샷 + 실패 시 복구를 적용했다.
- **비밀번호 정책 (3번)**: 검증을 `validate_password_policy()` 한 곳으로 모으고 비밀번호가 새로 정해지는 네 경로(가입·관리자 생성·변경·재설정)에 모두 적용. 프론트가 오류 사유를 `detail` 문자열로 읽기 때문에, 스키마 제약(422, 배열 응답) 대신 함수로 두어 "8자 이상" 안내가 화면에 그대로 뜨도록 했다.
- **LLM 한도 (4번)**: 세 공급자 클라이언트에 타임아웃·재시도를 적용(텍스트 60초 / 이미지 생성 180초, 재시도 2회). 네 곳에 흩어져 있던 Gemini 클라이언트 생성을 `build_genai_client()`로 모아 한도를 강제했다.

**기대 효과**

- **동시 사용 가능**: 블로킹 엔드포인트 2건 동시 요청이 2.40초(직렬) → 1.21초(병렬)로 개선. 심사·데모 환경에서 여러 명이 동시에 써도 서로를 막지 않는다.
- **데이터 신뢰성**: 업로드가 실패해도 기존 성과 데이터가 남는다. 데이터 신뢰성이 곧 제품 가치인 서비스에서 가장 치명적이던 리스크를 제거.
- **장애 격리**: AI 공급자 지연이 서비스 전체 정지로 번지지 않는다.

**검증**: 백엔드 테스트 342건 통과(데이터 유실 회귀 테스트 5건 신규 — 구 코드에서는 실패하는 진짜 회귀 테스트), ruff 통과, 앱 기동 및 OpenAPI 56개 경로 생성 확인. 동시성 개선은 실제 앱에 동시 요청을 보내 측정했고, 같은 작업을 `async`로 둔 대조군이 2.40초로 직렬화되는 것을 함께 확인해 측정의 유효성을 검증했다. 전환한 엔드포인트 전부를 sqlite로 실제 호출해 런타임 오류가 없음도 확인했다.

**사후 교차검증에서 추가로 잡은 것**: 작업 직후 변경분을 역으로 다시 검증해 3건을 보강했다 — ①복구 범위가 좁아 신규 기간의 부분 삽입 행이 남던 문제, ②되돌리기 테이블 장애가 업로드 자체를 막는 가용성 회귀(되돌릴 데이터가 없을 때는 계속 진행하도록 분기), ③블로킹 작업을 스레드풀로 옮기면서 동시 DB 커넥션 요구가 늘어난 것에 맞춘 커넥션 풀 상향(5+10 → 10+20).

## 8. 조회 성능·대용량 처리·오류 응답 개선 (P1) — 2026-11-16 완료

**배경 / 문제**

P0(동시성·데이터 안정성)로 "멈추지 않는" 기반을 만든 뒤, 데이터가 쌓이고 파일이 커질수록 드러날 문제들을 정리했다.

1. **AI 기능이 쓸수록 느려지는 구조** — 월 예산 게이트가 AI 호출마다 사용 로그를 `created_at` 기준으로 집계하는데 그 컬럼에 인덱스가 없었다. 로그가 쌓일수록 이미지 정제·헤딩 추천이 **함께** 느려진다.
2. **월별 조회가 인덱스를 못 탐** — 모든 월별 조회·집계가 `extract('year', 날짜) = 2026 AND extract('month', 날짜) = 10` 형태였다. 컬럼에 함수를 씌우면 날짜 인덱스를 쓰지 못해 매번 전체 스캔이다.
3. **대용량 다운로드가 메모리를 통째로 점유** — 프론트의 BFF가 엑셀/zip 파일 전체를 메모리에 올린 뒤 다시 내보냈다. 실제로 응답 크기 제한에 부딪혀 "엑셀을 메일로 받기" 우회 경로를 만들었던 원인이다.
4. **키워드 비교 표가 수천 행을 한 번에 그림** — 모바일 카드와 데스크톱 표를 **둘 다** 만들어 필터·정렬할 때마다 멈췄다. 행 식별자로 배열 순번을 써서 정렬을 바꾸면 모든 행이 불필요하게 다시 그려졌다.
5. **오류 메시지가 제각각이고 내부 사정을 노출** — 라우터 14곳이 원본 예외 문자열을 그대로 응답에 실어 DB 오류나 내부 경로가 화면까지 샐 수 있었다. 프론트는 그 메시지를 꺼내는 코드가 8벌 복제돼 있었고 우선순위가 달라 사유를 잃기도 했다.
6. **긴 AI 작업을 끊을 수단이 없음** — 이미지 편집은 수십 초가 걸리는데 취소 버튼이 없고, 서버가 멈추면 사용자는 무한정 기다려야 했다.

**개선 내용**

- **인덱스·쿼리 (1·2번)**: 사용 로그와 발송 기록의 `created_at`에 인덱스를 추가(마이그레이션 0007). 월별 조건을 `in_month()` 한 곳으로 모아 **날짜 범위 조건**(`해당 월 1일 ≤ 날짜 < 다음 달 1일`)으로 바꿔 인덱스를 타게 했다. 매체 예산 조회도 전 기간을 메모리로 읽어 걸러내던 것을 SQL 한 줄로 바꿨다.
- **스트리밍 (3번)**: BFF가 파일 바디를 버퍼링하지 않고 그대로 흘려보내도록 했다. 응답 크기 제약의 근본 원인을 제거.
- **표 렌더링 (4번)**: 한 번에 300행만 그리고 "더 보기"로 이어 받도록 했다. 행 식별자를 키워드·캠페인·기기·전환유형 조합으로 바꿔 정렬 시 불필요한 재렌더를 없앴다.
- **오류 응답 (5번)**: 전역 예외 핸들러를 두어 **서버 탓(5xx)은 사유를 로그에만 남기고** 사용자에겐 일반화된 안내를, **사용자가 고칠 수 있는 입력 오류(4xx)는 사유를 그대로** 보여주도록 경계를 정했다. 단, 관리자 전용 메일 재발송처럼 사유가 곧 조치인 화면은 그대로 노출을 유지했다. 프론트의 메시지 추출 8벌과 다운로드 코드 4벌도 공용 유틸로 합쳤다.
- **취소·타임아웃 (6번)**: 조회성 요청에 30초 상한을 두고, 수십 초가 정상인 AI 작업은 상한 대신 **취소 버튼**을 붙였다. 사용자가 직접 끊은 경우는 실패가 아니므로 오류로 표시하지 않는다.

**기대 효과**

- 사용량이 쌓여도 AI 기능 속도가 유지되고, 월별 조회·리포트 집계가 데이터 증가에 비례해 느려지지 않는다.
- 큰 엑셀을 우회 경로 없이 바로 받을 수 있다.
- 수천 행 키워드 비교가 즉시 뜨고 필터·정렬이 매끄럽다.
- 오류 화면에서 내부 정보가 노출되지 않으면서, 사용자가 고칠 수 있는 문제는 사유가 그대로 보인다.

**검증**: 백엔드 테스트 356건 통과(월 경계 8건·오류 응답 6건 신규), ruff·ESLint·타입 검사·프로덕션 빌드 통과. 실제로 로컬 전체 스택을 띄워 브라우저에서 확인했다 — 10월 집계가 시드와 정확히 일치(노출 50,000·비용 720,000)하고 인접 월이 섞이지 않음, 엑셀 내보내기 516KB가 BFF 스트리밍으로 파일명·형식 그대로 전달됨, 500 응답이 내부 정보 없이 일반 문구만 반환, 500행 업로드 시 300행만 그려지고 "200건 더 보기"가 뜨며 정렬을 바꾸면 다시 첫 페이지로 돌아감, 편집 중 취소 버튼이 나타나고 누르면 오류 없이 중단됨.

## 9. 중복 제거·안전망 확보 (P2) — 2026-11-16 완료

**배경 / 문제**

P0·P1 로 "멈추지 않고 빨라진" 뒤, 기능을 계속 더해도 깨지지 않을 바닥을 다졌다. 같은 규칙이 여러 곳에 복제돼 있으면 한쪽만 고쳐져 **같은 입력에 기능마다 다른 결과**가 나오는데, 실제로 그런 상태였다.

1. **투명 이미지가 기능마다 다르게 보임** — 알파 채널을 흰 배경에 합성하는 분기가 네 곳에 복제돼 있었고 서로 달랐다. 헤딩 썸네일은 일부 투명 형식을 놓쳤고, **요소 분석 썸네일은 투명한 부분이 검게 깔렸다**(합성 없이 변환하면 검정이 된다). 같은 소재를 올려도 AI 가 보는 그림이 기능마다 달랐다.
2. **AI 응답 파싱 규칙이 두 벌** — 모델이 ```json 코드블록이나 설명을 덧붙이는 걸 걷어내는 로직이 헤딩 추천과 요소 분석에 각각 있었다.
3. **사용량 기록 실패가 사용자 요청을 깨뜨림** — 이미지·헤딩 라우터가 각자 기록을 남기면서, 기록이 실패하면 그대로 오류가 났다. AI 호출은 이미 끝나 토큰을 쓴 뒤라 **사용자는 실패한 줄 알고 다시 눌러 토큰을 한 번 더** 썼다.
4. **메일 발송이 GET 으로 트리거됨** — 부작용이 있는 동작인데 링크 프리페치나 캐시로 의도치 않게 발송될 수 있었고, 비동기 경로에는 있는 AI 예산 게이트도 이 경로에만 빠져 있었다.
5. **발송 기록 저장이 요청 전체를 커밋** — 호출자가 넘긴 세션에 기록을 쓰고 커밋해서, 그 요청에서 대기 중이던 다른 변경까지 함께 저장될 수 있었다.
6. **업로드 입구에 테스트가 없음** — 매체마다 다른 CSV 를 받아들이는 가장 복잡한 코드인데 직접 테스트가 없었다(코드 주석에 "컬럼명이 바뀌어 500" 같은 이력이 남아 있다).
7. **엑셀 리포트에 계약이 없음** — 백엔드가 순수 dict 를 돌려주고 프론트가 그 모양을 손으로 베껴 둔 탓에, 파서가 키를 바꿔도 아무도 못 잡고 화면에서 조용히 빈칸이 됐다.
8. **화면 로직 복제** — 파일 업로드·미리보기·비율 계산이 두 화면에, 끌어다 놓기가 네 곳에 복제돼 있었다.

**개선 내용**

- **이미지·파싱 규칙 통일 (1·2번)**: 알파 합성을 `image_util` 한곳으로 모아 "투명한 곳은 흰색"으로 통일하고, LLM 응답에서 JSON 을 꺼내는 규칙은 `llm_json` 으로 합쳤다.
- **사용량 기록 일원화 (3번)**: 다섯 곳이 각자 하던 기록을 전용 세션을 쓰는 창구 하나로 모아, 기록 실패가 사용자 요청을 깨뜨리지 않게 했다.
- **발송 경로 정리 (4·5번)**: 동기 발송을 POST + 관리자 전용 + 예산 게이트로 바꾸고, 발송 기록은 전용 세션으로 분리했다.
- **입구 테스트 (6번)**: CSV 포맷·인코딩 감지(네이버 2행 헤더, 카카오 1행, 구글 UTF-16 탭, cp949, 엑셀 오업로드), 컬럼명 별칭, 기간 추출, 매체 분류, 집계까지 43건을 고정했다. **이 과정에서 실제 버그를 찾았다** — 파일명에서 기간을 읽는 규칙이 `네이버_26.05.csv` 처럼 밑줄이나 한글이 앞에 오면 동작하지 않아, 기간을 못 읽고 조용히 기본값으로 넘어가고 있었다.
- **엑셀 리포트 계약 (7번)**: 응답 스키마를 정의해 파서 출력이 어긋나면 서버에서 걸리게 하고, OpenAPI 에 실어 프론트 타입을 코드젠할 근거를 만들었다. 셀 값 타입은 일부러 열어 뒀다 — 목적은 구조 드리프트를 잡는 것이지 셀 타입 단속이 아니고, 좁히면 멀쩡한 파일이 막힌다.
- **화면 로직 공용화 (8번)**: `useImageUpload`(업로드·미리보기·치수 측정·URL 해제), `useAspectRatioInputs`(비율 연동), `useFileDrop`(끌어다 놓기)로 추출했다. 끌어다 놓기는 `preventDefault` 를 빠뜨리면 브라우저가 그 파일을 열어 작업하던 화면이 날아가는데, 네 곳이 각자 기억해야 할 일이었다. 더불어 업로드 영역이 **Space 키로도 열리도록** 고쳤다(예전엔 Enter 만).

**기대 효과**

- 같은 소재를 어느 기능에 넣어도 같은 결과가 나온다 — 기능별로 다르게 동작하던 투명 처리 제거.
- 사용량 기록 문제로 사용자가 토큰을 두 번 쓰는 일이 없어진다.
- 업로드 입구와 리포트 계약에 안전망이 생겨, 매체가 양식을 바꾸거나 파서를 손볼 때 **배포 전에** 걸린다.
- 화면 로직이 한곳에 모여, 고칠 일이 생겼을 때 한 번만 고치면 된다.

**검증**: 백엔드 테스트 417건 통과(이미지 합성 10건·업로드 입구 43건·리포트 계약 8건 신규), ruff·ESLint·타입 검사·프로덕션 빌드 통과. 리팩터링한 화면은 실제로 띄워 확인했다 — 800×600 업로드 시 치수가 자동으로 채워지고 비율 연동이 양방향 모두 정확(400→300, 150→200), 끌어다 놓기가 상태 전환·기본동작 차단·파일 수용까지 동작, Space·Enter 양쪽으로 업로드 창이 열림. 리포트 계약은 실제로 내보낸 516KB 엑셀을 다시 불러오는 왕복으로 확인했다(비교 8행·예산 8줄·매체 5시트 모두 통과).

## 10. 사후 교차검증·마무리 (P3) — 2026-11-16 완료

**배경 / 문제**

P0~P2 를 커밋한 뒤, **그 변경분 자체를 다시 적대적으로 검증**했다. 고치는 과정에서 새로 들어간 문제를 찾는 것이 목적이었고, 실제로 **직전 작업이 만든 회귀 2건**이 나왔다.

1. **예산 상속이 끊김 (가장 심각)** — 월별 예산 조회를 SQL 로 내리면서 "값이 있는 행"을 `IS NOT NULL` 로 판정했다. 그런데 관리자가 예산을 **비우면** 컬럼에 저장되는 값이 SQL NULL 이 아니라 JSON null 이라, 비워 둔 달이 "가장 최근 값"으로 뽑혀 **그 달부터 이후 모든 달의 예산이 0** 이 됐다. 예산소진율·잔여광고비가 통째로 0 이 되는, 이 기능이 막으려던 바로 그 상황이다.
2. **날짜를 기간으로 오인** — 파일명 기간 추출을 고치면서 `네이버_05.01~05.31.csv` 같은 **날짜 범위**까지 연·월로 읽혀 "2005년 1월" 리포트가 만들어졌다. 게다가 파일명에서 읽으면 더 믿을 만한 CSV 제목행 탐색으로 넘어가지 않는다.
3. **되돌릴 수 없는 작업이 "실패"로 보임** — 조회 요청에 30초 상한을 걸면서, 서버에서 오래 걸리는 **메일 재발송**과 **기간 삭제**까지 상한에 걸렸다. 브라우저가 요청을 끊어도 서버 작업은 계속되므로, 관리자는 실패로 보고 다시 누르고 → 같은 수신자에게 메일이 두 번 나간다.
4. **스레드가 커넥션보다 많음** — 블로킹 작업을 스레드풀로 옮기면서 동시에 DB 를 때리는 요청이 늘었는데, 워커 스레드(40)가 커넥션 풀(30)보다 많아 스레드는 남고 커넥션이 없어 대기하다 실패하는 조합이 됐다.
5. **행이 화면에서 사라질 수 있음** — 키워드 표의 행 키를 네 값의 조합으로 바꿨는데, 이미 비교된 통합 시트는 같은 조합이 두 줄 이상 올 수 있어 키가 겹치면 그 행이 누락된다.
6. **잘린 파일** — 다운로드를 스트리밍으로 바꾸면서 원본 `Content-Length` 를 그대로 전달했다. 응답이 압축되면 그 길이가 실제 전송량과 어긋나 엑셀·zip 이 잘린 채 받아진다(압축을 켜는 순간 터지는 잠복 버그).

**개선 내용**

- 위 6건을 모두 수정하고, **회귀를 재현하는 테스트**를 붙였다(예산 상속 10건, 날짜 오인 5건). 고치기 전 코드로 되돌려 테스트가 실제로 실패하는 것까지 확인했다.
- 되돌릴 수 없는 작업에는 상한을 걸지 않도록 분리하고, 워커 스레드를 커넥션 풀 크기에 맞췄다 — 초과분이 "실패" 대신 "대기"로 줄을 선다.
- 긴 AI 작업 세 곳(요소 분석·배경 시안·헤딩 생성)에 **취소 버튼**을 마저 붙였다. 직전 작업에서 이미지 편집 한 곳만 해결돼 있었다.
- **replace 저장 후 "되돌리기"가 아무것도 복원하지 않으면서 성공이라고 보고**하던 문제를 고쳤다 — 삭제 직전 스냅샷을 되돌리기 기준으로 연결하고, 되돌릴 것이 없을 때는 그 사실을 그대로 알린다.
- 그 밖에: 헤딩 화면의 미리보기 URL 누수(정리 함수가 첫 렌더 값에 묶여 아무것도 해제하지 못했다), 같은 파일을 다시 골랐을 때 이전 시안이 남던 문제, 큰 그림 → 작은 그림으로 빠르게 바꿀 때 늦게 도착한 치수가 덮어쓰던 경합, 구형 브라우저에서 타임아웃이 조용히 사라지던 문제를 함께 정리했다.
- 보조 정리: Pydantic 설정 방식 통일, 발송 이력 조회의 레포 우회·페이지네이션 보완, 관리자 화면 전용 오류 경계 추가(한 화면의 오류가 앱 전체를 덮지 않는다), 브라우저 저장 공간이 꽉 찼을 때 조용히 실패하던 리포트 보관에 정리 정책과 안내 추가.

**기대 효과**

- "고치는 과정에서 새로 넣은 문제"를 배포 전에 걷어냈다. 특히 예산 상속 회귀는 엑셀 리포트의 숫자가 통째로 틀어지는 문제라 발견이 늦었으면 비용이 컸다.
- 되돌릴 수 없는 작업에서 "실패로 보이지만 실제로는 수행됨" 이 사라져, 메일 중복 발송과 중복 과금 경로가 막혔다.
- 오래 걸리는 AI 작업을 전부 끊을 수 있다 — 새로고침 말고는 방법이 없던 화면이 없어졌다.

**검증**: 백엔드 테스트 432건 통과(예산 상속 10건·날짜 오인 5건 신규), ruff·ESLint·타입 검사·프로덕션 빌드 통과. 수정은 실제로 띄워 확인했다 — 11월 예산을 비워도 12월이 10월 값을 그대로 상속(`inherited_from: 2026-10`), 기동 시 워커 스레드가 커넥션 풀 크기로 맞춰짐, 500행 업로드 후 정렬을 바꿔도 300행이 유지되고 중복 키 경고 없음, 전월이 비면 "선택하세요"로 표시됨.

**방법 메모**: 이번 작업의 버그는 전부 "변경분을 다시 읽는" 교차검증에서 나왔다. 테스트·타입 검사·빌드는 전부 통과한 상태였고, 그것만으로는 잡히지 않는 종류였다(JSON null 과 SQL NULL 의 차이, 정규식이 넓어지며 생긴 오탐, 상한을 걸면 안 되는 작업). 큰 변경 뒤에는 같은 코드를 다른 관점으로 한 번 더 보는 단계를 두는 편이 좋다.
