# 멀티테넌시 개편 기획 확정 문서

- 작성일: 2026-11-25
- 상태: **기획 확정** (구현 미착수)
- 범위: 권한 체계 개편(dev 역할 신설), 기업 단위 멀티테넌시 도입, dev 전용 관리자 페이지, 체험(trial) 계정 시스템

---

## 1. 한 줄 요약

단일 테넌트 구조인 현재 시스템을 **기업(테넌트) 단위로 완전히 분리**하고, 그 위에 `dev`(개발자) > `admin`(기업 관리자) > `member`(사원) 3단계 권한과 **자동 만료되는 체험 계정**을 올립니다. 핵심 원칙은 "**한 기업의 데이터는 그 기업 소속 계정만 접근할 수 있다**"이며, 이를 코드 한 줄의 실수로도 깨지지 않도록 3중 방어로 설계합니다.

## 2. 배경과 현황 (2026-11-25 코드 탐색 기준)

현재 코드는 전면적인 단일 테넌트 전제입니다.

| 영역 | 현재 상태 | 근거 위치 |
|---|---|---|
| 역할 | `user` / `admin` 2단계뿐 | `back/app/models/user_model.py` |
| 기업 개념 | 없음 — `company_id` 컬럼이 어느 테이블에도 없음 | 백엔드 전체 grep 0건 |
| 데이터 격리 | 없음 — 앱 레벨 `require_admin`만 존재, RLS 미사용 | `back/app/core/security.py` |
| 토큰 사용량 | 로그·월 예산 429 차단 **이미 구현** (단, 전역 싱글턴) | `ai_tool_usage_logs`, `back/app/core/ai_budget.py` |
| 관리자 페이지 | `/admin` (users·settings·ai-usage-logs·report-logs·periods) | `front/app/admin/` |

따라서 이번 개편은 페이지 추가가 아니라 **모든 데이터 테이블과 모든 API가 영향을 받는 구조 전환**입니다.

## 3. 역할 체계

```
dev (개발자/플랫폼 운영자)
 └─ 기업 "sy"      ── admin 1명 ── member 들   ← 기존 데이터 전부 백필
 └─ 기업 B          ── admin 1명 ── member 들
 └─ 체험 샌드박스 기업 ── trial 1명 (2~3일 후 자동 소멸)
```

| 역할 | 소속 | 권한 요약 |
|---|---|---|
| `dev` | 없음 (`company_id = NULL`) | 기업·계정·토큰 예산·감사 로그·체험 계정 관리. 기업 실데이터 열람은 가능하되 **감사 로그 필수 기록** |
| `admin` | 기업당 **정확히 1개** | 자기 기업 데이터 전체 CRUD, 자기 기업 사용량 조회. 사용자 관리는 **자신의 계정과 자기 기업 사원 계정만** 조회·생성·관리 가능 |
| `member` | 기업 소속 | 자기 기업 데이터 CRUD (업무 기능 사용) |
| `trial` | 전용 샌드박스 기업 | 샌드박스 안에서만 데이터 조작·기능 체험. 계정 관리·메일 발송 등 외부 영향 기능 차단 |

**기업당 admin 1개 강제**: 애플리케이션 코드가 아니라 DB 제약으로 보장합니다.

```sql
CREATE UNIQUE INDEX uq_one_admin_per_company
  ON users (company_id) WHERE role = 'admin';
```

## 4. 데이터 모델 변경

### 4.1 신규 테이블

- **`companies`**: `id, name, is_active, is_trial, expires_at(체험용, NULL 허용), created_at`
- **`audit_logs`**: `id, actor_user_id, actor_role, action, target_type, target_id, company_id(대상), detail(JSON), created_at`

### 4.2 기존 테이블 변경

- `users`: `company_id` FK 추가 (dev만 NULL 허용), `role` 값 체계를 `dev | admin | member | trial`로 전환
- **모든 비즈니스 테이블에 `company_id` 추가**: `marketing_period_meta`, `marketing_data`, `ai_tool_usage_logs`, `report_logs`, `heading_suggestions`, `keyword_watch`, `rank_alert_logs`, `undo_snapshots`, `background_tasks`, `embeddings` 등
- `ai_usage_budget`: 전역 싱글턴(id=1) → **기업당 1 row** (기업별 월 토큰 예산)
- `system_settings`·기능 플래그: **전역 유지** (dev만 제어) — 확정 결정

### 4.3 마이그레이션 전략

1. `companies` 생성 → 첫 기업 **"sy"** 1건 삽입
2. 각 테이블에 `company_id` nullable로 추가 → 기존 데이터 전부 sy로 백필
3. `NOT NULL` 전환 + FK + 인덱스 (users의 dev는 NULL 예외)
4. admin 1개 partial unique index 적용

## 5. 데이터 격리 보안 — 3중 방어

"서비스 코드에서 필터를 한 번 깜빡하면 뚫리는" 구조를 금지하는 것이 설계 목표입니다.

### 1층 — 신뢰 원천은 JWT뿐
`company_id`와 `role`을 access token claim에 포함하고, **요청 바디·쿼리스트링으로 들어오는 company_id는 절대 신뢰하지 않습니다.** 남의 ID를 찍어 접근하는 IDOR 공격의 원천 차단입니다.

### 2층 — 리포지토리 계층 강제 스코핑
FastAPI 의존성으로 `TenantContext(company_id, role)`를 주입하고, 리포지토리 생성 시 company_id를 **필수 인자**로 받아 모든 쿼리에 자동으로 `WHERE company_id = ?`가 붙게 합니다. 개별 라우터가 필터를 "기억"할 필요가 없는 구조입니다.

### 3층 — Postgres RLS (2차 방어선)
Supabase(Postgres)에서 요청마다 `SET LOCAL app.current_company_id`를 설정하고 전 테이블에 RLS 정책을 겁니다. 1·2층에 버그가 생겨도 DB가 최종 차단합니다. 로컬 SQLite 폴백 환경에는 RLS가 없으므로 1·2층이 primary 방어입니다.

### 추가 보안 원칙

- **타 기업 리소스 접근 시 403이 아닌 404 반환** — 리소스가 존재한다는 사실 자체를 노출하지 않음
- **감사 로그**: dev의 모든 행위, admin의 계정 관리 행위, dev의 기업 데이터 열람을 `audit_logs`에 기록. dev 페이지에서 조회 가능
- **공개 회원가입 없음**: dev가 기업+admin을 발급하고, admin이 자기 기업 사원을 직접 생성(초대 메일 없음 — 확정 결정)
- **기업 정지 즉시 반영**: `is_active=false`면 소속 계정의 토큰 refresh 시점에 DB 재확인으로 차단 (기존 refresh 구조 활용)

## 6. dev 전용 관리자 페이지

- 경로: 프론트 `/dev`, API `/api/dev/*` (가드: `require_dev` 의존성 + 프론트 proxy 경로 차단)
- 기능:
  1. **기업 관리** — 생성·정지·삭제(soft), 기업별 admin 계정 발급·비밀번호 초기화
  2. **계정 관리** — **기업별로 모든 계정을 조회·생성·수정·삭제** 가능, 잠금 해제, 활성/비활성
  3. **토큰 사용량** — 기업별·월별 집계 대시보드, 기업별 예산 설정
  4. **감사 로그 뷰**
  5. **체험 계정 발급·관리** (7장)
  6. **기능 플래그(전역) 제어** — 기존 `/admin/settings`에 있던 플래그 관리를 dev 전용 관리자 페이지로 **이동** (기업 admin 페이지에서는 제거)

기존 `/admin` 페이지는 "기업 admin" 범위로 축소합니다: 사용자 관리는 **자신의 계정과 자기 기업 사원 계정만** 조회·생성·관리하고, 자기 기업 사용량을 조회합니다. 기능 플래그·시스템 설정 관리는 dev 페이지로 이동합니다.

## 7. 체험(trial) 계정 시스템

**설계 원칙: 체험 계정을 특별 권한으로 만들지 않고, "유통기한 있는 샌드박스 기업"으로 만든다.**

trial에게 "실데이터는 못 보지만 임의 데이터는 조작 가능"이라는 예외 규칙을 권한 로직에 심으면 격리 체계에 구멍이 나기 쉽습니다. 대신 멀티테넌시 격리를 그대로 활용합니다.

### 발급 (dev 페이지에서 버튼 1개)

1. 샌드박스 기업 생성: `is_trial = true`, `expires_at = 발급 + 2~3일` (발급 시 2일/3일 선택)
2. trial 계정 1개 생성 (해당 기업 소속)
3. **샘플 데이터 자동 시드** — 랜딩 페이지 목업용 예시 데이터셋 재활용
4. 화면에 아이디·초기 비밀번호 표시 → 예비 클라이언트에게 전달

실데이터 접근 불가는 별도 규칙이 아니라 **테넌시 격리 자체로 자동 보장**되며, 샌드박스 안에서는 데이터를 자유롭게 넣고 지우며 "이렇게 작동됩니다"를 실제 조작으로 보여줄 수 있습니다.

### 자동 삭제 (2중)

- **즉시 차단**: 로그인·토큰 refresh 시점에 `expires_at` 검사 → 만료면 그 자리에서 거부 (정리 잡이 아직 안 돌았어도 접근 불가)
- **물리 삭제**: 하루 1회 정리 잡이 만료된 trial 기업을 데이터째 삭제 (NCP VM cron 또는 앱 내 스케줄러)

### 남용 방지

- trial 기업에 **토큰 예산 소액 기본값** (기업별 예산 체계 활용 — LLM 비용 폭주 방지)
- 리포트 메일 발송 등 외부로 나가는 기능 차단
- 사원 생성·계정 관리 기능 없음
- dev 페이지 목록에서 남은 기간 확인, 연장·즉시 삭제 가능

| ⑤ | 기존 `/admin` 페이지를 기업 admin 범위로 축소 | **✅ 완료 (2026-11-25)** — 플래그·AI 상태를 dev 전용으로 이동(`/dev/settings`, API 가드 require_dev), admin 사용자 화면은 사원 생성 전용으로 정리 |
| ⑥ | Supabase RLS 정책 적용 | **보류 (근거 있음)** — 현재 DB 접속이 소유자(postgres) 계정이라 RLS 가 무시된다(BYPASSRLS). 효과를 보려면 전용 역할 분리 + 요청마다 `SET LOCAL` 을 거는 작업이 선행돼야 하므로, 앱 계층 격리가 실기동까지 검증된 지금은 다음 라운드 과제로 둔다 |
| ⑧ | 과도기 장치 제거 (`server_default` 기본값) | **✅ 완료 (2026-11-25)** — 리비전 0015. 소속 누락이 조용히 sy 로 귀속되는 대신 즉시 실패하게 전환 |
| ⑦ | **크로스 테넌트 격리 자동 테스트**: A기업 토큰으로 B기업 데이터 전 엔드포인트 접근 → 전부 404 확인을 CI에 상설화 | 이후 기능 추가 시 격리 회귀 방지 |

## 10. 미결·추후 과제

- 체험 기간 기본값(2일 vs 3일)과 trial 토큰 예산 기본값 수치 — 구현 시 결정
- dev 계정의 2FA 도입 여부 — 추후 검토
- 기업별 플랜(요금제) 개념 — `companies` 테이블에 확장 여지만 남겨둠
